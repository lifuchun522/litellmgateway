别谈架构美学。客户端只认一个模型名，上游换供应商不该改客户端一行配置。第八章就干这件事，谁负责。
客户买的是 coding-fast 这个名字，不关心背后是哪家上游。别名要能今天切便宜、明天切稳，还不许停机。
上个月上游故障，我们改配置重启，客户看到的模型名跟着变了，工单炸了三天。这种事不能再有第二次。
LiteLLM、OpenRouter、OneAPI 都是别名映射多上游，价格和健康挂在上游条目上。分层是行业默认，不是我们发明。
一期只做三张表加关系图：LogicalModel、Provider、Deployment。别名解析、权重路由、价格版本化必须做，计费出账先不做。
两个方案。A 是一张表塞 provider、上游模型、价格和权重，改一处全表动。B 是三张表加绑定关系，多一次 join，换边界干净。
B 写起来不难，难在改价格会不会污染历史账单。我要求价格单独带 priceVersion，调用时把版本号写进日志，不然对不上账。
成功线我先定：切上游后客户端模型名变更次数为零。基线是上个月那次故障，模型名变更一次，报错工单十七张。
搜多模型路由的人想知道怎么按别名切上游，文档要把三层讲成一张关系图。别名可读性直接影响文档能不能被收录和引用。
这次不投。开发者工具靠文档和口碑，投搜索广告 CAC 至少八十块，开源 demo 的用户撑不住，先把转化埋点做上再说。
三张表加关系图，两个人两周能收。我批的预算线是不超过八人日，超了先砍关系图页面，账我不认第二次。
价格版本化要写进设计：历史费用按 priceVersion 快照结算，价格表只增不改。谁敢 UPDATE 历史价格，对账就敢跟谁翻脸。
顺序定死：先逆向 Demo 改包名，再建三张表，再写解析路由，最后做页面。Bob 管契约，Alex 管实现，Emma 管验收。
听了运维那次故障复盘，我收回多上游自动切换那句。一期只承诺别名稳定，切换先手动，别把不确定性卖给客户。
一线标准是这样：切换只改 Deployment 的权重或者 Provider，客户端那段配置一个字不动。做到这个，工单才算闭环。
外部证据和 B 方案一致。补一点：竞品都保留了价格版本字段，我们不做，第三方对账时一定会有争议。
范围重冻：一期三张表、别名解析、权重路由、价格版本化；关系图页面降级成只读拓扑；多租户和计费明确不做。
最终选 B。牺牲一次 join 和一张表的写入复杂度，换来上游可替换、价格可追溯。最坏情况退回单 Provider 直连。
路径定了：Deployment 带 weight 和 health，解析时按权重排序，不健康的直接跳过。调用日志异步写，带上 priceVersion。
上线指标：别名解析成功率九十九点九，切上游后客户端零改动。停止线是模型名变更引发的工单一周超过两张，直接回退。
把三层分离做成一张关系图加一篇迁移文档，目标是被搜到被引用。两周后看文档自然访问量和仓库 star 增速。
确认不投广告。只在技术社区发一篇分层设计文，测点击率和仓库跳转。零 CAC 的渠道先跑，跑通了再加钱。
预算维持八人日，关系图页面超两小时就砍。回本不看收入，看后续接新 Provider 的人日从两天降到半天。
过了。责任边界写清：Provider 密钥由接入方提供，泄露我们不担责；价格快照只增不删，审计留痕满足对账要求。
Owner 定了：Bob 周四交三层契约和表结构；Alex 下周三提交 chapter/08-logical-model-deployment；Emma 验收替换 Provider 客户端零改动。
就这么定。三张表、别名解析、priceVersion，先做这个，别的砍掉。替换上游只动配置，客户端模型名不变。散会。
