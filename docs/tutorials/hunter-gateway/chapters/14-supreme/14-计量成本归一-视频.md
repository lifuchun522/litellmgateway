第14章只做一件事：让一次请求的 token 变成可追溯的成本。usage 到 cost 到报表，一条链打通。
客户不为 token 表付费，为客户能自己解释账单付费。按 Project 和 Key 拆账，才是能续费的展示面。
客户问这个月为什么贵了，我们现在答不出。报表要能按 Key 和模型下钻，不然每笔争议都得人工翻日志。
三家网关文档都显示：上游在流式最后一个 chunk 回 usage。有真实值就优先用真实值，这是通行口径。
一期只做四件事：标准化 usage、算 cost、日聚合、一张趋势页。预算告警和多币种结算，全部不进。
两个候选。A 请求日志同步写 usage 和 cost；B 先落事件队列，再异步聚合。A 简单但写放大，B 多一跳但扛量。
流式请求断在最后一个 chunk，usage 就丢了。必须按 chunk 累加兜底、标记 ESTIMATED，不能算零也不能整条判失败。
先立基线：usageSource 真实值占比、聚合 cost 与上游账单差异率。差异率超百分之二，是信号不是噪声。
开发者搜的是 LLM 网关怎么算 token 成本。文档页要写清 usage 字段和价格版本，让自然流量直接落到成本口径。
这次我不主张投流。成本核算的受众是已有客户，花钱买不来新客，先把开通后的转化事件埋干净再说。
月聚合按天分区，保留十三个月，跑在现有实例上，不新增集群。增量成本我给它每月两千块上限。
价格表和 priceVersion 必须落库留痕，客户对账时要能复现当时单价。改价不许覆盖历史，只能新增版本。
我按两棒排：Alex 打通写入与成本计算，David 做聚合和指标。每棒收尾都必须有一次端到端可追溯演示。
Bob 的异步方案长期我认，但一期不上队列，先同步写，压测到瓶颈再换。省下的时间全给可追溯验收。
听完架构取舍，我把卖点收成一句：客户能按 Project 看到本月花了多少、花在哪个模型上。预算告警延后。
一线标准就一条：客户拿着账单截图来问，客服不找研发，点三下就能看到那条请求的 usage 和价格版本。
我又查了计量口径，各家对缓存命中的计费规则并不统一。建议一期如实记录 usageSource，不做缓存折扣推断。
按 Iris 这条反证，范围重冻：缓存折扣、多币种、预算告警全部出局，一期口径就是原始 usage 加线性计价。
最终取舍：牺牲写入吞吐余量，换来一期零新增中间件和可追溯闭环。量上来以后，再把写路径换成事件队列。
路径定了：Gateway 统一归一化 usage，Deployment 带价格版本，同步算 cost 落日志，日聚合凌晨跑且可重跑。
成功线：真实 usage 占比过九成，聚合 cost 与上游账单差异率低于百分之二。停止线：差异率超百分之五就停上线查口径。
成本口径写成一页文档，标题用开发者常见问法，内链到 usage 字段和 priceVersion。验证就看这页的自然搜索进入量。
付费这边明确不投。只提一个要求：把 usage 和 cost 页面的开通请求接成转化事件，给下一章多租户增长留数据。
预算确认：无新集群，月增量不超两千。ROI 门槛是账单争议工单每月降三成，达不到就缩到只留内部报表。
修正后的方案过了合规门槛：价格版本留痕、usage 只存 token 数不存正文、请求 ID 可对账。红线是不得事后改历史单价。
Owner 定了：Alex 做 usage 归一化与 cost 计算，David 做日聚合与指标，我负责验收。三天后交第一版可追溯演示。
拍板：分支 chapter/14-metering-cost，一次请求从 usage 到 cost 到报表必须可追溯。做不到，这章就不算完成。
