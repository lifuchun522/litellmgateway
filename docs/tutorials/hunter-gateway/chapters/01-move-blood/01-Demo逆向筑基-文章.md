# 解压并逆向 open-api.zip：为 LLM Gateway 冻结 0 号代码基线

> 不改一行代码，先让 Demo 的底牌全部亮出来

```text
[读者] 拿到一份 LLM Gateway Demo 压缩包、被要求“先别重写”的 Java 后端
[痛点] 代码能打开，却说不清有哪些模块、请求怎么走、哪些能复用
[现在读] 后面每一章都要在这份基线上增量改，基线不清就是一路返工
[读完] 拿到可回归的 As-Is 文档、复用矩阵与冻结哈希
```

```text
[旧方案] 打开 IDE，边读边猜，边猜边改
    |
    v
[新需求] 长期增量演进，需要一条能反复回归的 0 号基线
    |
    v
[冲突] 没有逆向结论，任何“重构”都只是把未知换成另一种未知
    |
    v
[后果] 改到后面才发现某段逻辑早就有了，或早就该删
```

我是老李。上周接手的活儿很具体：一个 Java 轻量级 LLM Gateway 项目，起点是仓库里那份 open-api.zip，团队明确要求不重新造骨架，先在既有 Demo 上做增量。听起来省事，实际上最难受的恰恰是这句话——它把“设计”这件舒服的事推后了，把“读懂别人代码”这件难受的事提到了第一天。

我把 zip 解开，目录能展开，Spring Boot 的启动类在，Controller 也在，看着像一份能跑的工程。可当有人问我三个问题——这份 Demo 到底已经有什么、一个请求从入口走到哪里、哪些代码可以直接搬进新项目——我发现我只能说“大概是这样吧”。这不是能力问题，是流程问题：我从来没把“读代码”当成一件必须有产出的活儿。

任务是：在不改一行源码的前提下，把这份 Demo 逆向成一份可验证的 As-Is 基线，冻结它，然后才允许动刀。这一章的产物不是功能，是一份别人能拿去复核的判断。

问题一：一份别人写的、没有任何设计文档的 Demo，凭什么能逆向外推到“哪些代码可以复用”这种结论？

问题二：我是该先按习惯做一次大规模包名替换、把项目变成“我的”，还是先原样跑起来、把旧的跑法钉死？

问题三：如果这一章的产物主要是一份 Markdown，那它到底解决了什么问题？会不会只是给“多看两天代码”换个好听的名字？

# 01、故事

现场是这样的：仓库根目录挂着一个 open-api.zip，解压后是一个典型的 Java 后端工程，配套一个管理端页面。它是别人写的，没有设计文档，没有接口契约文件，没有迁移说明。团队要在这个基础上长出 Provider 适配、模型路由、虚拟密钥、限流预算、可观测这些能力，并且明确要求——不重新造骨架。

当前方案很朴素：谁要改哪块，谁就去读那块代码。听起来合理，实际执行起来是灾难。三个人读同一份代码，得到三种“这个类大概是干嘛的”。没人能回答“这个方法被谁调用”，也没人敢删任何一行——删了怕炸，留着怕脏。

变化来自要求本身：从“把网关做出来”变成“在既有骨架上把网关做出来”。这句话的潜台词是——你对旧代码的理解，会被反复检验，而且检验你的是后面每一章的增量改动。

冲突就在这里：动手的冲动，和读懂的耐心，天然对立。改包名只要一次全局替换，十分钟就能让工程改名换姓，看上去进度飞快；可一旦替换完成，旧的那条“原样能跑通”的参照线就永久丢失了。后面任何一个故障，你都无法判断是自己改坏的，还是它本来就有病。

所以我给自己定了一条硬规矩：0 号基线的第一属性不是“能用”，而是“可回归”。在它被冻结之前，一行源码都不许动。

> 包未解先读
> 名未改先记
> 链未走先画
> 基未冻先停

# 02、问题

旧方案失效的表现非常直接：当被问到“这个 Demo 已有什么”时，回答依赖个人记忆；当被问到“请求怎么走”时，回答依赖临时翻代码；当被问到“哪些能复用”时，回答依赖直觉。这三件事都是不可复核的，而不可复核的判断，在多人协作里等于没有判断。

业务影响往往被低估。它不体现在某一次故障上，而体现在整个工程节奏上：因为不知道旧代码边界，所以每次新增能力都要重新评估一遍风险；因为不知道哪些能删，所以代码只增不减；因为不知道旧的行为是什么，所以回归测试没有基准，只能靠人肉点页面。

技术表现上，可以归纳成四类具体失灵：

第一类，模块边界失灵。你知道有个 service 包，但不知道哪几个类属于同一个领域，改动一个就会牵动另一个。

第二类，调用链失灵。你知道有个 Controller，但不知道它经过几层到数据库，中间有没有缓存、有没有异步、有没有拦截器改过参数。

第三类，配置失灵。你知道有 application.yml，但不知道哪些配置项是启动必需、哪些是可选项、哪些是连到外部服务的硬绑定。

第四类，复用判定失灵。最典型的是把“看着像网关核心”的代码当宝贝，实际它只是 Demo 里的一段演示逻辑。

那什么算完成？我给自己定了四条可验证的标准，缺一条都不算逆袭完成：

一是能画出模块树，且每个模块能说清职责一句话；二是能指出唯一启动入口，并说清它加载了哪些配置；三是能给出接口清单与至少一条端到端调用链，从 HTTP 入口到持久化落地；四是能交付一张复用矩阵，每一行都有“为什么这么判”的理由，且理由指向具体文件与行号。

> 旧案靠印象
> 新需步步紧
> 说不清已有
> 改不动未来

# 03、原理

这一章只需要理解一个原理：逆向的本质不是“通读代码”，而是“建立可验证的映射关系”。

通读的产物是记忆，记忆会衰减、会失真、无法复核。映射的产物是判断，判断可以写成表格，表格可以被第二个人拿证据推翻或确认。两者的差别，在单人小项目里看不出来，在多人长期演进里是生死线。

反直觉判断：你读代码读得越顺，结论反而越不可靠。因为顺畅感通常来自“这段代码写得很像我以为的样子”，而不是“我已经验证过它的行为”。越熟悉的写法越容易让人跳过验证，把猜测当事实。

第二个反直觉判断：Demo 的“完整度”和它的“可复用度”不成正比。一份功能齐全、页面漂亮、接口一大堆的 Demo，很可能恰恰最难复用——因为它的每一层都耦合了演示逻辑，剥不干净。反倒是那些看起来简陋、只有一两个接口的骨架，复用成本最低。

基于这个原理，复用判定必须落到二维上，而不是一维的“好/坏”。第一维是改动成本：直接搬、改个名搬、拆开重构再搬。第二维是归属边界：它是属于网关核心、属于管理面、属于演示壳子，还是根本不该存在于这个项目里。

把这两维展开，就得到五个格子，也就是后面要反复用的复用矩阵：直接复用、改名复用、重构复用、废弃、新增。注意这五格里的“废弃”和“新增”是同等重要的产出——能明确说出“这段不该留”，比说“这段能留”更有价值，因为它直接减少了后面每一章的负担。

还有一个容易被忽略的点：逆向的边界必须显式声明。逆向不负责判断“这个设计好不好”，也不负责“现在要不要优化”。它只回答“现在是什么”。一旦在逆向阶段掺入改进冲动，As-Is 文档就变成了半张 To-Be 草图，两头都不成立。

> 逆向非读书
> 判断需可验
> 一图一线索
> 一证一结论

# 04、架构

```text
[输入] open-api.zip（只读，全程不改一行源码）
    |
    v
[模块] 隔离解压区 → 指纹冻结 → 静态扫描器 → 人工复核
    |
    v
[数据/状态] zip.sha256 / 模块树 / 根包名 / 接口清单 / ER / 页面路由
    |
    v
[处理] 调用链还原 → 复用矩阵五格判定 → 缺口与风险登记
    |
    v
[输出] docs/reverse/as-is.md + 类图 + 时序图 + 风险清单
```

这套流程的边界很清楚：它只做只读扫描与人工复核，不产生任何对源码的修改。解压落在独立的隔离目录里，不覆盖当前工作区，也不写入 Maven 本地仓库以外的任何位置。扫描器只负责“找出候选”，判定权永远在人手里。

收益有三层。第一层是可复核：每个结论都能指回一个文件、一段配置，别人可以逐条反驳。第二层是可回归：因为冻结了压缩包哈希和一条“原样能跑通”的路径，后面任何一次改动出问题，都能立刻判断是新引入还是旧有。第三层是省事：复用矩阵一旦定下来，后面每一章动工前都不用重新做一遍边界判断，直接查表。

代价同样要说清楚。最直接的代价是时间——本来今天就能开始改包名，现在要花半天到一天做扫描和复核。其次是覆盖面：静态扫描只能找到“写了什么”，找不到“为什么这么写”，更找不到那些靠运行时才能暴露的隐式契约，比如某个字段为空时的默认行为、某个异常被全局处理器吞掉的路径。这些必须靠启动后实际打接口来补。

适用条件也要明确。如果 Demo 只有三五个类、一屏就能看完，这套流程是过度工程，直接读更快。如果 Demo 有几十个类、多层模块、前端后端加 SQL，那么今天投入的扫描成本，会在后面每一次增量改动里被摊薄。规模越大，收益越高。

> 输入先归一
> 模块各守边
> 状态留证据
> 输出可回放

# 05、实战一次

环境与版本基线：JDK 17、Maven 3.9、Spring Boot 3.x（具体版本以解压后 pom.xml 与实际编译结果为准，不同 Demo 版本可能有差异，需按当前官方文档核验）。以下命令与目录名都以你手上的 open-api.zip 实际结构为准，本文不预设它一定包含某个具体模块。

第一步，先建隔离目录，绝不原地解压。这一步的意义不是洁癖，是为了让后面所有操作都能一键重来。

第二步，把扫描脚本写成文件，而不是敲在终端里。脚本是可复现的，终端历史不是。

```bash
#!/usr/bin/env bash
# docs/reverse/scan.sh —— 只读扫描，不改任何源码
set -euo pipefail

ZIP=${1:-open-api.zip}
OUT=${2:-docs/reverse}
WORK=.reverse-work

mkdir -p "$OUT"
rm -rf "$WORK"
unzip -q "$ZIP" -d "$WORK"

# 1. 冻结压缩包指纹：这是 0 号基线的锚点
sha256sum "$ZIP" > "$OUT/zip.sha256"

# 2. 定位真实项目根（zip 常常多套一层目录）
ROOT=$(dirname "$(find "$WORK" \( -name pom.xml -o -name build.gradle -o -name build.gradle.kts \) -print -quit)")
ROOTABS=$(cd "$ROOT" && pwd)
echo "$ROOTABS" > "$OUT/root.txt"

# 3. 根包名与包分布
if [ -d "$ROOTABS/src" ]; then
  grep -rhoE '^package[[:space:]]+[a-zA-Z0-9_.]+' "$ROOTABS/src" \
    | awk '{print $2}' | sort | uniq -c | sort -rn > "$OUT/packages.txt"
fi

# 4. 接口清单（Controller 注解全落盘，人工再筛）
if [ -d "$ROOTABS/src" ]; then
  grep -rn --include='*.java' \
    -E '@(RestController|Controller|RequestMapping|GetMapping|PostMapping|PutMapping|DeleteMapping)' \
    "$ROOTABS/src" > "$OUT/endpoints.raw.txt"
fi

# 5. 外部依赖（Spring Boot 项目走 Maven 依赖树更准）
if [ -f "$ROOTABS/pom.xml" ]; then
  (cd "$ROOTABS" && mvn -q dependency:tree -DoutputFile="$OUT/dependency-tree.txt" -DappendOutput=false)
fi

# 6. 配置文件、SQL、容器化资产清单
find "$ROOTABS" \( -name 'application*.y*ml' -o -name 'application*.properties' \
  -o -name '*.sql' -o -name 'Dockerfile*' -o -name 'docker-compose*.y*ml' \) \
  | sed "s|$ROOTABS/||" > "$OUT/assets.txt"

echo "== scan done =="
```

执行：

```bash
chmod +x docs/reverse/scan.sh
./docs/reverse/scan.sh open-api.zip docs/reverse
```

示例输出（未在当前环境实测，以下为预期结果）：

```text
== scan done ==
$ cat docs/reverse/root.txt
/repo/.reverse-work/open-api
$ cat docs/reverse/zip.sha256
9f2c...  open-api.zip
$ wc -l docs/reverse/packages.txt docs/reverse/endpoints.raw.txt docs/reverse/assets.txt
  18 docs/reverse/packages.txt
  47 docs/reverse/endpoints.raw.txt
   9 docs/reverse/assets.txt
```

第三步，先原样编译并启动。这一步是整个逆向里最重要的动作：它给出“旧代码在什么条件下能跑”的事实。跑不起来，说明逆向还没完成，不是项目坏了。

```bash
cd "$(cat docs/reverse/root.txt)"
./mvnw -q -DskipTests clean package || mvn -q -DskipTests clean package
ls -lh target/*.jar
```

启动时把端口显式指定，避免和本机已有服务冲突：

```bash
java -jar target/*.jar --server.port=18080 --spring.profiles.active=dev
```

第四步，跑接口与页面，把“能跑”变成证据。不要只点一个接口就收工，至少覆盖三类：一个只读查询、一个写操作、一个前端页面路由。

```bash
# 探活
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/actuator/health

# 挑一个只读接口（路径以 endpoints.raw.txt 实际结果为准）
curl -s http://localhost:18080/api/xxx/list | head -c 400

# 页面路由
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/
```

示例输出（未在当前环境实测，以下为预期结果）：

```text
200
{"code":0,"data":[...],"msg":"ok"}
200
```

第五步，把扫描结果与人工复核合成 As-Is 文档。文档结构固定，不自由发挥：模块树、启动入口、接口清单、调用链、ER、页面路由、外部依赖、复用矩阵、风险清单。每一项都要能指回文件路径。

第六步，冻结基线。冻结动作就三件事：记录 zip 哈希、记录可运行命令、打 Git 分支。

```bash
git checkout -b chapter/01-reverse-demo
cp docs/reverse/zip.sha256 docs/reverse/root.txt docs/reverse/endpoints.raw.txt \
   docs/reverse/ 2>/dev/null || true
git add docs/reverse
git commit -m "docs(ch01): reverse engineer open-api demo baseline"
```

到这里，V1 完成：基线冻结，且能原样跑通。但它只留下一个问题——这套扫描是我手敲的，换个人、换台机器，跑出来的东西可能不一样。这就是下一章要解决的遗留问题。

> 一解看全貌
> 一跑证可行
> 一冻结基线
> 一表定复用

# 06、排查

逆向阶段最容易踩的坑，都在“原样跑起来”这一步暴露。以下三条来自实际操作顺序中的典型路径。

第一条诊断链。现象：`mvn clean package` 直接失败，报依赖无法解析或父 POM 找不到。怀疑：本地 Maven 仓库损坏，或者网络问题。检查：先看报错里那个坐标是不是公共仓库能查到的，再看 pom.xml 里有没有显式 `repositories` 与 `distributionManagement` 配置，同时看本机 `~/.m2/settings.xml` 有没有 mirror 覆盖。证据：pom.xml 里出现了一个指向内网地址的仓库声明，而当前环境不通内网。根因：这不是代码问题，是 Demo 作者的环境硬绑定被一起打包进来了。修复：不改源码，只在本地 settings.xml 里加镜像把该仓库指向可访问的公共源；如果依赖本身是私有的，就把这一条登记进风险清单，标记为“该能力在换骨阶段必须替换”。注意，修复动作落在本地环境配置，不落在仓库里，这样 0 号基线依然干净。

第二条诊断链。现象：编译成功，`java -jar` 启动报错，日志里出现数据源初始化失败或连接拒绝。怀疑：Spring Boot 版本和 JDK 不匹配。检查：先在启动日志开头确认 JDK 版本与 Spring Boot 版本，再看能不能找到数据源相关配置项，最后确认本机有没有对应数据库实例在监听。证据：日志里的 JDBC URL 指向一个本地地址加一个具体库名，而本机该端口无人监听。根因：Demo 默认连一个已存在的库，压缩包里没有可执行的建库建表脚本，或者脚本存在但没有被自动执行。修复：手动建库、执行 assets.txt 里列出的 SQL 文件、必要时覆盖 `spring.datasource.*` 启动参数。这一步必须在 as-is.md 里写清楚，因为“Demo 需要预置数据库”是后续所有环境搭建的前置条件。

第三条诊断链，也是这一章最有价值的一条。现象：启动成功，页面能打开，但按 LLM Gateway 的直觉去请求 `/v1/chat/completions`，返回 404。怀疑：OpenAI 兼容层被某个拦截器挡住了，或者路由前缀需要额外配置。检查：在 `endpoints.raw.txt` 里检索 `chat`、`completions`、`/v1` 关键字，同时看全局的 `server.servlet.context-path` 配置。证据：整个工程里根本不存在这个路径的映射，所有接口都在管理面前缀下。根因：这份 Demo 是一个管理端应用，不是协议网关；它管的是配置和资源，不管的是模型请求转发。修复：本章不做任何代码改动，把这条“协议入口完全缺失”作为最重要的缺口，登记进风险清单，交给后面的协议与路由章节。

**错误尝试：** 我一度想先把根包名全局替换掉，理由是“反正迟早要改，改完看着顺眼，读代码更有代入感”。这个做法是错的，而且错得很隐蔽。第一，全局替换会让 Git 的 diff 变成整仓库级别的噪音，任何后续的逐行对照都失去参照；第二，替换过程中会顺带改掉配置里的扫描路径、反射用的类名字符串、MyBatis 的 type-aliases 包名，这些地方编译器不报错，但运行期会静默失效，于是你拿到的“能跑”其实是另一种意义上的不能跑；第三，也是最致命的——一旦替换完成，你就永远失去了“原样能跑通”这条参照线，后面任何一个故障，你都无法区分是旧有问题还是自己改坏的。改名必须发生在基线冻结之后，顺序不能颠倒。

> 现象非根因
> 怀疑须落地
> 证据在日志
> 修复在源头

# 07、优化

第 06 章暴露的根因是：扫描过程依赖手工命令，且环境依赖没有前置声明。于是 V1 的“可回归”只回归了一半——代码基线冻结了，环境基线没有。

修改一：把环境前置条件显式写入文档顶部。原因：三次诊断里有两次的根因都是环境缺失，而不是代码缺陷。如果环境要求不写清楚，下一个人会重新踩一遍。新行为：as-is.md 的第一节不是模块树，而是“运行前置条件”清单，包含 JDK 版本、构建工具版本、必需的外部服务及其端口、必需执行的 SQL 脚本路径。验证方式：找一个没参与逆向的人，只给他 zip 和这份文档，看他能否在首次尝试内启动成功。

修改二：把扫描脚本的候选结果转成“人工确认表”，而不是直接当结论。原因：`endpoints.raw.txt` 是机器筛出来的候选，里面会混入被注释掉的映射、测试类里的映射、以及只在特定 profile 生效的映射。直接把原始输出当接口清单，等于把噪音当事实。新行为：每个候选后面跟一列“确认/否决/待验证”和确认人，被否决的要写一句理由。验证方式：随机抽十条候选，让另一个人独立复核，看判定是否一致。

修改三：复用矩阵升格为独立文件，且每一行必须带证据列。原因：复用判定是最容易被主观化的一环，而它恰恰是后面每一章都要查询的东西。新行为：矩阵表头固定为“对象、所在路径、判定、理由、证据（文件:行号）、生效章节”。验证方式：随便挑一行，看能否仅凭证据列在三十秒内定位到源码。

修改四：把“缺口清单”和“风险清单”分开。原因：V1 里我把“没有 OpenAI 兼容入口”既当缺口又当风险，混在一起后，优先级无法判断。缺口是“必须补的能力”，风险是“可能出问题的地方”，两者的处理节奏完全不同。新行为：缺口清单按能力域归类并给出建议章节，风险清单按严重度排序并给出触发条件。

经过这四处修改，V2 的产物从“一份文档”变成了“一套可被他人复核的基线包”：脚本可重跑，结论可证伪，环境可复现，缺口有归属。

> 一次靠手感
> 二次靠脚本
> 手感会漂移
> 脚本不会忘

# 08、演进

```text
[同一份 open-api.zip]
    |
    +--[V1] 人工通读 + 凭印象判定复用 / 代价：结论不可复核，环境不可复现
    |
    +--[V2] 脚本化扫描 + 环境前置声明 + 证据化复用矩阵 / 代价：先投入半天建流程
    |
[Trade-off]
得到可重复的基线与可证伪的判断；失去“立刻开改”的爽感；
边界：Demo 规模越大收益越明显，三五页代码的 Demo 用人眼更快
```

正确性上，V1 和 V2 都能得出“有哪些模块”这类结论，差别在结论的可复核程度。V1 的结论依赖讲述者的记忆，换个时间点可能不一样；V2 的结论指向文件与行号，可以被逐条反驳。在一个人做的小项目里这个差别为零，在需要交接的项目里这个差别就是全部。

稳定性上，V2 明显更强。V1 的扫描方式不可重跑，第二次执行时命令可能已经忘了；V2 的脚本进仓库，任何人任何机器都能跑出同一份候选集。这一点在后面做回归时会非常关键——当代码改动之后，你可以重跑扫描，直接对比接口清单的差异。

复杂度上，V2 引入了额外资产：一个脚本、一份环境前置清单、一张带证据列的矩阵表。这些都是维护成本。如果项目推进到一半决定放弃这套流程，这些资产会变成负担。所以适用条件必须写死在文档里，而不是靠人记。

成本上，V2 的首次投入更高，主要体现在建脚本和统一文档结构上。但逆向这件事的边际成本是递减的：第一次扫描最贵，之后每次重扫几乎免费。

适用范围上，规模是决定性的。文件数十个以内，人眼加 IDE 全局搜索足够；数百个以上，脚本收益压倒性地高。本文描述的这套方法，在中等规模工程上收益最明显。

遗留问题有三个，都留给后续：一是包名迁移尚未执行，它是下一步最高优先级；二是环境依赖还没有容器化，目前仍靠人工准备；三是协议入口完全缺失，这是整个项目最核心的缺口，但必须先完成换骨才能安全地补。

> 同包不同命
> 改与不改间
> 得一份清楚
> 失一份速度

# 09、洞见

## 9.1 基线的第一属性是可回归，不是能用

在这件事上我的判断被改过一次。一开始我认为“能跑起来”就是基线，所以急着让它启动。后来发现，能跑起来只说明此刻你的机器上它是活的；一旦你改了任何一行，你就再也回不到“它本来的样子”。

反直觉判断：真正意义上的“跑通”，成本恰恰在于你必须先忍住不去修它。哪怕它有个明显的 bug、有个丑陋的写法，只要不阻塞启动，就原样放着。因为修掉它的那一刻，你就失去了判断“这个行为是旧有还是新引入”的能力。基线的价值不在于它有多好，而在于它是一个不动点。

## 9.2 复用判定必须在改代码之前完成

复用矩阵最大的风险是边改边判。一旦你开始改包名或者调整结构，你对“这段代码能不能直接用”的判断就污染了——你看到的已经是改过之后的版本，而不是它原本的样子。

更隐蔽的是心理层面的污染：人会不自觉地为自己已经做的改动辩护，于是原本该废弃的代码，会被判定成“重构后可用”，只是为了不浪费已经投入的力气。把判定前置，是在保护判断的独立性。

## 9.3 越像“核心”的代码，越应该优先怀疑

反直觉判断：在逆向一份 Demo 时，最危险的不是那些看不懂的代码，而是那些一眼就看懂、且看起来正好是你需要的那部分。它让你产生“这个已经有了，我可以直接用”的错觉，而这个错觉往往要等到集成的最后阶段才被证伪。

本文里最典型的一例就是协议入口：直觉上，一个 LLM Gateway 的 Demo 应该有 OpenAI 兼容的请求入口。实际扫描结果是它根本没有，它是个管理端应用。如果我在第 01 章就默认“这个入口肯定有”，后面所有关于协议的设计都会建立在错误前提上。凡是“理所当然应该有”的东西，都要去清单里查一次存在性。

## 9.4 逆向的产物不是文档，是回答问题的能力

文档只是证据的载体。真正的产物是：面对“已有什么、请求怎么走、哪些能复用”这三个问题时，能给出有证据支撑、且可以被别人推翻的答案。

这条判断决定了文档该怎么写。如果目标是“产出一份好看的文档”，你会倾向于把不确定的地方写成模糊的概括；如果目标是“回答问题时能顶上”，你会倾向于把每个结论都钉在一个文件行号上，哪怕它看起来琐碎。

> 能跑不算基
> 能再来才算
> 越像核心者
> 越该先怀疑

# 10、系统落地

原来有什么：仓库根目录一个 open-api.zip，加一个“不重新造骨架”的口头约定。这份压缩包对团队而言是一个黑盒——能打开，但不能回答任何关于边界和复用的问题。

本篇新增了什么：一份 `docs/reverse/as-is.md`，包含运行前置条件、模块树、启动入口、接口清单、调用链、ER、页面路由、外部依赖；一张带证据列的复用矩阵；一份缺口清单与风险清单；一个可重复执行的扫描脚本；一个冻结的压缩包哈希；以及一个独立分支 `chapter/01-reverse-demo` 和一次提交。

现在能做什么：能准确地回答“现有 Demo 已有什么”——答案指向具体文件；能回答“请求怎么走”——从 HTTP 入口到持久化的链路上每一跳都有落点；能回答“哪些代码可以复用”——每一行判定都有理由和证据。更重要的是，后面任何一次改动出问题，都能拿这次的哈希和运行记录做对照，判断是新引入还是旧有。

还缺什么：包名与项目名尚未更换，项目还叫原来的名字；环境依赖尚未容器化，换台机器仍要人工准备；协议入口完全缺失，网关的核心能力一行都没有；数据库结构虽已梳理，但迁移方案还没有；前端页面只做了路由层面的确认，接口契约还没有对齐。

下一步如何演进：先做换骨——在冻结的基线上替换包名与项目名，同时把配置里的扫描路径、类型别名、反射字符串一并处理干净，并保证替换后接口清单与基线完全一致；然后补齐环境容器化，让新人一条命令就能起环境；最后才开始补协议入口。顺序不能乱，因为协议层的设计要建立在明确的模块边界之上，而模块边界正是这一章确定下来的。

> 原来只有包
> 如今有了图
> 缺的还很多
> 路要先走稳

# 11、小结

```text
Q1 → 能，前提是把“复用”定义成有证据的边界判定，而不是主观印象
Q2 → 先原样跑通并冻结基线，再谈改名；顺序颠倒会永久污染参照线
Q3 → 产物不是文档本身，是“能准确回答三个问题”的能力，文档只是载体
状态 → 0 号基线已冻结且可原样跑通，可以进入换包名与骨架迁移
```

这一章没有增加任何一行业务代码，但它决定了后面所有章节的返工率。若把整个项目看作一条长链，这一章是链子的第一环：它不承重，但它决定了后面每一环挂在哪里。

最需要记住的一句话是：在改之前，先拥有一个能回去的地方。

> 一问已有何
> 二问如何走
> 三问可复用
> 三答定基线

# 12、作业

## 12.1 理解题：为什么说“能跑起来”不等于“有了基线”？

参考答案：能跑起来只证明当前环境下代码是活的，它是一个时间点上的状态；基线要求的是可回归，即任何人都能在任何时间回到同一个起点。要做到可回归，至少需要三样东西：一个不变的输入（压缩包哈希）、一条可重复的执行路径（构建与启动命令）、一份可复核的结论（带证据的 As-Is 文档）。缺少任何一样，跑通都只是偶然事件，不是基线。

## 12.2 实战题：给你一份没有任何文档的 Spring Boot 工程压缩包，如何在两小时内产出一份可被别人复核的接口清单？

参考答案：分四步。第一步，隔离解压并记录哈希，保证后续操作可重来。第二步，用脚本按注解扫出候选映射，落盘成 `endpoints.raw.txt`，注意区分 `@RestController` 与 `@Controller`，并记录类级 `@RequestMapping` 前缀。第三步，人工逐条确认，排除被注释的、测试类里的、以及只在特定 profile 生效的映射，每条标注确认人与理由。第四步，挑其中一条实际打一次请求，用响应验证清单的真实性——没被验证过的清单只是候选集。最后把清单、脚本、验证记录一起提交，别人才可能复核。

## 12.3 排障题：启动成功、页面能打开，但按预期路径请求网关接口返回 404，你如何定位？

参考答案：按三层排查。第一层查路由是否存在：在接口清单里检索目标路径关键词，如果没有匹配，说明是能力缺失而不是配置错误，直接登记进缺口清单。第二层查前缀：确认 `server.servlet.context-path` 配置和类级 `@RequestMapping` 前缀，很多时候路径是对的但前缀拼错了。第三层查拦截：确认有没有全局拦截器或安全框架在路径匹配前就返回了 404。要特别注意区分“404 因为找不到”和“404 被伪装成找不到”，看响应体是否带框架特征。定位到根因后，如果是能力缺失，本章不改代码，只登记。

## 12.4 架构判断题：复用矩阵里，“废弃”这一格为什么和“新增”同等重要？

参考答案：因为它们都直接减少后续工作量，只是方向不同。“新增”决定了你要写什么，“废弃”决定了你不用维护什么。一份只标“能复用”的矩阵，等于把旧代码的所有历史包袱原样背进新项目；而明确标出“这段该删”的行，等于提前把复杂度砍掉。更关键的是，废弃判定需要证据和勇气——它往往是逆向中最容易被跳过的一格，因为删东西比加东西更容易引起争议，所以必须在基线阶段就把理由写清楚。

> 手工读一遍
> 脚本跑一遍
> 脚本胜手工
> 可重复为真

# 13、思考

回到开篇那个冲突：动手的冲动和读懂的耐心，天然对立。这一章的处理方式是——把冲动往后压一段时间，用一次冻结换一份可回归。

这个判断可以复用。任何一个“在既有系统上增量演进”的任务，都会遇到同一道题：什么时候可以开始改。常见的错误答案是“等我看明白了”，因为“看明白”是一个没有验收标准的状态，它会无限延长，也会在某一天被一句“先做起来再说”草率终结。正确答案是“等我拥有一个能回去的地方”，它是可验证的——你能否用一条命令回到起点，能否用一份文档说清现状，能否用一张表回答“哪些能用”。

还有一层更隐蔽的判断：逆向的边界必须被显式声明。逆向只回答“现在是什么”，不回答“应该是什么”。一旦在逆向阶段掺入改良冲动，As-Is 就会变成半张 To-Be 草图，最后两头都不成立——既描述不清现状，也指导不了未来。把这两件事分开做，看起来慢，实际上是唯一不会返工的走法。

不重造骨架，先摸清底牌，这句话的重点不在“不重造”，而在“先摸清”。因为底牌不清的时候，重造和改造的代价是一样的，甚至改造更贵——你会在别人的设计里，用别人的约束，去实现自己都没想清楚的需求。

> 不重造骨架
> 先摸清底牌
> 逆向立根基
> 增量才有凭
