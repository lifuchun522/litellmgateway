# 遁一境·不灭经：RuntimeConfigSnapshot 持久化与重启恢复


我是老李，最近在把 litellmgateway/open-api.zip Demo 改造成 Java 轻量级 LLM Gateway。前面第12境已经把 RPM/TPM/Budget 的硬约束压到治理层，但配置本体还散落在启动参数、YAML 和内存缓存里。

任务是让运行配置从“进程内状态”变成“可发布、可回滚、可恢复的持久化快照”。第13境对应遁一境·不灭经：肉身元神不灭，映射到工程里，就是配置不因重启、发布、实例切换而丢失或漂移。

如果配置只在 Caffeine 里，发布后需要每个实例重新加载吗？  
如果 Published 快照已经落库，数据面应该读 DB 还是读缓存？  
如果为了多实例强一致直接上 Redis，单机 MVP 的复杂度代价谁来承担？  

# 01、故事

周五晚上，控制台里改的是模型路由：把默认流量从 A 供应商切到 B 供应商，并给降级策略加 800ms 超时。当前方案很直接：Admin API 更新 Caffeine，数据面从 Caffeine 读。数据库里没有配置版本，也没有 Published 快照。

任务是让每次发布产生一个 `configVersion`，并把 `PUBLISHED` 快照落库。变化来自运营要求：重启后不能回默认，灰度期间要能看版本，出错要能回滚。冲突也在这里：内存缓存很快，但它不是真相源；DB 稳，但如果没有发布边界，读侧照样不知道读哪一份。

一次发布后服务重启，网关回到 YAML 默认路由，运营以为已经生效。日志里只有缓存命中，没有版本号；数据库里连快照表都没有。故事到这里，问题已经不是“要不要持久化”，而是“发布出来的配置如何成为唯一运行真相”。

> 内存一时快
> 重启万事空
> 若留发布印
> 方能复旧踪

# 02、问题

旧方案失效：配置在 YAML + Caffeine，发布没有版本，DB 没有快照。业务影响是重启后策略丢失，限流、预算和路由漂移，排障不可复现。技术表现是同一请求在重启前后路由不同，多实例缓存不一致，控制台也无法展示发布时间和刷新状态。

可验证的完成标准需要写成可检查项：应用重启后，所有运行配置自动恢复；`GET /admin/runtime-config/current` 返回唯一 `PUBLISHED` 的 `configVersion` 和 `checksum`；数据面只读这个快照，不读 `DRAFT`；控制台能看到配置版本、发布时间、刷新状态。

> 旧策靠内存
> 新求可复原
> 先立发布界
> 再谈多节点

# 03、原理

这一境只讲一个原理：配置持久化的核心不是“把 JSON 写进 DB”，而是“定义唯一 Published 版本，并让数据面只读这个不可变快照”。Draft 可以编辑，Published 才能运行；configVersion 用来标识快照，checksum 用来验证内容未变。

反直觉判断：把配置写进数据库并不等于重启可恢复，只有当存在唯一 Published 版本，并且启动时按发布时间选出它，恢复才成立。Caffeine 在这里不是真相源，而是读缓存；它缓存的是 `RuntimeConfigSnapshot`，不是散装字段。发布成功后，缓存通过原子替换指向新快照。

Flyway 负责 schema 演进，先增量加表，不重写 Demo 现有持久化层。Redis 只做 P1 集群扩展：单机 MVP 先让 DB + Caffeine 闭环，避免把内存态外移却不解决发布语义。

> 真相不在快
> 在可唯一寻
> 缓存只读影
> 不替发布心

# 04、架构

```text
[输入] Admin 发布请求 / 启动恢复
    |
    v
[模块] ConfigAdminService + RuntimeConfigSnapshotStore
    |
    v
[数据/状态] runtime_config_snapshot，status=PUBLISHED
    |
    v
[处理] 事务提交后原子替换 Caffeine 快照
    |
    v
[输出] 数据面只读 RuntimeConfigSnapshot
```

边界很明确：MVP 是单机持久化与本地缓存，不承诺多实例强一致；DB 存 Draft/Published 快照，数据面不直接查 Draft；Caffeine 只保存当前 Published 引用；Redis 留给 P1 集群扩展。

收益是重启可恢复、发布有版本、缓存读稳定。代价是多了一张表、一次发布事务和启动加载逻辑；如果多实例同时发布，需要额外约束，否则会出现版本竞争。适用条件是单机或少量实例、以配置发布为低频操作、可接受短暂刷新延迟。

> 一层存版本
> 一层做读影
> 边界先划清
> 扩展再上云

环境按 Java 17、Spring Boot 3.x、Flyway、Caffeine 组合编写；具体版本需按当前官方文档核验。以下为最小 V1，未在当前环境实测，以下为预期结果。

Flyway 迁移：

```sql
CREATE TABLE runtime_config_snapshot (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  config_version VARCHAR(64) NOT NULL,
  status VARCHAR(16) NOT NULL,
  payload_json TEXT NOT NULL,
  checksum VARCHAR(64) NOT NULL,
  published_at TIMESTAMP NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_config_version (config_version)
);
```

核心服务：

```java
@Service
public class RuntimeConfigService {
  private final RuntimeConfigSnapshotRepository repository;
  private final AtomicReference<RuntimeConfigSnapshot> current = new AtomicReference<>();

  public RuntimeConfigService(RuntimeConfigSnapshotRepository repository) {
    this.repository = repository;
  }

  @PostConstruct
  public void loadPublished() {
    repository.findFirstByStatusOrderByPublishedAtDesc("PUBLISHED")
        .ifPresent(current::set);
  }

  public RuntimeConfigSnapshot current() {
    RuntimeConfigSnapshot snapshot = current.get();
    if (snapshot == null) {
      throw new IllegalStateException("no published runtime config");
    }
    return snapshot;
  }

  @Transactional
  public RuntimeConfigSnapshot publish(String version, String payloadJson) {
    String checksum = DigestUtils.sha256Hex(payloadJson);
    RuntimeConfigSnapshot snapshot = new RuntimeConfigSnapshot();
    snapshot.setConfigVersion(version);
    snapshot.setStatus("PUBLISHED");
    snapshot.setPayloadJson(payloadJson);
    snapshot.setChecksum(checksum);
    snapshot.setPublishedAt(LocalDateTime.now());
    repository.save(snapshot);
    TransactionSynchronizationManager.registerSynchronization(
      new TransactionSynchronization() {
        @Override
        public void afterCommit() {
          current.set(snapshot);
        }
      });
    return snapshot;
  }
}
```

接口：

```java
@RestController
@RequestMapping("/admin/runtime-config")
public class RuntimeConfigController {
  private final RuntimeConfigService service;

  public RuntimeConfigController(RuntimeConfigService service) {
    this.service = service;
  }

  @GetMapping("/current")
  public RuntimeConfigSnapshot current() {
    return service.current();
  }

  @PostMapping("/publish")
  public RuntimeConfigSnapshot publish(@RequestBody PublishRequest request) {
    return service.publish(request.configVersion(), request.payloadJson());
  }
}
```

启动后请求：

```bash
curl -X POST http://localhost:8080/admin/runtime-config/publish -H 'Content-Type: application/json' -d @publish-request.json
```

示例输出：

```bash
configVersion=v13-001 status=PUBLISHED checksum=示例值
```

验证方式：重启应用后再次请求 `GET /admin/runtime-config/current`，预期仍返回同一 `configVersion` 与 `checksum`；数据面只调用 `RuntimeConfigService.current()`。

> 先落一张表
> 再缓一份真
> 重启看一眼
> 版本仍同身

# 06、排查

现象一：发布后新实例正常，旧实例仍走旧路由。怀疑缓存未刷新。检查 Admin 返回的 DB `PUBLISHED` 版本，以及数据面 `current()` 的版本。证据是 DB 已出现新版本，但旧实例内存引用仍是旧对象。根因是发布只写 DB，没有在事务提交后替换本地 Caffeine 快照。修复是在 `afterCommit()` 中 `current.set(snapshot)`，或用发布事件触发本地替换。

现象二：应用重启后配置回默认。怀疑 DB 没保存。检查 Flyway 表和 status。证据是 `runtime_config_snapshot` 里只有 `DRAFT`，没有 `PUBLISHED`，启动逻辑也没加载最新 Published。根因是发布只更新草稿，没有形成 Published 语义。修复是发布时生成 `PUBLISHED` 快照，启动时按 `published_at` 倒序加载第一条。

**错误尝试：** 为了多实例一致，直接把 Caffeine 换成 Redis，并让单机 MVP 强依赖 Redis。为什么错误：根因是缺少 DB Published 版本和原子发布边界，不是缺少一个共享缓存；Redis 只是把内存态外移，没有解决版本选择、回滚和启动恢复。更糟的是，单机 MVP 多了部署、网络和序列化故障面。

> 旧版仍在跑
> 新库已落章
> 先证发布界
> 再修替换枪

# 07、优化

根据第 06 章证据，V2 的根因修正是：发布必须产生唯一 Published 快照，缓存只缓存该快照，启动必须从 DB 恢复。修改包括 Flyway 增量表、Draft/Published 状态、configVersion、Caffeine 原子替换、控制台展示版本与发布时间。

原因是数据面需要稳定读，而不是每次请求查库或拼装配置。新行为是：`publish` 事务提交成功后，`AtomicReference<RuntimeConfigSnapshot>` 指向新快照；`current()` 只读引用；重启后 `@PostConstruct` 从 DB 加载最新 Published。验证方式是发布 v2 后重启，再查询 current，预期版本与 checksum 不变；同时确认 Draft 不进入数据面。以下为示例输出，未做生产压测。

```bash
publish -> v13-002
restart -> current=v13-002
checksum -> same
```

> 根因一落定
> 改动不飘零
> 只读已发布
> 草稿不通行

# 08、演进

```text
[同一输入]
    |
    +--[V1] 写 Caffeine / 重启丢失 / 多实例漂移
    |
    +--[V2] Flyway 增量表 + Published 快照 + Caffeine 原子替换
    |
[Trade-off]
得到重启恢复与发布边界 / 失去单点即全部真相的简单幻觉 / 适用单机 MVP，P1 再上 Redis
```

正确性上，V2 把运行真相从进程内状态移到 DB 的 Published 快照，重启可恢复。稳定性上，数据面只读不可变引用，避免发布中读到半成品。复杂度上，多了一张表、迁移脚本和启动加载。成本上，低频发布可接受，单机无需 Redis。适用范围是单机或少量实例；遗留问题是多实例广播、发布权限和更细审计。

> 旧路快而散
> 新路慢却明
> 取舍在边界
> 不失为真经

# 09、洞见

## 9.1 配置持久化是发布语义，不是 CRUD

反直觉判断：把配置写进 DB 并不等于可恢复，只有存在唯一 Published 版本才可恢复。CRUD 只关心行存在，发布语义关心哪一行能进入数据面。这个判断解释了为什么 Draft 必须与 Published 分离。

## 9.2 缓存的目标是稳定读，不是追新

反直觉判断：数据面缓存越追求实时，发布原子性越难保证；只读不可变快照反而更稳。Caffeine 在这里不是加速查库，而是给数据面一个稳定引用。

## 9.3 Redis 是扩展层，不是单机 MVP 的止血带

单机 MVP 的痛点是重启恢复和发布边界，不是跨实例共享。先把 DB + Caffeine 闭环，Redis 留到 P1 集群扩展，避免用复杂度掩盖根因。

## 9.4 重启恢复是验收，不是附属功能

如果验收只看发布接口返回成功，重启后回默认就会被漏掉。必须把“重启后所有运行配置自动恢复”作为主验收项，配置持久化才算进入系统能力。

> 发布先定性
> 缓存只读影
> 扩展留后手
> 重启见真经

# 10、系统落地

原来有什么：Demo 现有持久化层、YAML 配置和进程内缓存。本篇新增什么：Flyway 增量迁移、`runtime_config_snapshot` 表、Draft/Published 状态、configVersion、Caffeine 当前快照、发布后原子替换、启动恢复。现在能做什么：发布配置、查看版本、重启恢复、数据面只读 Published。还缺什么：多实例广播、Redis P1 共享、发布审批与更细审计。下一步如何演进：在不破坏 Published 只读语义的前提下，把快照分发扩展到集群。

# 12、作业

## 12.1 理解题：为什么 Draft/Published 比单 status 字段更清晰？

参考答案：单 status 容易把编辑态和运行态混在一起。Draft/Published 明确数据面只读 Published，发布、回滚和审计都围绕唯一运行快照展开。

## 12.2 实战题：写一个 Flyway 迁移和启动加载

参考答案：迁移创建 `runtime_config_snapshot`，包含 config_version、status、payload_json、checksum、published_at。启动时 `@PostConstruct` 查询最新 Published 并放入 `AtomicReference`。

## 12.3 排障题：发布后新实例正常，旧实例仍走旧配置，怎么查？

参考答案：先查 DB 是否有新 Published 版本，再查旧实例 current 引用是否更新。如果 DB 新、内存旧，定位为缓存替换未发生；修复 afterCommit 原子替换。

## 12.4 架构判断题：单机 MVP 是否应强依赖 Redis？

参考答案：不应。单机 MVP 的核心是 DB Published 快照 + Caffeine 稳定读，Redis 只做 P1 集群扩展，避免把根因误判为共享缓存缺失。

> 先分清草稿
> 再验替换桥
> 架构不堆料
> 单机也成招

# 13、思考

这一境的核心冲突只有一个：配置在内存里很快，但重启会归零；配置落库很稳，但如果没有 Published 语义，读侧仍不知道读哪一份。工程判断是，先立发布边界，再谈缓存和集群扩展。

不灭经映射到系统里，不是让进程永不重启，而是让重启后的运行配置有唯一可恢复来源。只要 Published 快照、版本和 checksum 在，缓存可以重建，实例可以恢复，排障可以复现。

> 一念辨边界
> 一证定根因
> 一改知取舍
> 一役见真章
