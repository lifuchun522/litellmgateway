第十三章只做一件事：复用 Demo 持久化层，增量加表，Flyway 管 schema，配置重启自动恢复。Redis 不进单机 MVP。
客户只关心改配置不重启、不丢、能回滚。页面必须一眼看到当前版本、发布时间和刷新状态，别把复杂度甩给用户。
一线最怕配置发错后没人能恢复。请把 Published 版本落库，支持回滚上一版；重启恢复必须走客户真实路径验证。
调研开源网关，APISIX、Kong 都用 DB 持久化配置，Redis 多用于集群分发。单机 MVP 用 Caffeine 加 DB 恢复，证据足够。
一期范围冻结：配置版本列表、发布时间、刷新状态、回滚上一 Published。不做 Redis 集群、审批流、多租户。重启恢复百分百算成功。
候选 A 单表 configVersion 加 status；候选 B Draft/Published 双表。我选 A，snapshot 存 Published，数据面只读，发布后原子替换 Caffeine。
发布写 DB 成功但缓存替换失败怎么办？事务先写 Published，再通过 AtomicReference 替换 Caffeine；启动时从 DB 读最新 Published 恢复。
基线：配置变更需重启，恢复靠手工。成功线：重启恢复百分百，发布生效 P95 小于一秒。停止线：连续两次恢复失败，暂停发布并回退。
配置页面标题和文档要能被搜到，关键词是 Java LLM Gateway 配置版本、运行时快照。验证指标：自然搜索进文档后注册或部署转化。
这次不投广告。单机 MVP 的 CAC 不划算，也归因不了配置恢复价值。预算留给 P1 Redis 集群验证，先用社区内容换信任。
增量复用 Demo 持久化层，只加迁移和缓存，人力不超三人天，云成本零新增。ROI 门槛：配置事故减少八成，否则不批 Redis。
配置表和审计日志必须记 operator、version、publishedAt。敏感值不能明文，引用密钥管理。发布人负责，系统给回滚路径。
拆五棒：Flyway 迁移、Repository、Caffeine 发布、页面状态、重启验收。Alex 主写，Bob 评审，Emma 验收，David 定指标，T 加三交。
听完技术和预算约束，我接受一期不做 Redis。但页面必须一句话说清当前 Published 版本和刷新状态，客户不用理解内部表。
一线标准再加一条：配置发错后，两分钟内能回滚上一 Published 版本，并且页面显示回滚结果。做不到，这个方案就不算闭环。
补充反证：有些网关把 Redis 当强依赖，导致单机部署复杂。我们的目标用户是 Java 轻量级场景，DB 恢复加 Caffeine 更匹配。
根据回滚和审计新增，范围重新冻结：Do 加回滚上一版和审计字段；Not Do 仍是 Redis 集群、审批流、多环境。验收以重启恢复为准。
最终 Trade-off：牺牲单表极简，采用 configVersion 加 status 加 snapshot JSON。换来发布原子性和重启恢复。Redis 延后 P1，不作强依赖。
实现路径：Flyway V13 建 runtime_config_snapshot，复用 Demo Repository。发布事务写 Published 后原子替换 Caffeine，启动加载最新 Published。
上线后看三个数：重启恢复成功率、发布生效延迟、回滚耗时。成功线全绿；停止线是恢复失败一次就回退版本，两次就暂停发布修缺陷。
自然增长验证：发布配置版本页面和文档，标题含 LLM Gateway 配置持久化。四周看搜索曝光和文档到仓库点击，没转化就改内容结构。
付费验证仍不投。如果以后做 P1 Redis 集群，先设 CAC 上限和转化事件，预算按周递增。现在没有归因事件，投了就是浪费。
最终预算线：开发三人天，云成本零新增，P1 Redis 预算冻结。ROI 只看配置事故下降和重启恢复率，达不到八成就不释放下一笔。
合规门槛已过：审计字段落库，敏感配置引用密钥管理，发布人责任明确。最终红线：任何配置不得绕过 Published 直接推给数据面。
Owner 清单：Alex 负责迁移和缓存，Emma 负责页面与回滚验收，David 负责指标，Bob 评审架构，我盯 T 加三交付。验收重启后全恢复。
拍板：复用 Demo 持久化层，Flyway 增量加表，只读 Published 快照，Caffeine 原子替换，重启从 DB 恢复。Redis 留到 P1。

## 摘要

第13章用 Flyway 增量加表，复用 Demo 持久化层，以 Published 快照和 Caffeine 缓存实现配置发布与重启自动恢复。
