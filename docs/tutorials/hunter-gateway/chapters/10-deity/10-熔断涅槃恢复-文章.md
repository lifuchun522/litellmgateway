# 真凰不死身：Deployment 级熔断恢复与自动重入

> 熔断不是把坏节点扔掉，而是让它在证据齐了之后回来

```text
[读者] 正在给 LLM Gateway 做多上游接入的 Java 后端
[痛点] Retry 只管单次请求，坏 Deployment 每一轮都被撞一次
[现在读] 上游一抖，路由还在往伤口上撒盐
[读完] 能让节点自动摘除、自动重入，且人工优先
```

```text
[旧方案] 失败就重试，重试到兜底模型
    |
    v
[新需求] 按 Deployment 记忆健康，坏了先摘出去
    |
    v
[冲突] 摘除容易，判活难，放回来更难
    |
    v
[后果] 要么误杀健康节点，要么把病节点反复放回
```

我是老李。上一章做完 Retry/Fallback 之后，网关确实不会再因为单个上游抖动就整体失败了，日志里也能看到请求在 Deployment 之间轮转。但轮转本身暴露了一个新问题：坏掉的那个 Deployment，每一轮都要被撞一次。

litelmgateway 的 open-api.zip Demo 里，Provider 适配层是很薄的：一个 ProviderAdapter 直接拿 HTTP client 打上游，异常往上抛，由 Pipeline 兜。这个结构在只有一两个上游时够用，一旦 Deployment 变多，失败就不再是“一次请求的失败”，而是“一个节点的失败”。

任务是给每个 Deployment 建立自己的健康与熔断状态：坏了自动摘出去，好了自动放回来，同时保留人工一票否决的权力。Resilience4j 的 CircuitBreaker 正好提供 CLOSED / OPEN / HALF_OPEN 三态机，但把它接到路由上，坑比想象中多。

上游 504 开始刷屏时，你凭什么判断这个 Deployment 是真的病入膏肓，还是恰好赶上一次网络抖动？

探测通了就能立刻把全部流量放回去吗，还是应该先放几个请求试水？

运维同学手工禁用的节点，自动恢复逻辑有没有资格把它重新打开？

# 01、故事

我在 Pipeline 里加了一段候选 Deployment 轮转逻辑：主 Deployment 抛异常，就按顺序换下一个，最后再落到兜底模型。上线第一周，感觉良好，错误率确实降了。

第二周开始，日志里出现了一种很别扭的形态：同一个 Deployment 的超时反复出现，但每个请求都会先去撞它一次，撞完再切走。Retry 把“一次请求”救活了，却把“一个节点已经坏了”这个事实完全丢掉了。

我拉了一段路由日志，下面是脱敏后的形态：

```log
[router] round=1 chosen=dep-a result=ReadTimeout(30000ms)
[router] round=2 chosen=dep-b result=OK
[router] round=1 chosen=dep-a result=ReadTimeout(30000ms)
[router] round=2 chosen=dep-b result=OK
[router] round=1 chosen=dep-a result=ReadTimeout(30000ms)
[router] round=2 chosen=dep-b result=OK
```

dep-a 每次都要吃掉一次完整的超时。任务很明确：给每个 Deployment 建立自己的健康判断和断路状态，让路由层在“发请求之前”就知道这个节点现在不该被选。

这话说起来简单，做起来有三个岔路口。判活的标准是失败率、连续失败次数，还是把慢调用也算进去？探测由谁来做，让真实流量去探，还是另起一个定时任务？探测说好了，就能立刻全量放回去吗？

这三个问题不解决，熔断做出来就是一个“偶尔把好节点也关掉”的随机数生成器。

> 超时刷满屏
> 重试不知倦
> 墙倒人人撞
> 谁记这片伤

# 02、问题

Retry 的语义是“这一次请求失败了，换一个再试”。它天然无状态：它不记得上一分钟 dep-a 已经超时过多少次，也不关心 dep-b 是不是已经连续成功了两小时。

业务上的影响是排队效应。当 dep-a 进入持续超时状态，每一个进入网关的请求都会在 dep-a 上先付一次完整的超时成本，然后再切到 dep-b 重来一遍。用户感受到的不是错误，而是“偶尔会卡很久”，这种问题比直接报错更难被投诉描述清楚。

技术上有四个具体表现：路由层没有准入判断，候选集永远是全量；失败信息只向上抛，不写回任何节点级状态；没有人工干预入口，想摘掉一个节点只能改配置重启；也没有恢复路径，即使上游已经好了，也没有机制去确认。

所以本章的完成标准必须是可验证的，而不是“感觉熔断生效了”：

```text
1. dep-a 连续失败达到阈值后，新请求不再路由到它
   —— 路由日志中 60 秒内不再出现 chosen=dep-a
2. dep-a 恢复后熔断器进入 HALF_OPEN，放行少量探测请求
   —— 探测通过则回到 CLOSED 并重新进入候选集
3. 手工 DISABLED 的 Deployment 在任何健康状态下都不进候选集
4. 健康探测产生的调用不写入熔断器滑动窗口
   —— 可用 metrics 计数对照验证
5. 上述状态均可从管理接口一次性读出
```

第 4 条最容易被忽略，但它恰恰是后面反复出问题的根源。

> 失败无记忆
> 路由无边界
> 标准先立好
> 再谈自动摘

# 03、原理

先给一个反直觉判断：熔断器不是“失败就断开”的开关，它是一台带证据窗口的状态机；真正决定系统可用性的，是 HALF_OPEN 阶段的放行额度，而不是 OPEN 阶段的失败率阈值。

阈值只决定“什么时候不再相信”，HALF_OPEN 才决定“凭什么重新相信”。前者做错了，最坏是摘得太晚；后者做错了，就是把一个还没好的节点反复塞回主链路，形成“刚恢复就被打挂、打挂之后又恢复”的振荡。

三个状态的语义分别是：CLOSED 正常放行，同时按滑动窗口统计失败与慢调用；OPEN 直接拒绝，不向上游发出任何真实请求；HALF_OPEN 放行有限数量的探测请求，判定成功则回 CLOSED，否则回 OPEN。

Resilience4j 的 CircuitBreakerConfig 里，和这件事直接相关的字段是（具体默认值以 Resilience4j 官方文档为准）：slidingWindowType 选择 COUNT_BASED 或 TIME_BASED；slidingWindowSize 定义窗口大小；minimumNumberOfCalls 决定达到多少样本之前不计算失败率，防止样本太少误判；failureRateThreshold 是失败率阈值；slowCallDurationThreshold 与 slowCallRateThreshold 把慢调用单独控制，这对 LLM 网关尤其重要，因为上游经常“不报错但极慢”；waitDurationInOpenState 决定 OPEN 保持多久；permittedNumberOfCallsInHalfOpenState 是半开探测额度；automaticTransitionFromOpenToHalfOpenEnabled 决定是否自动从 OPEN 转 HALF_OPEN。

第二个反直觉判断：健康检查成功，不等于熔断器应该 CLOSED。

两者证据来源完全不同。主动探测是低频、单点、请求很轻的，很容易被上游网关、负载均衡或 CDN 缓存掉，得到一个“假成功”。被动统计是高频、真实负载、真实参数大小的，它能反映真实容量。让探测结果直接去改熔断器状态，会出现两种污染：探测成功把失败率冲淡，导致熔断器永远不 OPEN；或者探测失败被记进窗口，让刚恢复的节点立刻又被打开。所以必须分账。

粒度也要想清楚：按 Deployment，而不是按 Provider，也不是全局。Deployment 是最小的可网络到达单元，同一个 Provider 下的不同 Deployment 可能在不同区域、不同账号、不同规格，故障并不同步。按 Provider 熔断，会造成一个区域抖动就摘掉整个供应商。

> 阈值非开关
> 窗口是证据
> 半开留额度
> 恢复方可期

# 04、架构

```text
[输入] OpenAI 兼容请求 /v1/chat/completions
    |
    v
[模块] Router：候选 Deployment 过滤（人工状态 → 健康 → 熔断准入）
    |
    v
[数据/状态] HealthStore（探测结果）、DeploymentBreaker（CLOSED/OPEN/HALF_OPEN）
    |
    v
[处理] 调用上游 → 回写成功/失败到本 Deployment 的熔断器
    |
    v
[输出] 上游响应 / 全候选被拒时触发 Fallback
```

这条链上有一个关键顺序：准入判断必须发生在“发请求之前”，而不是“收到异常之后”。这是本章最容易做错的地方，第 06 章的两条排查链都源于此。

边界要划清楚。熔断器只管“能不能发”，不管“发几次”，重试次数仍由上一章的 Retry 策略决定；健康探测只写 HealthStore，不写熔断器窗口；人工状态 ENABLED / DISABLED 优先级最高，覆盖一切自动判断。

收益是明确的：坏节点被摘除后，请求不再为它付超时成本；恢复路径有明确证据，不靠猜。

代价同样明确：每 Deployment 一个熔断器实例，内存与指标基数随 Deployment 数量线性增长；HALF_OPEN 期间会出现少量请求被“牺牲”用作探测；状态是进程内的，多实例部署时需要额外同步，这部分本篇不做，留给后面的多实例章节。

适用条件：上游数量大于等于 2，且存在同构可替换的 Deployment。如果只有一个上游，熔断只会让请求全部快速失败，必须配合兜底模型才有意义。

> 前置问准入
> 后置记成败
> 探测走旁路
> 三态各自明

# 05、实战一次

环境沿用 litelmgateway 的 open-api.zip Demo 现有工程，不额外升级 Spring Boot，JDK 与构建工具保持 Demo 原样。

依赖方面引入 resilience4j-spring-boot3（对应 Spring Boot 3）或 resilience4j-spring-boot2（对应 Spring Boot 2）。具体版本与 Spring Boot 的对应关系需按当前官方文档核验，不要凭记忆写死版本号。

配置先落地：

```yaml
gateway:
  health:
    probe-interval-ms: 30000
    probe-timeout-ms: 3000
    unhealthy-threshold: 3
  circuit-breaker:
    sliding-window-type: TIME_BASED
    sliding-window-size: 60
    minimum-number-of-calls: 20
    failure-rate-threshold: 50
    slow-call-duration-threshold-ms: 30000
    slow-call-rate-threshold: 60
    wait-duration-in-open-state-ms: 30000
    permitted-calls-in-half-open: 3
```

核心实现分四块。第一块是每个 Deployment 一个熔断器：

```java
@Component
public class DeploymentBreakerRegistry {

    private final CircuitBreakerRegistry registry;
    private final Map<String, CircuitBreaker> cache = new ConcurrentHashMap<>();

    public DeploymentBreakerRegistry(CircuitBreakerRegistry registry) {
        this.registry = registry;
    }

    public CircuitBreaker of(String deploymentId) {
        return cache.computeIfAbsent(deploymentId,
                id -> registry.circuitBreaker(id, defaultConfig()));
    }

    private CircuitBreakerConfig defaultConfig() {
        return CircuitBreakerConfig.custom()
                .slidingWindowType(CircuitBreakerConfig.SlidingWindowType.TIME_BASED)
                .slidingWindowSize(60)
                .minimumNumberOfCalls(20)
                .failureRateThreshold(50.0f)
                .slowCallDurationThreshold(Duration.ofSeconds(30))
                .slowCallRateThreshold(60.0f)
                .waitDurationInOpenState(Duration.ofSeconds(30))
                .permittedNumberOfCallsInHalfOpenState(3)
                .automaticTransitionFromOpenToHalfOpenEnabled(true)
                .build();
    }
}
```

第二块是路由准入，顺序不能乱：

```java
public Optional<Deployment> pick(List<Deployment> candidates) {
    for (Deployment d : candidates) {
        if (d.getAdminState() == AdminState.DISABLED) {
            continue;
        }
        if (!healthStore.isHealthy(d.getId())) {
            continue;
        }
        if (!breakers.of(d.getId()).tryAcquirePermission()) {
            continue;
        }
        return Optional.of(d);
    }
    return Optional.empty();
}
```

第三块是调用后回写证据，注意这里用的是带耗时的重载，慢调用才能被统计到：

```java
public Response invoke(Deployment d, Request req) {
    long start = System.nanoTime();
    try {
        Response resp = client.call(d, req);
        breakers.of(d.getId()).onSuccess(System.nanoTime() - start, TimeUnit.NANOSECONDS);
        return resp;
    } catch (Exception e) {
        breakers.of(d.getId()).onError(System.nanoTime() - start, TimeUnit.NANOSECONDS, e);
        throw e;
    }
}
```

第四块是定时主动探测，它只写 HealthStore，绝不碰熔断器：

```java
@Scheduled(fixedDelayString = "${gateway.health.probe-interval-ms:30000}")
public void probe() {
    for (Deployment d : deploymentRepository.findAll()) {
        if (d.getAdminState() == AdminState.DISABLED) {
            continue;
        }
        boolean ok;
        try {
            ok = client.ping(d, Duration.ofMillis(probeTimeoutMs));
        } catch (Exception e) {
            ok = false;
        }
        healthStore.update(d.getId(), ok);
    }
}
```

HealthStore 用连续失败计数来避免单次抖动误杀：

```java
public void update(String deploymentId, boolean ok) {
    State s = states.computeIfAbsent(deploymentId, k -> new State());
    synchronized (s) {
        s.lastProbeAt = Instant.now();
        if (ok) {
            s.consecutiveFailures = 0;
            s.healthy = true;
        } else {
            s.consecutiveFailures++;
            if (s.consecutiveFailures >= unhealthyThreshold) {
                s.healthy = false;
            }
        }
    }
}
```

# 06、排查

**现象一：熔断状态已经是 OPEN，但路由日志里仍然出现 chosen=dep-a。**

怀疑是熔断器没接进路由。检查发现路由层确实调用了 DeploymentBreakerRegistry，但只在 catch 块里调了 onError，调用前没有 tryAcquirePermission。看 metrics：dep-a 的 callNotPermitted 计数为 0，而 timeout 计数持续增长。证据说明熔断器一直在被动记录，从未真正拦住请求。根因是把熔断当成了“事后统计器”，而不是“准入闸门”。修复是把 tryAcquirePermission 提到发请求之前，全部候选都拒绝时返回空并交给 Fallback。

**现象二：dep-a 明明已经恢复，健康接口显示 healthy=true，但熔断器持续停在 OPEN，永远不回来。**

怀疑是探测没有触发状态迁移。检查发现探测任务调用了同一个 CircuitBreaker 实例，而 OPEN 状态下 CircuitBreaker 会直接拒绝这次调用，抛 CallNotPermittedException，被 catch 成“探测失败”，于是探活永远失败。根因是探测与真实请求共用了同一个熔断器。修复是让探测走独立的 HTTP 通道，只写 HealthStore，同时把 automaticTransitionFromOpenToHalfOpenEnabled 打开，让 OPEN 到 HALF_OPEN 由时间驱动，而不是由探测驱动。

**错误尝试：** 我一开始把探测间隔从 30 秒改成 1 秒，想着“探得越勤，恢复越快”。结果完全相反：OPEN 期间探测请求依旧被熔断器拒绝，恢复时间没有任何改善；而并发探测在上游侧形成小规模请求风暴，日志里开始出现 429。这个尝试错在混淆了两件事——探测频率和状态转换条件。OPEN 保持多久由 waitDurationInOpenState 决定，半开时放行几个由 permittedNumberOfCallsInHalfOpenState 决定，跟探测频率没有关系。

**现象三：手工把一个 Deployment 设为 DISABLED 之后，过了几分钟它又出现在候选集里。**

怀疑是人工状态被自动恢复覆盖。检查 admin 接口的写入路径，发现 Disable 只改了 HealthStore 的 healthy=false，没有改 adminState 字段，而探测成功后 healthy 被重置为 true，于是节点自动回到候选集。根因是把人工干预当成了健康状态的一种。修复是拆成两个独立字段：adminState 由人写，只有人能改；healthy 由探测写。路由层先看 adminState，再看 healthy。

> 先看准入点
> 再查记录源
> 错误尝试过
> 方知路走偏

# 07、优化

第 06 章的三条证据，直接确定了 V2 的五个改动。

根因一：准入与统计混在一起。修改：把 tryAcquirePermission 作为路由过滤链的第一道闸门，onSuccess / onError 只在真实调用后执行。原因是熔断器的语义是“拒绝 + 统计”两件事，必须分两个时机。新行为是全候选被拒时立即走 Fallback，不再向任何 OPEN 节点发出请求。验证方式是对照 metrics 中 callNotPermitted 与 timeout 的计数关系：OPEN 之后 timeout 不再增长，callNotPermitted 开始增长。

根因二：探测与真实请求共用熔断器。修改：探测走独立的轻量 HTTP 客户端，只写 HealthStore；熔断器的 OPEN 到 HALF_OPEN 交给 waitDurationInOpenState 和 automaticTransitionFromOpenToHalfOpenEnabled。原因是两者的证据口径不同，混用必然互相污染。新行为是探测失败不会把刚恢复的节点再次推回 OPEN。验证方式是主动打故障节点，观察探测失败次数增长的同时熔断器状态不变。

根因三：人工状态被自动逻辑覆盖。修改：deployment 表新增 admin_state 字段，与 healthy 完全分离，路由顺序固定为 adminState → healthy → breaker。原因是人做判断时掌握的信息（上游账单、账号状态、业务沟通）是探测拿不到的。新行为是 DISABLED 节点永久退出候选集，直到人工 Enable。验证方式是 Disable 之后等待多个探测周期，节点始终不出现。

另外两个配套改动：按 Deployment 规模给 Config 做了差异化，把慢调用阈值和滑动窗口放进配置而不是写死在代码里；恢复后的节点不是瞬间拿回全部权重，而是先在半开阶段以较小权重参与路由，观察一段时间再回满。这里只给出机制，不给出具体权重数字，因为权重怎么设必须由你自己的流量特征和上游容量决定。

> 隔离方不扰
> 分账始清白
> 权重渐回填
> 恢复不莽撞

# 08、演进

```text
[同一输入]
    |
    +--[V1] 全量候选轮转 + 事后记录
    |        代价：每次请求为坏节点付一次超时
    |
    +--[V2] 前置准入 + 独立探测 + 人工优先
    |        代价：半开期牺牲少量探测请求，指标基数上升
    |
[Trade-off]
得到：坏节点被真正摘除，恢复有证据、有人工闸门
失去：实现复杂度上升，HALF_OPEN 期存在不确定性请求
边界：多实例部署需要额外状态同步，本篇未覆盖
```

正确性上，V1 只保证单次请求可完成，V2 保证节点级状态可判定。稳定性上，V1 在坏节点上持续付出超时成本，V2 把这个成本压缩到阈值判断所需的那几次调用。复杂度上，V1 几乎是零成本，V2 引入了每节点一个熔断器、一个定时探测任务、两个状态字段和三态迁移逻辑，代码量与调试难度都明显上升。成本上，V2 增加的是内存与指标基数，以及半开期被牺牲的少量请求。适用范围上，V2 要求有至少两个可替换的 Deployment，单上游场景需要先有兜底模型。遗留问题是进程内状态无法在多副本间共享，副本 A 认为节点健康、副本 B 认为它已熔断，这在 K8s 多实例下会变成真问题。

> 同一请求入
> 两版行不同
> 得失常相伴
> 边界自心生

# 09、洞见

## 9.1 熔断器管的是准入，不是重试

反直觉判断：把 tryAcquirePermission 放在 catch 里，比不接熔断器还危险。因为请求已经发出去了，超时成本已经付了，熔断器只是把结果记下来，然后继续让下一个请求也去付一遍。准入门和统计门必须是两个不同时机，这一点在排查里被 metrics 计数直接坐实。

## 9.2 主动探测与被动统计必须分账

反直觉判断：探测越频繁，恢复越慢。因为 OPEN 状态下的探测会被熔断器自己拒绝，探测结果反而变成“上游仍然不可用”的伪证据。探测只该回答“这个节点现在通不通”，熔断器只该回答“这个节点能不能接真实流量”，两者是一套指标，但必须是两条链路。

## 9.3 人工状态是最高优先级

反直觉判断：自动化越完善，越需要保留一个不讲道理的开关。探测能测出网络通不通，测不出上游账号是否欠费、合同是否到期、业务是否正在灰度。把 adminState 和 healthy 拆成两个字段，看起来是冗余，实际上是给运维保留了最后一道止损手段。

## 9.4 恢复是一个渐进过程，不是一次状态翻转

CLOSED 到 OPEN 是断崖式的，OPEN 到 CLOSED 却必须是渐进的。半开额度、恢复后的权重回填，本质上都是在“尽快恢复容量”和“别把刚喘过气的上游再打挂”之间找平衡。把恢复当成一次翻转，就会得到振荡。

> 准入非重试
> 分账见真章
> 人工压自动
> 恢复须渐进

# 10、系统落地

原来有什么：上一章留下的 Pipeline 已经有 Retry 和 Fallback，路由能在多个 Deployment 之间轮转，但轮转是无状态的，节点级故障没有任何记忆。

本篇新增了什么：Deployment 级的 CircuitBreaker 注册表，三态状态机接入路由准入；独立的定时健康探测与 HealthStore，采取连续失败计数；adminState 与 healthy 双字段分离，人工优先；管理接口 /admin/deployments/health 与 circuit/reset、disable、enable 操作；健康看板所需的字段结构在本章定稿。

现在能做什么：上游节点故障后自动摘除，恢复后自动重新入池；运维可以一键禁用某个 Deployment 并由系统保证它不会被自动放回；所有状态变化可查、可操作；全候选被拒时会明确走 Fallback 而不是空转。

还缺什么：熔断与健康状态都在进程内存里，多副本之间不共享；管理页面只定了字段，UI 还没进控制台；恢复后的权重回填只有机制没有策略；配置重启后依赖配置文件，没有热更新与快照。

下一步如何演进：先补上 Key 与项目级的权限边界，让不同租户的请求走不同的候选集；之后把配置持久化与重启恢复补齐，再把状态共享问题交给多实例部署那一章解决。

> 昨日只重试
> 今日有生死
> 缺者犹存半
> 前路分级明

# 11、小结

```text
Q1 → 判活靠三态状态机 + 滑动窗口证据，慢调用与失败分开统计
Q2 → 探测通了只进 HALF_OPEN，按额度放行，通过后才回 CLOSED
Q3 → 手工 DISABLED 优先级最高，自动逻辑无权覆盖
状态 → Deployment 可自动摘除、自动重入，且全程可查可干预
```

Q1 的答案是：不要用单次失败或单次探测来下结论，用最小样本量约束下的失败率与慢调用率，配合 waitDurationInOpenState 控制观察节奏。Q2 的答案是：恢复必须走半开，半开额度是一次“有成本的试水”，试水成功才恢复全量。Q3 的答案是：把人工状态和健康状态做成两个字段，路由顺序固定，人工永远在前。

本篇最终交付的能力是：一个按 Deployment 隔离的熔断与健康体系，它能在故障发生时自动摘除节点，在上游恢复后自动重入，并且把最终决定权留给运维。

> 三问皆可答
> 一行状态清
> 摘除与重入
> 皆有据可循

# 12、作业

## 12.1 理解题：为什么 tryAcquirePermission 必须放在发请求之前，而不是在处理异常的 catch 里？

参考答案：熔断器的两个职责是拒绝和统计。放在 catch 里只完成了统计，请求已经发出，超时成本已经支付，OPEN 之后仍然会持续向上游发送流量，熔断等于没做。放在发请求之前，才能在状态为 OPEN 时直接拒绝，把成本压到零。

## 12.2 实战题：给现有 Demo 加一个 /admin/deployments/{id}/circuit/reset 接口，要求在不动 adminState 的前提下把熔断器重置为 CLOSED，并说明为什么重置不能顺带把 DISABLED 改成 ENABLED。

参考答案：实现上调用 CircuitBreakerRegistry 取到该 Deployment 的 CircuitBreaker，执行 reset 并把 HealthStore 的连续失败计数清零，只改熔断与健康状态，不触碰 adminState 字段。不能顺带改 adminState，是因为这两个状态来源不同：熔断是系统基于流量的判断，adminState 是人的判断，自动路径一旦能改写人工状态，第六章那个“DISABLED 节点自己回来”的问题就会复现。

## 12.3 排障题：某个 Deployment 的健康接口一直显示 healthy=true、circuitState=CLOSED，但真实请求的失败率明显偏高，你会怎么定位？

参考答案：先怀疑探测与真实流量口径不同。探测请求轻，可能被上游网关缓存或快速返回，而真实请求参数大、耗时长。检查 slowCallDurationThreshold 是否设置合理，确认慢调用是否被计入统计；再检查熔断器的滑动窗口类型和 minimumNumberOfCalls，看样本量是否足够触发阈值；最后确认真实请求的失败是否被完整记入 onError，是否存在被上层 catch 吞掉而没有回写的情况。

## 12.4 架构判断题：如果把熔断粒度从 Deployment 改成 Provider 级，会带来什么后果？

参考答案：Provider 级熔断会把同一个供应商下所有区域的 Deployment 绑成一个整体。一个区域的网络抖动会导致全部 Deployment 被摘，容量瞬间下降；反过来，某个区域持续故障时，其他健康区域也没有独立判定。Deployment 是最小可网络到达单元，故障域与它对齐，粒度放在这里才有意义。

> 四题分四角
> 理解到判断
> 答案非唯一
> 证据是准绳

# 13、思考

这一章真正的冲突不是“怎么接 Resilience4j”，而是“凭什么相信一个节点已经好了”。摘除一个坏节点很容易，任何一个连续失败计数器都能做到；难的是用什么证据把它放回来，以及在这个证据不足时保留人的判断权。

把这条判断抽出来，它可以复用到任何多上游系统上：任何自动化恢复机制，都必须先回答三个问题——证据来自哪条链路、状态在什么条件下翻转、以及谁有权限覆盖它。这三件事只要有一件含糊，恢复机制就会变成振荡源。

熔断器给出的其实不是“自动恢复”，而是一个可以被审计的恢复流程。真凰不死身的价值不在于不死，而在于每次重生之后，它都还是同一只凤凰。

> 一念辨边界
> 一证定根因
> 一改知取舍
> 一役见真章
