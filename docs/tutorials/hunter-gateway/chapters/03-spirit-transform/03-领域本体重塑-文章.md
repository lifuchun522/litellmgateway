# 七模型定本体：LLM Gateway 的 To-Be 语义与迁移差异映射

> 换完包名只是换壳，本体不定，后面十五境全要返工。

```text
[读者] 已逆向完 Demo、正准备堆功能的 Java 后端工程师
[痛点] 类名表名随手定，AI 一上午能生成十个语义重复的实体
[现在读] 正处在第 03 境，本体没定，越晚定代价越大
[读完] 能用七模型写出一份可追溯、可机器校验的 As-Is → To-Be 映射
```

```text
[旧方案] 照着 Demo 的 Controller / Entity 一路加字段
    |
    v
[新需求] 多 Provider、多项目、多 Key、预算、计量、审计同时上
    |
    v
[冲突] Demo 的本体是“单上游单租户”，撑不起多租户多上游
    |
    v
[后果] 表越加越乱，API 语义漂移，Key 权限和成本无法自洽
```

我是老李，这个系列一路写下来，基座是 GitHub 上 litellmgateway 仓库 open-api.zip 那份 Demo。前两境干的事很朴素：先把 Demo 解压出来逆清楚，再把项目名和包名整体换掉，让它看起来像我们自己的东西。换完之后，本地跑起来通，Swagger 页面也能打开，所有人都觉得“骨架有了”。

问题出在第三境。换骨只是改名，Demo 的骨架仍然按“一个上游、一个用户、一个 Token”来组织。而我们要做的网关，要接多家 Provider、要按项目隔离、要给每个 Key 限速限预算、要出成本报表。你如果直接把“加字段”当成演进手段，那这份代码会在第 07 境前彻底失控。

所以这一境不写业务逻辑，只做一件事：用 ontology-driven-dev 的七模型，把 To-Be 语义先钉死，再把 Demo 现有的类、表、API 逐条映射过去，形成一个可被机器校验的差异清单。后面每一个 API、每一张表、每一个页面，都必须能说清楚它属于哪一层。

把 Demo 换完包名，就等于有了自己的网关本体了吗？

是先把本体钉死再写代码，还是先写代码再回头补文档？

如果本体定义错了，这份代价会在第几境集中爆发？

# 01、故事

场景是换骨之后的第二周。仓库已经改名，包名统一成了 gw 前缀，Demo 里的 Controller、Service、Mapper、Entity 全部搬了过来，编译通过。

任务是：在冻结的新仓库上，定义 LLM Gateway 的 To-Be 本体，并给出 As-Is 到 To-Be 的差异映射。分支名和提交信息在动工前就定好了，`chapter/03-ontology-domain` 和 `docs(ch03): define gateway ontology and migration map`。它明确告诉团队：这一境只产出定义和映射，不产出功能。

第一天的 PR 就把冲突摊开了。A 同学加了 `ProviderController`，里面既有上游配置的增删改查，又有“试调用一次上游”的接口；B 同学加了 `ModelController`，里面存了模型名，也存了上游地址。评审时大家吵起来：A 说模型是上游的事，B 说模型是网关对外暴露的东西。吵到最后发现，两个人说的“模型”根本不是同一个东西。

更麻烦的是命名。前面逆向出来的 `Unit`、`UnitController`、`TokenController`、`RouteConfig`，这些名字当时只是“Demo 里叫什么我们就叫什么”。可一旦开始加多租户、加预算、加重试，这些名字会把后面十几个类的设计带偏。

这里的核心冲突只有一句话：Demo 的本体是单上游单租户的，而我们要的是多上游多租户的。换包名解决的是“它看起来像谁的代码”，本体建模解决的是“它到底在说什么”。后者的欠账，会在每一次加表、加接口、加页面时收利息。

> 换壳不改骨
> 加表先加乱
> 一词一归处
> 未定莫开工

# 02、问题

旧方案是把 Demo 的结构当作默认正确，遇到新需求就在最近的类上加字段。这个方案在单上游场景下完全够用，但在我们的目标形态下会连续失效。

第一层失效是实体边界失效。上游配置、上游调用能力、对外模型名、物理端点、路由策略，这五件事在 Demo 里往往分散在两三个类里，谁都能改。一旦要支持“同一个对外模型名路由到三家上游的五个端点”，你会发现在现有结构里根本找不到“端点”这个概念的落脚点，只能把地址塞进路由配置行里。改了上游地址，等于改了路由；改一次路由，等于动一次线上配置。

第二层失效是权限边界失效。Demo 的 Token 没有项目归属，谁拿到 Token 谁就是上帝。而我们后续要做的虚拟 Key、项目隔离、模型 ACL、RPM/TPM 限额、预算封顶，全部要求“Key 属于项目、受规则约束”。Key 这个实体不带上项目关系，后面所有的限流和预算都无处挂载。

第三层失效是计量边界失效。要出成本报表，就必须回答“这一次请求是谁发的、走的哪个 Key、命中哪个部署、消耗多少 token、按什么单价计费”。这五问里有三问的实体在 Demo 里根本不存在。没有 RouteAttempt 和 Usage，重试和回退就只是一段没有痕迹的 for 循环，成本核算更是无从谈起。

业务影响也很直接：没有本体，定价和预算就只能靠人工对账；没有权限边界，接进来的第一个外部项目就是一次安全口子；没有计量实体，付费客户拿不到可信账单。

技术表现则更朴素：同一个概念在三个类里各写一遍；数据库里出现三张带 `provider` 前缀的表却字段不一致；Swagger 里两个接口都叫“查询模型”，返回结构不同。

这一境的完成标准必须是可验证的，我把它写成三句话。第一句，每一个 To-Be 实体、能力、规则、角色、流程、视图、菜单，都必须能被归入七模型中的唯一一层。第二句，每一行 Demo 里已有的类、表、接口，都必须在映射清单里出现，且带明确的处置动作。第三句，这份清单必须能被一段代码自动校验，且校验失败时构建失败。

> 旧模撑不住
> 新需压上来
> 标准写清楚
> 才算真完成

# 03、原理

ontology-driven-dev 的七模型，本质上是在动代码之前先把“系统在说什么”分层固定下来。

M1 是实体层，管的是系统里长期存在的名词。对这个网关来说，就是 Provider、LogicalModel、Deployment、RoutePolicy、Project、VirtualKey、RequestLog、RouteAttempt、Usage、Budget 这一组。它们会被落成表、落成类、落成 API 的资源路径。

M2 是能力层，管的是系统能做什么：接入一个 Provider、执行一次请求、选择一条路由、校验一个 Key、做一次重试、执行一次回退、记一次用量、算一次成本。

M3 是规则层，管的是什么允许、什么禁止：Key 明文只显示一次、模型 ACL、重试白名单、预算封顶、隐私字段脱敏、配置快照。规则不产生新名词，它约束 M1 和 M2 的行为。

M5 是角色层：SystemAdmin、OpsAdmin、ProjectOwner、Developer、Auditor、GatewayClient。M6 是流程层：Provider 接入、请求执行、Key 发放、配置发布、故障恢复。M7 是视图层：Dashboard、Usage、Cost、Health、Routing、Error。MU 是菜单层，是这些视图在控制台里的入口组织方式。

这里有一个反直觉判断：本体不是文档，而是约束生成器。

大多数人理解的本体是一份写给人看的说明，写完就归档。但在这套方法里，本体的价值恰恰在于它能反过来约束代码——同一个词只能属于一层，于是 `Provider` 不能既是实体又是能力；同一个概念只能有一个名字，于是不会出现 `Unit` 和 `Provider` 并存。文档是给人看的，约束是给编译器和 CI 看的。前者靠自觉，后者靠失败。

第二个反直觉判断更具体：M1 里最该先定死的，不是 Provider，而是 RouteAttempt 和 Usage 这类“过程型实体”。

人的直觉是先定大名词，把 Provider、Model、Key 摆好，剩下的边写边加。但真正会撕裂系统的恰恰是过程型实体——它们记录的是“一次发生了什么的快照”，天然需要引用请求、Key、项目、部署、用量五六个上游。这些实体晚定一天，引用关系就晚定一天，后面所有重试、回退、熔断、计量的代码都要返工。

理解了这两点，后面的架构就不是“设计一个目录结构”，而是“用分层把这个约束落到工程里”。

> 本体非文档
> 乃是约束器
> 先慢后不返
> 一字定乾坤

# 04、架构

```text
[输入] Demo 的类 / 表 / API 清单（As-Is）
    |
    v
[模块] 七模型分层容器（M1/M2/M3/M5/M6/M7/MU）
    |
    v
[数据/状态] 差异映射行（as-is | decision | layer | to-be | note）
    |
    v
[处理] 归类 → 重命名 → 拆分 / 合并 / 新增 / 废弃
    |
    v
[输出] 可机器校验的迁移清单 + 领域词汇表
```

这张图里最关键的是中间那条竖线：差异映射行。它把“人脑里的归类”变成了“文件里的一行”，一行只能有一个 decision、一个 layer、一个 to-be 名。只要它落在文件里，就能被脚本读、被 CI 卡。

边界要划清。这套东西管的是语义归类，不管代码怎么写：它不会告诉你接口该用什么注解，也不会规定表字段类型。它管的是“这个词属于哪一层、它对应的旧物是什么、它该叫什么名字”。

收益有三个。第一，任何新增的东西都能被质问“你属于哪一层”，从而挡掉大量语义重复的设计。第二，重命名不再靠口头约定，改名会同时改掉映射文件，历史可追溯。第三，拆分类的重构有了依据——`UnitController` 拆成 `Provider` 和 `ProviderConnector`，不是重构冲动，而是映射表里的两条 SPLIT。

代价也很实在。维护一份映射文件本身要花时间；团队里总有人觉得“这不就是文档吗”，从而绕过它。所以必须配合机器校验，让绕过的人构建失败。

适用条件写在这里：只要系统还会长期演进、还会有多人并行加实体，这套分层就值得做。如果只是一次性的脚本、永远不会有第二个 Provider，那确实没必要。

> 输入是旧类
> 中间是七模
> 输出是映射
> 边界先画清

# 05、实战一次

这一节做一个最小可跑的 V1：用一段纯 JDK 的 Java 代码，读入 TSV 格式的映射清单，校验它是否满足“一物一层、保留项必须有 To-Be 名、七层必须被覆盖”。

环境与依赖：JDK 17 或以上，不需要 Maven、不需要任何第三方库，javac 直接编译。这一点是刻意的——本体校验只该依赖 JDK，任何为了跑校验而引入的依赖都会让人拒绝执行它。

package gw.ontology;

public enum Layer {
    M1_ENTITY("M1", "实体：系统里长期存在的名词"),
    M2_CAPABILITY("M2", "能力：系统能做什么"),
    M3_RULE("M3", "规则：什么允许、什么禁止"),
    M5_ROLE("M5", "角色：谁可以做什么"),
    M6_PROCESS("M6", "流程：事情按什么顺序发生"),
    M7_VIEW("M7", "视图：人看到什么"),
    MU_MENU("MU", "菜单：入口在哪里");

    private final String code;
    private final String desc;

    Layer(String code, String desc) {
        this.code = code;
        this.desc = desc;
    }

    public String code() { return code; }

    public String desc() { return desc; }
}

读取 TSV。字段数不对就直接抛异常，宁可炸在读取阶段，也不要把半截数据带进校验。

```java
// ontology/gw/ontology/MappingFile.java
package gw.ontology;

import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

public final class MappingFile {

    public static List<Mapping> load(Path path) throws IOException {
        List<Mapping> out = new ArrayList<>();
        for (String raw : Files.readAllLines(path, StandardCharsets.UTF_8)) {
            String line = raw.trim();
            if (line.isEmpty() || line.startsWith("#")) {
                continue;
            }
            String[] c = line.split("\t", -1);
            if (c.length != 5) {
                throw new IllegalArgumentException("字段数必须是 5，实际 " + c.length + "：" + line);
            }
            out.add(new Mapping(c[0], Decision.valueOf(c[1]), Layer.valueOf(c[2]), c[3], c[4]));
        }
        return out;
    }

    private MappingFile() {
    }
}
```

核心校验器。三条规则：保留类动作必须有 To-Be 名；每一行必须归层；同一个 To-Be 名不得跨层。第三条是整套方法里最锋利的一刀。

```java
// ontology/gw/ontology/OntologyCheck.java
package gw.ontology;

import java.nio.file.Path;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public final class OntologyCheck {

    public static void main(String[] args) throws Exception {
        Path file = Path.of(args.length > 0 ? args[0] : "docs/ontology/as-is-to-be.tsv");
        List<Mapping> all = MappingFile.load(file);

        List<String> errors = new ArrayList<>();
        Map<String, Set<Layer>> nameToLayers = new LinkedHashMap<>();

        for (Mapping m : all) {
            boolean dropped = m.decision() == Decision.DROP;

            if (!dropped && (m.toBe() == null || m.toBe().isBlank())) {
                errors.add("保留/重命名/拆分/合并/新增项缺少 To-Be 名：" + m.asIs());
            }
            if (m.layer() == null) {
                errors.add("未归层：" + m.asIs());
                continue;
            }
            if (!dropped && m.toBe() != null && !m.toBe().isBlank()) {
                nameToLayers.computeIfAbsent(m.toBe(), k -> new LinkedHashSet<>()).add(m.layer());
            }
        }

        nameToLayers.forEach((name, layers) -> {
            if (layers.size() > 1) {
                errors.add("跨层命名冲突：" + name + " -> " + layers);
            }
        });

        long added = all.stream().filter(m -> m.decision() == Decision.NEW).count();
        long uncovered = Arrays.stream(Layer.values())
                .filter(l -> all.stream().noneMatch(m -> m.layer() == l))
                .count();

        System.out.println("条目=" + all.size() + " 新增=" + added
                + " 未覆盖层=" + uncovered + " 错误=" + errors.size());
        for (String e : errors) {
            System.out.println("  [FAIL] " + e);
        }
        if (!errors.isEmpty()) {
            System.exit(1);
        }
    }

    private OntologyCheck() {
    }
}
```

# 06、排查

V1 跑通之后，我开始做一件更狠的事：把最初写的那版映射再跑一遍。那版 `UnitController#invoke` 的 To-Be 名我顺手也写成了 `Provider`，因为脑子里想的是“这就是 Provider 的调用”。校验器立刻报错。

第一条诊断链。

现象：`条目=16 新增=8 未覆盖层=0 错误=1`，紧跟一行 `[FAIL] 跨层命名冲突：Provider -> [M1_ENTITY, M2_CAPABILITY]`。

怀疑：第一反应是校验器太严。Provider 确实既是实体又是能力，现实世界就是这样，凭什么不许跨层。

检查：把映射文件里所有 to-be 名为 Provider 的行打出来，同时回到 Demo 里看这两个 As-Is 项各自承担了什么。

证据：`UnitController` 里有字段、有状态、有 CRUD，还会被其它类当作配置引用；`UnitController#invoke` 只有一个动作——拿配置去调一次上游。前者是名词，后者是动词。而 Demo 把动词方法挂在名词类上，映射时我忠实照抄了这份耦合，于是两层撞在了同一个名字上。

根因：不是校验器严，是 Demo 把“配置实体”和“调用能力”揉在一个类里；映射阶段照抄，等于把这份耦合平移进了 To-Be。

修复：M1 保留 `Provider`，只描述供应商的名称、类型、状态、凭证引用；M2 新增 `ProviderConnector`，负责“用某份配置去调一次上游”这个能力。调用入口从实体类里移出，实体类里不再出现任何 send 语义的方法。

**错误尝试：** 我第一次的“修复”是把校验器里的“一物一层”规则注释掉，让构建先过，想着等写完代码再回来拆。为什么这是错的？因为规则一旦消失，冲突就从“构建期一次失败”变成“编码期反复踩坑”。更糟的是，它会在别人的分支上爆炸：我这边继续加 `Provider` 的调用方法，同事那边在做 Deployment，两边合起来才发现同一个词在两个包下各有一套语义。规则的价值不在于它不出错，而在于它出错得早、出错得集中、出错在动手之前。

第二条诊断链。

现象：写完路由相关的映射后，我发现路由表设计里存在一个尴尬点——目标上游地址和路由策略写在同一行。改一个上游域名，要动一次路由配置；验一次路由策略，又必须连着端点的信息一起看。

怀疑：路由配置表设计得不合理，字段该拆。

检查：回到 Demo 看路由是怎么选上游的，再看映射表里 `Unit` 被处理成了什么。

证据：`Unit` 这一行被我一度写成 `DROP`，理由是“Unit 这个名字太含糊，先废弃，等需要端点时再加表”。而路由选择的确需要一个“目标”概念，在没有 Deployment 的情况下，目标只能塞进路由行里。也就说，路由行被迫承担了它不该承担的物理端点信息。

根因：To-Be 里缺了 Deployment 这一层。没有它，物理端点（地址、凭证、权重、健康状态）就没有归属，只能寄宿在路由策略里；而路由策略是逻辑决策，本来不该关心走哪台机器。

修复：把 `Unit` 改为 `RENAME → Deployment`，并明确职责边界——LogicalModel 是“对外暴露什么”，Deployment 是“实际打到哪”，RoutePolicy 是“用什么规则在多个 Deployment 之间选”。Routing 作为 M2 的能力，输入是 LogicalModel 加请求上下文，输出是一个 Deployment。三者分开后，换上游地址只动 Deployment，改策略只动 RoutePolicy。

> 现象先记录
> 怀疑要落地
> 证据说话前
> 根因才现身

# 07、优化

两条诊断链给出了两个明确的根因，V2 就按这两条改。

第一条根因：实体与能力被同一个类承载，映射阶段被照抄进 To-Be，导致跨层命名冲突。修改方式是在七层里加一条硬规则——同一个 To-Be 名只能出现在一层，且这条规则必须由代码检查，不靠人 review。原因很简单：命名冲突在代码里是隐性的，两个包下各有一个 Provider，编译器不会报错，只有人到线上排查时才会发现。新行为是：只要映射文件里同名跨层，`OntologyCheck` 立刻以非零码退出。验证方式是把上一节那行冲突改回去，命令应输出错误 1 行并返回失败，改回来则恢复 0 错误。

第二条根因：缺 Deployment 层，物理端点寄宿在路由策略里。修改方式是在映射表里显式新增 Deployment，并把它标成 NEW 而不是 DROP 掉含糊的旧名。原因是“旧名字含糊”不等于“这个概念不存在”，直接把 Unit 废弃会丢掉一个真实的领域概念，等到第 06 境再补，前面所有路由代码都要重写。新行为是路由链变成 LogicalModel → RoutePolicy → Deployment，端点信息只出现在 Deployment。验证方式是检查映射表里是否还有任何一行把“地址、权重”类语义归到 RoutePolicy 层——应当为零。

V2 里还补了两条低成本但很值钱的规则。第一条，七层必须全部被覆盖，`未覆盖层` 大于 0 时给出提示（不直接失败，因为早期某些层确实可能暂时没有内容，但要让人看见）。第二条，每个 As-Is 项必须出现且仅出现一次，避免同一个旧类被两条映射行分别处理，最后两边各改一半。

把这两条加上之后，映射文件从“一份说明书”变成了“一份构建输入”。它的定位变了：以前是人写、人看、人忘；现在是机器读、机器卡、人和机器一起维护。

再往后，这份文件应该接进流水线的最前面。任何新增实体、新增接口、新增页面的提交，都必须先改映射，再改代码。顺序反过来就等于失效。

> 根因已找到
> 改法随之来
> 校验进流水
> 新行为可验

# 08、演进

```text
[同一输入] 一份 Demo 的类/表/API 清单
    |
    +--[V1] 人工归类 + 口头约定命名
    |      代价：换个人就换一套说法，冲突在第 06 境才暴露
    |
    +--[V2] TSV 映射 + OntologyCheck 构建门禁
    |      代价：多维护一份文件，多一层构建步骤
    |
[Trade-off]
得到：语义可追溯、冲突前置、改名有据
失去：随手加字段的自由、绕过流程的便利
适用边界：长期演进、多人并行的网关项目
```

正确性上，V2 明显更强。V1 的正确性完全依赖当时在场的人的记忆和表达能力；V2 把正确性的一部分外化成了文件加校验，谁改谁负责，改动留痕。

稳定性上，V2 更稳但也更僵。它会在你想“先加个字段试试”的时候拦住你，要求你说清楚这个字段属于哪个实体。对探索期的小项目来说这是负担，对已经定了方向、要长期跑的网关来说这是保护。

复杂度上，V2 多了一个概念——映射文件本身。团队需要理解三层：As-Is 长什么样、To-Be 叫什么、中间用什么动作迁移。这个学习成本大概半天，但它替代掉的是无数次“这个名字到底该叫什么”的会议。

成本上，V2 的增量主要是维护映射行的时间。降低这份成本的办法是把映射文件做成提交前的必改项，让人顺手就写，而不是攒到季度末集中补。

适用范围要诚实地说：这套东西适合本系列这种“明确要演进十几境”的项目。如果只是一次性脚本，或者只有一个人写、写完就丢，那确实是过度设计。

遗留问题有三个，都留到后面的境里解决。第一，映射文件目前只校验层与命名，还没校验实体之间的引用关系是否成立，比如 RouteAttempt 引用了哪些实体、是否必须引用 Usage。第二，M3 规则层还没有结构化表达，规则现在只是映射表里的一行名字，还没有参数、作用域和优先级。第三，映射表到数据库 DDL 之间还没有自动通道，表结构目前仍要手写。

> 同一份输入
> 两条路分叉
> 得失常相伴
> 边界要写清

# 09、洞见

## 9.1 本体是约束生成器，不是文档

这一境里最终起作用的不是那份 TSV 内容本身，而是 `OntologyCheck` 里那三段十来行的校验逻辑。真正把设计钉死的是代码，不是文字。文档可以被忽略，构建失败不能被忽略。

反直觉判断：本体做得越“完整漂亮”，如果它不能被执行，价值就越低。一份三百行、没人会跑的领域说明，价值低于十行会失败的校验。前者给人安全感，后者给人约束力。

## 9.2 最该先定死的是过程型实体

Provider、Model、Key 这些“大名词”很显眼，大家都想先定它们。但真正决定系统能不能扩的是 RouteAttempt、Usage、RequestLog 这类过程型实体，它们记录“一次请求发生过什么”。它们晚定一天，所有引用它们的代码就晚定一天。

反直觉判断：先定动词、后定名词，架构反而更稳。因为名词的数量是可控的，而“一次请求经过哪些环节”是天然的复杂源头，它决定了名词之间要建立多少条关系。

## 9.3 命名冲突比缺实体更危险

缺实体会以编译错误的方式暴露，你一定会发现。命名冲突不会，它会让两拨人各自写出能跑的代码，然后在联调时才发现是同一个东西。前者的代价是一次改动，后者的代价是一次重构加一次信任损耗。

这也是“一物一层”这条规则值得用代码去卡的原因：它卡的不是风格，是协作成本。

## 9.4 可追溯性必须由机器保证

“后续每个 API、每张表、每个页面都可追溯到七模型”这句话，如果靠人保证，三个月后就只剩下一句话；如果靠 `OntologyCheck` 加 CI 保证，它就成了每次提交都要过的门槛。

本体的完整性不是一次评审出来的，是被每一次提交反复确认出来的。

> 判断从证来
> 非从感觉来
> 反直觉之处
> 正是要害处

# 10、系统落地

原来有什么：一份换完包名、能跑的 Demo 骨架，类名表名沿用了上游 Demo 的命名，业务语义只存在于几个人脑子里。

本篇新增了什么：一份七层枚举定义，一份 As-Is 到 To-Be 的映射清单，一个能独立运行的 `OntologyCheck` 校验器，以及三条被固化的规则——保留类动作必须有 To-Be 名、每行必须归层、同一个 To-Be 名不得跨层。分支 `chapter/03-ontology-domain` 上的提交 `docs(ch03): define gateway ontology and migration map` 就是这份产出的落点。

现在能做什么：任何一个新来的同学，打开映射文件就能知道 `Unit` 对应 `Deployment`、`UnitController#invoke` 对应 `ProviderConnector`，并且知道为什么这么拆。任何一个准备加表的同学，在动手前必须先想清楚这张表属于 M1 还是 M7。重命名不再是“我觉得”，而是映射文件里的一次 diff。

还缺什么：M3 规则层目前只是一行名字，没有参数；M5 角色层到 M6 流程层之间的授权矩阵还没表达；实体之间的引用关系（谁必须引用谁、谁可以引用谁）还没有进入校验范围；映射表到 DDL、到 OpenAPI 的自动生成通道也还没有。

下一步如何演进：把映射文件升级成三段式——实体定义段、引用关系段、规则定义段。实体段与引用段合起来就可以驱动 DDL 生成，规则段可以在后续实现 Key 权限与限流预算时被直接读取。这样一来，第 04 境的协议契约与第 11 境的 Key 权限，都能从同一份本体生长出来，而不是各自另起一套。

# 12、作业

## 12.1 理解题：为什么 Provider 只能出现在一层？如果业务上真的既是实体又是能力怎么办？

参考答案：跨层命名会让两拨人写出两个都叫 Provider 却语义不同的东西，编译器不报错，人也不容易发现，代价推到联调期才付。业务的解法不是允许同名跨层，而是拆成两个名字：M1 的 Provider 描述配置与状态，M2 的 ProviderConnector 描述调用行为。名字分开，职责就分开了。

## 12.2 实战题：给 As-Is 里的 `Model` 表设计映射，要求能支持“同一个对外模型名路由到三家 Provider 的五个端点”。

参考答案：`Model` 重命名为 `LogicalModel`，归 M1，只保存对外模型名、可见性、状态、ACL 引用。新增 `Deployment`（M1），一条记录对应一个物理端点，含 providerId、endpoint、凭证引用、权重、健康状态。新增 `RoutePolicy`（M1）描述选择规则，`Routing`（M2）描述选择动作。三者关系为：一次请求带 LogicalModel 进来，Routing 依据 RoutePolicy 在一组 Deployment 中选出一个。三家 Provider 五个端点就落成五条 Deployment。

## 12.3 排障题：`OntologyCheck` 报 `跨层命名冲突: Provider -> [M1_ENTITY, M2_CAPABILITY]`，你怎么定位并修？

参考答案：先打印所有 to-be 名为 Provider 的映射行，定位是哪两个 As-Is 项映射到了同一个名字；再回到 As-Is 看这两项各自是名词还是动词。若是名词加动词，动词那行改名为 ProviderConnector 并归 M2，同时把调用入口从实体类中移出。改完后重跑校验，错误数应为 0。注意不要通过删规则来“修复”。

## 12.4 架构判断题：把 MU 和 M7 合并成一层，可行吗？

参考答案：短期可行，长期不建议。M7 是视图语义，回答“人看到什么数据”；MU 是入口语义，回答“这些视图在控制台里怎么组织、谁能看到”。同一份 Cost 视图，对 ProjectOwner 和 Auditor 的入口位置与权限不同，合并后必然要在视图定义里塞权限字段，视图层会变脏。保持两层分开，第三至尊术阶段的灰度与策略扩展才挂得上去。

> 理解要到位
> 实战要能跑
> 排障要能证
> 判断要能守

# 13、思考

这一境的核心冲突只有一个：我们手上是一份单上游单租户的 Demo，而要做的是一个多上游多租户的网关。换包名解决不了这个问题，加字段更解决不了，因为冲突发生在语义层，不在代码层。

真正把冲突解掉的动作，是把七模型当成一个约束器用起来。它逼你对每一个新增名词回答三个问题：你属于哪一层？你的 As-Is 是什么？你叫什么名字？这三个问题一旦变成构建期必须通过的检查，本体就不再是会后纪要里的几行字。

这一境交付的其实不是映射表，而是一条判断准则：任何不能被追溯回七模型的设计，都是还没想清楚的设计。后面无论是 Protocol 契约、Pipeline 编排、Retry 轮转，还是可观测与高级策略，都要回到这条准则上来对齐。

本体定下来，后面的每一境才有地方长。

> 本体定边界
> 映射定迁移
> 可追溯为纲
> 后境不返工
