# 荒天帝炼大模型网关-第3境-化灵境-原始真解-领域本体重塑

三天内把七模型压成一张可追溯的映射表，代码先不动，但每个字段都得有人认领。
客户只关心调用挂掉时能不能自动换模型，七模型讲不出这件事，就是给内部看的文档。
上周三张工单全是超时后没有 Fallback 记录，RequestLog 和 RouteAttempt 不分家，永远查不到根因。
我扫了六个开源网关，能追溯路由决策的只有两家，它们的 RouteAttempt 都是独立表，不是字段。
七模型全细化，一期做不完。我建议只冻结 M1 领域对象和 M3 规则，其余先登记不细化字段。
方案A全量七模型一次成型，干净但慢；方案B先冻 M1 加 M3 留指针，一周能交付。我倾向B。
我逆向完 open-api.zip，Usage 和 RequestLog 现在挤在一张表，先冻本体再改表，等于推倒重写。
现在成本数据误差大概两成，因为 Deployment 和 LogicalModel 没分开计价。基线不清，别谈成功线。
网关这类开发者工具，自然流量来自模型对比页和错误码文档，MU 里的 Playground 才是真正的入口。
这类产品投搜索词，CAC 至少两百块起。不如先把七模型做进文档站，这轮我明确不投钱。
纯文档三周，折人力就是六万。我最多批三天一个人，超了就得证明能省下多少返工。
VirtualKey 明文只显示一次，必须写成规则加测试用例，只写在文档里，泄露了责任算谁的。
第一棒 Bob 出七模型骨架，Emma 收 M1 和 M3，Alex 补 As-Is 映射。三天后必须有人签字。
既然 RouteAttempt 要独立，客户至少得看到每次换模型的原因。我接受先做骨架，但失败原因字段必须有。
按这个骨架，工单里能查到第几次尝试、换了哪个 Deployment。达到这个我认，否则一线还是黑盒。
我又核了两家云厂商的审计接口，都要求 Attempt 级别可导出。我们的 Auditor 角色必须能读这张表。
我改口径：一期只交付 M1 和 M3 冻结版，M2 到 MU 只做映射指针，字段层面这一期不再讨论。
最终取舍：牺牲一步到位的完美模型，换来可演进的指针结构。M1 和 M3 冻结，其余半年后补。
映射表细到表名、字段和 API 路径，RequestLog 拆出 RouteAttempt，Usage 独立建表，RequestId 做唯一键保证幂等。
成功线：成本误差从两成降到百分之五，路由可追溯率九成五。停止线：误差超一成五就回退旧口径。
把七模型翻成公开错误码表和路由说明页，三个月自然流量涨三成，验证指标是文档站到 Playground 的转化。
这轮不投。真要投也在 Playground 上线后只买品牌词，CAC 上限压到八十，埋点先埋注册和首次调用。
预算两万，三天一人，超支要 Mike 书面批，验收不过不追加。ROI 门槛是后续少返工两周。
三条红线：Key 只在创建时返明文，Retry 白名单必须可审计，Auditor 只读不能改配置。做到就算过关。
Owner 定死：Bob 出本体、Emma 定范围、Alex 写映射，周四十八点前推到 chapter/03-ontology-domain 分支。
就这么定：只做 M1 和 M3 冻结加全量映射指针，其余不做。周四提交，追溯不到七模型的字段一律删。
