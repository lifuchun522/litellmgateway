# 中文控制台：不重写 UI 骨架，用旧 Demo 前端统御 Gateway 全能力

> 网关跑通不等于能交付，管理面才是最后一根骨。

```text
[读者] 把 LLM Gateway 跑通、正卡在「怎么交出去」的后端工程师
[痛点] 配置靠 curl 和 SQL，新同事接一个模型要两小时
[现在读] 后端能力已齐，只差一个能把它们统御起来的管理面
[读完] 能用复用型前端加 Admin API，跑通 Provider→Model→Route→Key→Playground
```

```text
[旧方案] curl 加 SQL 手改配置，经验靠口口相传
    |
    v
[新需求] 管理员在页面上自助完成配置与验证
    |
    v
[冲突] 重写前端要两周，复用旧 Demo 前端又怕接不上新后端
    |
    v
[后果] 管理面不交付，网关永远停在「只有作者会用」
```

我是老李。这套 Java 轻量级 LLM Gateway 是从一份 open-api Demo 上长出来的：先逆向 Demo 摸清骨架（狻猊宝术），再换项目名与包名（柳神法），然后把本体七模型立正（原始真解），一路做协议、Pipeline、Provider、路由、Key、限流、熔断、Usage。到第 14 境为止，后端该有的能力基本都有了。

但有个尴尬的事实：我自己用没问题，换个人就不行。上周三，一位同事要接一个新的模型供应商，我给他的步骤是：先在库里插一条 provider，再插 deployment，再写一条 routing rule，再用 curl 生成 VirtualKey，最后 curl 一次 /v1/chat/completions 看通不通。他做了两个小时，中间错了三次。

我的目标是：让管理员只在浏览器里点，就能走完 Provider 到模型、到路由、到 VirtualKey、再到 Playground 这条闭环。

为什么后端能力已经齐了，管理面却还是空的？

前端这一步，是推倒重写，还是在旧骨架上接新筋？

如果为了让控制台快点出图，让它绕开主链路、直接读库或直连上游，会发生什么？

# 01、故事

周一早上九点四十，值班群里弹出一条消息：某个上游开始大面积 429。我打开终端，先 grep 配置文件，再连数据库看 deployment 表，再翻路由规则，二十分钟后才确认：出问题那条 deployment 的权重，是上周为了临时压测调高的，谁调的、为什么调，没有任何记录。

这就是第 01 境到第 14 境留下的债。我们有了上苍之手立下的协议边界，有了六道轮回天功编排的 Pipeline，有了鲲鹏宝术支撑的多上游适配，有了轮回宝术的失败轮转、真凰不死身的熔断恢复、天角蚁宝术的限流与预算、不灭经的配置持久化，还有金璇波纹功做的 Usage 与 Cost 统一计量。每一样都能用，但没有一样看得见。

任务是：把这条链路上每一次手敲，换成页面上的点击。

当前方案其实就在仓库里。那份 open-api Demo 自带一套已经成熟的前端工程，路由、布局、请求封装、基础组件都跑通了，原本只用来自家后台的几项功能。我们的做法是：不重写这套骨架，只在它成熟的路由和基础组件上加页面——Gateway 自己的十一个入口，Dashboard、Provider、模型、Deployment、路由、Project、VirtualKey、日志、Usage、Playground、系统，全部以「新增一个菜单项、新增一个页面文件、新增一个 api 模块」的方式挂上去。

冲突也在这里。后端这一年长出来的能力，前端一个都不知道。Provider 有健康状态、Deployment 有权重和额度、Route 有多层匹配、VirtualKey 有预算，这些在页面上全都没有对应的形状。要补形状，就得回头把此前只服务 curl 的接口，一个个补成服务 UI 的接口。

> 骨已长成山
> 门却只一把
> 今日开正门
> 让人自己走

# 02、问题

旧方案失效得很彻底。配置三件套只能靠 SQL 或脚本写；VirtualKey 只能 curl 生成，额度写在配置文件里；想知道今天花了多少钱，得手动跑聚合 SQL；出问题只能翻日志文件，RuntimeContext 和 RouteAttempts 只活在内存对象里，落库的只有一行结果。

业务影响是：交付半径等于会写代码的那个人。每接一个新供应商，我就得在旁边站着；每次变更没有审计、没有回滚入口；被问「现在到底是哪个 deployment 在服务哪个模型」时，我答不上来。

技术表现更具体，逐条都能验证：

- 接口层面缺一整块，没有任何 /admin 前缀的管理接口；
- 已有接口返回的对象带着敏感字段，provider 的 apiKey 是明文回显的；
- 列表接口没有分页、没有关键字过滤，前端一拉就是全表；
- 没有统一错误体，页面出错只能显示一句 500；
- 没有 Playground，验证一次模型要走 Postman；
- 没有登录态与权限，任何能访问端口的人都能改配置。

所以本章的完成标准必须写死，否则又会变成「差不多能用」：

1. 管理员账号能登录，非管理员进不来；
2. 页面上能新增、编辑 Provider 与 Deployment，并能测连通；
3. 能把 LogicalModel 与 Deployment 绑成一条 Route；
4. 能生成 VirtualKey，并指定所属 Project 与限额；
5. Playground 支持传入 key、model、system、user、temperature、max_tokens、stream；
6. Playground 结果区展示 provider、deployment、tokens、cost、latency、TTFT；
7. Dashboard 展示请求数、Token、Cost、成功率、P95、Provider 健康；
8. 日志详情展示 RuntimeContext、RouteAttempts 与错误信息，Prompt 默认不落库。

> 手能改的库
> 人看不懂的库
> 不落纸上功
> 终是独门技

# 03、原理

第一条原理：控制台是后端接口的第一个「非开发者用户」。以前接口的消费者只有 curl 和我本人，我可以容忍返回体带一个明文密钥、可以容忍列表不分页、可以容忍抛裸异常。一旦页面成为消费者，这些容忍全部失效。所以控制台不是 UI 工程，是接口契约的补全工程。

第二条原理是最反直觉的那条。反直觉判断：控制台工作量的七成在后端，而不是在前端。每加一个页面，通常要补四个接口——列表、详情、更新、动作（测试连通、生成 key、重置额度）。前端反而是最省的那部分，因为骨架已经成熟，改骨架的成本远高于写页面。

第三条原理：Playground 不能开后门。它本质上就是「带 UI 的 OpenAI 客户端」，必须拿真实 VirtualKey 走 /v1/chat/completions，和外部 SDK 请求共用同一条 Pipeline。只要它绕开主链路，它显示的 tokens、cost、latency 就与线上不是同一套计量，控制台立刻从「可信的窗口」退化成「最好看的假象」。

第四条原理：Prompt 默认不落库是合规取舍，不是偷懒。用户输入里可能有身份信息、有内部字段名、有还没公开发布的业务描述。落库带来的是可观测性收益，但代价是扩大敏感数据的驻留面。折中方案是：落 RuntimeContext、RouteAttempts、错误、token、cost、latency、TTFT，但不落 Prompt 原文，只在页面上明确提示「未存储」。

第五条原理：复用前端要有明确边界。只允许新增文件——新增菜单项、新增页面、新增 api 模块；不允许改动成熟的路由配置和基础组件。边界一旦模糊，一次「顺手优化基础组件」就可能让其他后台功能一起回归。

> 契约先于界面
> 计量先于展示
> 后门一旦开
> 数据即成谎

# 04、架构

```text
[输入] 管理员在浏览器点击 / Playground 发一次对话
    |
    v
[模块] 复用型前端骨架 + /admin 管理 API + 最小 RBAC
    |
    v
[数据/状态] 登录态、菜单表、Provider/Deployment/Route/Key 配置、Usage 聚合
    |
    v
[处理] 管理写操作落配置库；Playground 转内部调用走 /v1 主链路
    |
    v
[输出] 页面渲染 + 真实 RuntimeContext/RouteAttempts/Usage 回显
```

这套架构的边界很清楚：左边是浏览器，右边是已经存在的网关能力。控制台不新增任何业务能力，它只做三件事——把配置能力暴露出去，把观测能力读出来，把验证入口接到主链路上。

收益是交付半径从「会写代码的人」扩大到「会用浏览器的人」，变更有了统一的入口，统计口径和线上调用一致。

代价有三项要明说：一是内部调用会多一次 HTTP 往返，Playground 的首字节时间会比直连上游略高；二是管理接口需要额外的鉴权与脱敏代码，维护面变大；三是前端只要新增页面，就不动骨架，这也意味着某些「更优雅」的布局改造要放弃。

适用条件是：团队规模不大、前端人力有限、后端已经从 Demo 长出一套稳定的接口风格。如果一开始就没有可复用骨架，那这套做法不成立，应该先把骨架当项目做。

需要说明的是：Demo 的具体目录结构、前端技术栈与既有组件清单，需按当前仓库 lifuchun522/litellmgateway 的 open-api.zip 核验后再落地。

> 不造新骨架
> 只接新筋络
> 少即是快
> 稳即是远

核心实现第一块是登录与签发，直接给出类主体：

```java
@Service
public class AdminTokenService {

    private final Map<String, AdminUser> users;
    private final PasswordEncoder encoder;
    private final SecretKey key;
    private final Duration ttl;

    public AdminTokenService(AdminProperties props, PasswordEncoder encoder) {
        this.users = props.getUsers().stream().collect(Collectors.toMap(
                AdminProperties.User::getUsername,
                u -> new AdminUser(u.getUsername(), u.getPasswordHash(), Role.valueOf(u.getRole()))));
        this.encoder = encoder;
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(props.getJwtSecret()));
        this.ttl = props.getTokenTtl();
    }

    public AdminUser authenticate(String username, String rawPassword) {
        AdminUser user = users.get(username);
        if (user == null || !encoder.matches(rawPassword, user.passwordHash())) {
            throw new AdminAuthException("用户名或密码错误");
        }
        return user;
    }

    public String issue(AdminUser user) {
        Instant now = Instant.now();
        return Jwts.builder()
                .subject(user.username())
                .claim("role", user.role().name())
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(ttl)))
                .signWith(key)
                .compact();
    }

    public AdminUser verify(String token) {
        Claims claims = Jwts.parser().verifyWith(key).build()
                .parseSignedClaims(token).getPayload();
        return new AdminUser(claims.getSubject(), "",
                Role.valueOf(claims.get("role", String.class)));
    }

    public long ttlSeconds() {
        return ttl.getSeconds();
    }
}
```

第二块是过滤器与安全链，保证只有 ADMIN 能写、VIEWER 只能读：

```java
public class AdminTokenFilter extends OncePerRequestFilter {

    private final AdminTokenService tokenService;

    public AdminTokenFilter(AdminTokenService tokenService) {
        this.tokenService = tokenService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String header = request.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            try {
                AdminUser user = tokenService.verify(header.substring(7));
                var auth = new UsernamePasswordAuthenticationToken(
                        user.username(), null,
                        List.of(new SimpleGrantedAuthority("ROLE_" + user.role().name())));
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException | IllegalArgumentException ex) {
                SecurityContextHolder.clearContext();
            }
        }
        chain.doFilter(request, response);
    }
}

@Configuration
@EnableWebSecurity
public class AdminSecurityConfig {

    private final AdminTokenService tokenService;

    public AdminSecurityConfig(AdminTokenService tokenService) {
        this.tokenService = tokenService;
    }

    @Bean
    public SecurityFilterChain adminChain(HttpSecurity http) throws Exception {
        http.securityMatcher("/admin/**")
                .csrf(AbstractHttpConfigurer::disable)
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .authorizeHttpRequests(a -> a
                        .requestMatchers("/admin/auth/login").permitAll()
                        .requestMatchers(HttpMethod.GET, "/admin/**").hasAnyRole("ADMIN", "VIEWER")
                        .requestMatchers("/admin/**").hasRole("ADMIN"))
                .addFilterBefore(new AdminTokenFilter(tokenService),
                        UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

第三块是 Dashboard 聚合接口，把 Usage 与 Provider 健康一次查完，避免前端拉十几个请求：

```java
@RestController
@RequestMapping("/admin/dashboard")
public class AdminDashboardController {

    private final UsageQueryService usageQueryService;
    private final ProviderHealthQuery providerHealthQuery;

    public AdminDashboardController(UsageQueryService usageQueryService,
                                    ProviderHealthQuery providerHealthQuery) {
        this.usageQueryService = usageQueryService;
        this.providerHealthQuery = providerHealthQuery;
    }

    @GetMapping("/overview")
    public DashboardOverview overview(@RequestParam(defaultValue = "24h") String window) {
        Duration duration = DurationParser.parse(window);
        UsageAggregate usage = usageQueryService.aggregateSince(Instant.now().minus(duration));
        List<ProviderHealthView> health = providerHealthQuery.snapshot();
        return new DashboardOverview(usage.requestCount(), usage.promptTokens(),
                usage.completionTokens(), usage.costMicros(), usage.successRate(),
                usage.p95LatencyMs(), health);
    }
}
```

# 06、排查

第一条诊断链，现象是 Dashboard 上 Provider 健康全部显示 UNKNOWN。

怀疑是接口没接上数据。检查方式是先 curl 概览接口看原始返回，再去看 ProviderHealthQuery 的实现。证据是：snapshot 方法读的是熔断器的运行时状态，而熔断器状态只在有真实流量经过时才更新；进程刚启动、或者某个 provider 一整天没人用时，它的状态就是空的。根因是：健康态来自运行时内存，既没有持久化，也没有显式的 UNKNOWN 默认态，接口把「没有数据」和「挂了」混成了同一种表达。修复方式是在查询层引入显式三态加一个未知态，并带上最近一次调用时间。

第二条诊断链，现象是 Playground 的流式输出不是流式：页面转很久，然后一整段文字一起出现，TTFT 一栏永远是空。

怀疑是前端没解析 SSE。检查方式是抓包看响应头的 Content-Type，再去看控制台侧的对话接口实现。证据很清楚：那个接口是控制台自己写的一个「调试专用」通道，它把上游结果收集成一个完整 JSON 再返回，既没有透传 stream 参数，也根本不经过网关 Pipeline，所以 Usage 里没有这次调用的记录，TTFT 自然无处可算。根因是控制台开了后门。修复方式是删掉这个通道，让 Playground 内部以真实 VirtualKey 调 /v1/chat/completions，并把 stream 原样透传。

**错误尝试：** 有人会提出，干脆让前端直接请求上游 provider 的域名，绕开网关，最快最省事。这个方案错在三点：一是上游域名的密钥要下发到浏览器，等于把密钥公开；二是浏览器跨域会直接把这条路堵死，只能用代理再绕一层；三是绕过网关意味着绕过配额、限流、熔断和计量，页面上看到的 token 和成本根本不入账，控制台从此变成一个最贵的假象。更隐蔽的问题是，直连时的失败模式（超时、限流）和线上经过轮转与熔断后的失败模式完全不同，用它来排查线上问题，方向从第一步就歪了。

第三条诊断链比较轻，现象是日志详情页的 Prompt 一栏是空的，有人以为是落库失败。检查方式是直接查 Usage 表结构，确认没有 prompt 字段；再看日志详情接口的实现。证据是接口里压根没有查 Prompt 的逻辑。根因不是 bug，是设计：Prompt 默认不落库。修复方式不是补上落库，而是在接口返回里显式带一个 promptStored 标识，页面上明确提示「按策略未存储」，避免让使用者误判为数据丢失。

> 未知非已死
> 空值要发声
> 后门省一时
> 对账悔三日

# 07、优化

基于上一节的证据，V2 做五处修改。

第一处，Dashboard 从多次前端拼装改为一次聚合查询。根因是页面需要的数据散落在 Usage 与熔断器两处；修改是让 overview 接口内部并行取数并合并；原因是一次往返比十次往返更适合首屏；新行为是首屏只有一个请求，失败时只有一个错误提示；验证方式是打开页面观察网络面板只有一个请求，且接口异常时页面出现明确错误态而不是空白。

第二处，Provider 健康补充显式状态与最近调用时间。根因是 UNKNOWN 与 DOWN 被混同；修改是查询层返回四态并带 lastCallAt；原因是没有数据不等于服务不可用；新行为是刚启动时页面显示「未知（尚无调用）」，而不是红色告警；验证方式是重启服务后立即打开页面，确认不会出现误报。

第三处，Playground 接入主链路。根因是调试通道绕过了 Pipeline；修改是控制台侧不再实现任何上游调用，统一走 /v1/chat/completions，请求头透传 X-Request-Id，stream 参数原样透传；原因是要保证「页面所见等于线上所得」；新行为是结果区能拿到 provider、deployment、tokens、cost、latency、TTFT 六项，且这次调用会出现在日志与 Usage 中；验证方式是发起一次流式对话后，去日志页按 X-Request-Id 找回同一条记录。

第四处，日志详情结构化。根因是 RuntimeContext 与 RouteAttempts 是网关内部对象，此前只存在于单次请求的内存里；修改是新增日志详情接口，把它们序列化成结构化字段返回，并保留错误信息原文；原因是要让「为什么走了这个 deployment」可回答；新行为是页面上能看到这次请求依次尝试了哪些 deployment、各自失败原因是什么；验证方式是用一个不可用的上游制造一次 fallback，再去日志详情里核对尝试链。

第五处，脱敏与最小 RBAC。根因是此前接口把 provider 密钥明文回显；修改是密钥类字段只写不读，VirtualKey 只回显前缀与创建时间；原因是最小权限原则；新行为是 ADMIN 可写、VIEWER 只读；验证方式是用 viewer 账号调用写接口，确认返回 403。

这几处都不引入新的性能数字承诺，只描述行为变化。要看真实收益，应该在灰度环境按同一批请求对比接口耗时与页面首屏请求数，而不是凭感觉下结论。

> 改在证据上
> 不凭手感走
> 一次一变更
> 一次一验证

# 08、演进

```text
[同一输入] 管理员点开 Dashboard、发起一次 Playground 对话
    |
    +--[V1] 直连上游调试通道 / 多请求拼统计
    |      代价：显示与线上不一致，绕过配额熔断与计量
    |
    +--[V2] 走 /v1 主链路 + 一次聚合查询 + RBAC 与脱敏
    |      代价：多一次内部往返，接口实现更重
    |
[Trade-off]
得到：页面所见等于线上所得，统计可对账；失去：一点首字节时间与实现简洁性；边界：内部调用量远小于外部真实流量
```

先看正确性。V1 的 Dashboard 能出图，但数据来源是分散拼装，且健康态语义模糊；V2 的数据来源唯一，状态语义明确。正确性上 V2 是压倒性的，因为管理面的第一位要求是「说的和做的一致」。

再看稳定性。V1 的调试通道独立于主链路，意味着它不受限流、熔断、轮转保护，上游一抖动它就先炸；V2 复用主链路，天然继承了两章之前做好的可靠性治理。

复杂度上 V1 反而更低，页面代码更少，不需要理解 Pipeline；V2 需要理解内部调用与鉴权上下文，新同学上手要多读一点代码。

成本上 V2 每次 Playground 调用多一次内部 HTTP 往返，但这个量级相比真实外部流量可以忽略；真正的成本在于管理接口的维护面积变大了，多了一组接口要长期兼容。

适用范围上，V2 适用于已经有稳定 Pipeline 的网关；如果 Pipeline 本身都还没做出来，就不该先做控制台。

遗留问题也很清楚：这套管理接口目前还是手写的，随着页面增多会出现大量重复的 CRUD 代码，后续需要抽象一层通用的管理资源描述，而不是每个资源写一个 Controller。

> 慢半步入口
> 快一整条链
> 少一层特例
> 多一层可信

# 09、洞见

## 9.1 控制台是后端契约的第一次真正验收

前面十四境里，接口的消费者只有 curl 和我本人。curl 不会抱怨返回体带明文密钥，不会抱怨列表不分页，不会抱怨错误体只有一句 500。页面会。反直觉判断：把控制台当成前端任务，会得到一个漂亮的壳和一堆补不上的洞；把它当成接口契约的验收任务，才会得到一套能被别人使用的接口。本章拆下来的接线工作，八成发生在 Java 侧。

## 9.2 复用前端省下的不是时间，是判断力

重写一套前端，最贵的不是两周工时，而是你要重新决定布局、路由、权限、请求封装、错误提示这一整套约定。这些决定和网关的核心问题没有任何关系，却会消耗掉你最清醒的那部分注意力。所以复用骨架的价值不只是快，而是让你可以把判断力全部押在「接口契约」和「计量口径」这两个真正重要的问题上。边界必须写死：只新增文件，不动骨架。

## 9.3 Playground 不能有后门

反直觉判断：Playground 看起来是最不需要工程严谨的地方——它只是一个随手试试的框。恰恰相反，它是唯一一个把「配置是否正确」直接展示给人看的地方。如果它走的是另一条路，那么它验证的就不是线上链路，只是一个看起来很像的替身。一旦有人根据它下结论「模型接好了」，线上出问题时，你会先怀疑自己，再怀疑上游，最后才发现怀疑错了对象。

## 9.4 观测数据的可读性来自结构化，不来自更漂亮的图表

日志详情页真正要回答的问题是：这次请求为什么走了这个 deployment，前面几次尝试为什么失败。要回答它，RuntimeContext 和 RouteAttempts 必须以结构化字段返回，而不是一行大字符串。图表能让数据好看，结构化才能让数据可用。同理，Prompt 默认不落库不是数据缺失，是一个需要被显式告知的策略选择，页面上必须说清楚，否则下次来排查的人会先怀疑自己的查询。

> 契约先于界面
> 复用先于重写
> 通道必须唯一
> 结构胜于图画

# 10、系统落地

原来有什么：一套从 Demo 换骨而来的 Java 网关，具备协议兼容、Pipeline、多 Provider 适配、路由、失败轮转与熔断恢复、Key 与限额、配置持久化、统一 Usage 与 Cost 计量。它们都能用，但入口只有命令行。

本篇新增了什么：一套复用既有前端骨架的中文控制台，包含最小 Admin 登录与 RBAC、Dashboard 聚合接口、菜单与页面接线方式、Playground 走主链路的验证入口，以及日志详情需要的结构化返回。十一个入口里，Dashboard、系统、Playground 的骨架在本篇立起来，其余页面沿用同一套接线方式增量补齐。

现在能做什么：管理员可以在页面上登录、看请求数、Token、Cost、成功率、P95 与 Provider 健康，可以在 Playground 里带 key、model、system、user、temperature、max_tokens、stream 发一次真实对话，并看到 provider、deployment、tokens、cost、latency、TTFT。这一次调用会真实入账、真实出现在日志里。

还缺什么：Provider、模型、Deployment、路由、Project、VirtualKey、日志、Usage 这八个页面的完整表单与校验还没做完；管理接口还是逐个手写的，重复度高；审计日志（谁在什么时候改了哪条配置）还没有；前端没有国际化与暗色主题的统一处理。

下一步如何演进：先补齐这八个页面的表单与唯一性校验，让「Provider 到 Model 到 Route 到 Key 到 Playground」全部可以在页面上完成；再把重复的 CRUD 抽象成通用资源描述；然后才是可观测与高级策略的融合——缓存、护栏、灰度与扩展策略，需要一个统一的策略编辑面，而不是散落在各个页面角落里。最后是生产化：多实例部署、共享状态、滚动升级与回滚，都需要管理面给出明确的操作入口与状态反馈。

> 先立一根骨
> 再铺十个面
> 面面有回响
> 方称控制台

# 12、作业

## 12.1 理解题：为什么说控制台开发量的七成在后端？

参考答案：因为页面是接口的第一个非开发者消费者。列表需要分页与过滤，详情需要脱敏，更新需要校验与幂等，动作需要明确的状态码与错误体，而这些在只有 curl 的场景里统统可以省略。每加一个页面，通常要补列表、详情、更新、动作四类接口，工作量自然落在 Java 侧。

## 12.2 实战题：给菜单新增一个「日志」入口，并让日志列表支持按 requestId 精确查询。

参考答案：前端只在既有菜单数组里追加一项，路径指向新建的日志页面；页面里放一个输入框与查询按钮，调用 admin 侧新增的日志查询接口。后端接口接收 requestId 作为必填参数，直接走唯一索引查询单条记录，返回结构化字段。注意不要在列表接口里返回 Prompt 原文，只返回 promptStored 标识。

## 12.3 排障题：Playground 里能看到回复，但日志页查不到这条调用，怎么排查？

参考答案：第一步确认请求是否真的走了 /v1/chat/completions，可以在控制台侧打点或看访问日志；第二步确认是否透传了 X-Request-Id，若没有透传，日志页无法定位；第三步确认这次调用的 VirtualKey 是否绑定了 Project，未绑定可能导致计量归属缺失；第四步检查 Usage 写入是否在同一事务或异步链路上失败。常见根因就是控制台侧存在一条绕开 Pipeline 的调试通道。

## 12.4 架构判断题：为了赶进度，先让 Playground 直连上游，等以后有空再改成走网关，这个顺序合理吗？

参考答案：不合理。直连方案会引入密钥下发到浏览器、跨域代理、绕过配额熔断计量这三个必须处理的问题，而且它会产出一批不可信的历史数据，让后续的对账失去基线。更关键的是，直连路径的失败模式与线上完全不同，用它排查线上问题会把人带偏。正确顺序是先打通「同一条链路」，再考虑页面美观与交互细节。

> 题在链上解
> 答在证中寻
> 顺序一颠倒
> 回头十倍功

# 13、思考

这一章的核心冲突其实只有一个：后端已经长出满身能力，却还没有一个能让别人使用的入口。面对这个问题，最自然的反应是「先写个前端」，最危险的反应是「为了前端好写，让后端开个小口」。

判断的标准可以浓缩成一句话：管理面上的每一个数字，都必须能在主链路上被复现。凡是不能在日志和 Usage 里被找回的展示，都不是观测，是装饰。

这条标准同样适用于后面的路。可观测、高级策略、灰度发布、多实例调度，每一层增强都会顺手提供一些「更方便」的捷径，而每一次走捷径，都会让管理面离真实系统更远一点。真正让控制台立住的，从来不是页面有多全，而是它说的每一句话，后台都能对得上账。

> 界面是表象
> 契约是骨相
> 主链一口径
> 管理方可信
