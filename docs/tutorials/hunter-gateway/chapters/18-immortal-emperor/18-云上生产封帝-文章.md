# 仙帝境·他化自在法：Java LLM Gateway 的 Kubernetes 生产化闭环

> 单机跑通只证明功能，K8s 多副本才检验状态、连接与升级边界。

```text
[读者] 后端与架构师，已把 LLM Gateway 跑在单机 Docker
[痛点] 多 Pod 后限流预算错乱，SSE 断流，升级抖动
[现在读] 第18章要补齐生产化最后一环
[读完] 能把网关部署成可滚动、可恢复、可观测的 K8s 服务
```

```text
[旧方案] 单 Pod + 本地内存限流 + 手工重启
    |
    v
[新需求] 多副本、弹性扩缩、滚动升级、故障自愈
    |
    v
[冲突] 本地状态、SSE 长连接、Secret 和配置版本无法共享
    |
    v
[后果] 429 失真、预算超支、发布断流、回滚困难
```

我是老李。前面我们已经把 Java LLM Gateway 从 Demo 逆向、包名迁移、Provider 适配、Route 选择、Fallback、Usage/Cost 到中文控制台一路跑通。单 Pod 运行时，很多问题被掩盖了，因为所有请求、计数和配置都在同一个 JVM 里。

现在要把同一套网关推进 Kubernetes：多副本、HPA、滚动升级、Secret 外置、Redis 共享计数、配置版本同步。看起来只是把镜像换个地方跑，实际是系统性拆掉本地状态。

K8s 不会因为你写了 Deployment 就给你生产闭环。它会把本地内存、长连接、配置刷新、优雅下线的所有漏洞一次性暴露出来。

当网关从单 Pod 变成多 Pod，为什么本地内存限流和预算会先失真？

滚动升级时，SSE 长连接、在途请求和 Provider 故障为什么不能靠“重启一下”解决？

如果 Secret、配置版本、实例状态不能统一刷新，控制台凭什么让人相信生产可运维？

# 01、故事

我们先把现场摆出来。网关服务已经支持 OpenAI 兼容协议，外部客户端可以用 OpenAI SDK 指向我们的 `/v1/chat/completions`。内部有 `LogicalModel`、`Deployment`、`Provider` 三层模型，Route 负责选择 Deployment，Fallback 负责失败轮转，Usage/Cost 负责计量，Console 负责管理。

单机阶段，我们用 Docker 直接跑一个容器，RateLimit 和 Budget 计数放在 JVM 本地 Map，配置快照放在本地内存，Provider Secret 写在环境变量里。所有请求都打到同一个进程，SSE 也由同一个进程维持。功能验收没问题，全链也能闭环。

任务是：在不改坏 OpenAI 兼容协议和已有管理页面的前提下，把网关部署到 Kubernetes，并支持多副本、滚动升级、Pod 恢复、HPA、主 Provider 故障和 Redis 共享计数。最终验收仍然要求 OpenAI SDK 到 Key、LogicalModel、Route、Provider、Fallback、Usage/Cost、Console、K8s 全链闭环。

变化来了：副本从 1 变 N，Pod 随时会被重建；Service 背后 Endpoint 会变化；HPA 会在压测和长尾时扩缩；Secret 不再只躺在环境变量里；配置快照需要版本化并同步刷新。

冲突也随之出现。本地限流在多 Pod 下各算各的，预算会重复扣减；SSE 长连接在滚动升级时会被直接切断；Provider Secret 更新后，不同 Pod 可能读到不同版本；Pod 被终止时，如果没有优雅下线，正在生成的 Token 会丢。

此时真正的问题不是“怎么把镜像塞进 K8s”，而是“哪些状态必须离开 JVM，哪些边界必须由平台控制”。

> 一路跑通易
> 多副本难藏
> 状态一离身
> 故障自现形

# 02、问题

旧方案失效的第一个表现，是限流和预算失真。单 Pod 时，本地 `ConcurrentHashMap` 可以准确统计每个 VirtualKey 的 RPM、TPM 和预算消耗。多 Pod 后，每个 Pod 都维护自己的计数器，同一个 Key 的请求被负载均衡到不同 Pod，实际放行量会在副本数上叠加。用户看到的 429 忽多忽少，预算扣减也可能超过预期。

第二个表现，是滚动升级时 SSE 断流。LLM 请求经常是流式输出，一个 SSE 连接可能持续几十秒甚至更久。K8s 滚动升级默认会终止旧 Pod，如果进程收到 SIGTERM 后立即退出，客户端会看到连接中断。即使加了 `terminationGracePeriodSeconds`，如果 Service Endpoint 没有先摘除，新流量仍可能进入正在关闭的 Pod。

第三个表现，是配置与 Secret 版本漂移。Provider Secret 进入 K8s Secret 后，更新 Secret 并不会自动让 JVM 重新读取；ConfigMap 挂载到容器后，文件更新也有延迟，而且不同 Pod 的本地缓存可能处于不同版本。控制台显示“已更新”，但部分 Pod 仍在使用旧 Provider Key，故障时很难定位。

业务影响很直接：限流不准会导致恶意流量或成本超支；SSE 断流会破坏用户体验；Secret 漂移会让主 Provider 故障切换失效；滚动升级不可控会让发布变成高风险操作。

完成标准必须可验证：OpenAI SDK 能通过 Ingress 访问网关；多 Pod 下 RateLimit 和 Budget 使用 Redis 共享计数；滚动升级期间 SSE 连接不被硬切；Pod 被删除后能自动恢复；HPA 能基于指标扩缩；主 Provider 故障时 Fallback 生效；Console 能看到版本、实例状态、配置版本和依赖健康。

这些标准不是“跑起来”就结束，而是要求每个副本都可被替换，每个状态都可被重建，每个请求都可被追踪。

> 问题不在镜
> 而在本地态
> 计数一分散
> 账单先失真

# 03、原理

本篇只需要一个核心原理：K8s 里的 Pod 是临时执行者，不是长期宿主。任何只存在于 JVM 内存中的状态，都会在 Pod 被重建、扩缩或滚动升级时消失或被复制。因此，生产化网关必须把状态分成三类：可丢失的请求上下文、必须共享的治理状态、必须版本化的配置状态。

第一类是可丢失的请求上下文，比如单次请求的 TraceID、临时缓冲。它们可以留在内存，因为请求结束就结束。第二类必须共享，比如 RateLimit、Budget、并发计数、熔断状态、SSE 连接注册。它们要进入 Redis 或其他共享存储，并具备原子操作和 TTL。第三类必须版本化，比如 Provider Secret、Route 规则、模型配置、开关。它们要进入 ConfigMap、Secret、DB 或配置中心，并用 `configVersion` 驱动刷新。

这里有一个反直觉判断：K8s 的副本不是“多个相同进程”，而是“多个随时会被替换的临时执行者”。所以你不能把副本当成稳定节点来设计，而要把每次请求当成可能落在任意新 Pod 上。任何“这个 Pod 知道”的状态，都必须能被其他 Pod 或下一次重建后的 Pod 重建。

第二个反直觉判断：优雅下线不是把 `terminationGracePeriodSeconds` 调大就行。真正顺序是先从 Service Endpoint 摘除，让新流量不再进入；然后通知应用停止接收新请求；再等待在途请求和 SSE 连接排空；最后进程退出。如果顺序错了，长连接仍会被切断。

理解了这两点，后面的 Docker 多阶段、非 root、JVM 容器参数、readiness/liveness、Redis 共享计数、configVersion 刷新和 Secret 外置，都不是零散配置，而是同一原则的不同投影：让临时执行者可替换，让共享状态可重建，让配置版本可追踪。

> 副本非宿主
> 临时即常态
> 状态先外置
> 下线才从容

# 04、架构

```text
[输入] OpenAI SDK 请求 / SSE
    |
    v
[模块] Ingress -> Service -> Gateway Pod
    |
    v
[数据/状态] Redis 共享计数 + DB 配置快照 + K8s Secret
    |
    v
[处理] 鉴权 -> RateLimit/Budget -> Route -> Provider -> Fallback
    |
    v
[输出] SSE 响应 + Usage/Cost + Console 状态
```

这个架构里，Ingress 负责入口和 TLS，Service 负责把流量分发给 Ready 的 Pod，Deployment 负责副本和滚动升级。ConfigMap 放非敏感配置，Secret 放 Provider Key 和数据库密码。Redis 承担跨 Pod 的 RateLimit、Budget、熔断和连接注册。DB 或配置中心保存配置快照和 `configVersion`。Console 展示版本、实例状态、配置版本和依赖健康。

边界很清楚：Redis 不是数据库，只承担高频共享计数和短 TTL 状态；K8s Secret 不是配置中心，只负责敏感值分发；ConfigMap 不是热更新神器，应用仍要通过 `configVersion` 或轮询确认刷新。Provider Secret 可以进入 K8s Secret，也可以接外部 Secret Manager，但最终都要通过统一配置版本进入应用。

收益是网关从单点变成可替换副本，滚动升级和故障恢复成为常态操作。代价是引入 Redis、配置版本和更复杂的部署描述，排障链路变长。适用条件是团队已经能稳定运行 Redis 或托管 Redis，并能接受最终一致性或短时间配置延迟。如果仍是单副本小流量，可以先用最小 K8s 部署，但不要保留本地限流作为长期方案。

> 入口有秩序
> 状态有归属
> 版本可追踪
> 副本可替换

# 05、实战一次

环境与版本：JDK 17、Spring Boot 3.x 或现有 Demo 框架、Docker、Kubernetes 1.28+、Redis 7.x、Nginx Ingress 或云厂商 Ingress。以下未在当前环境实测，以下为预期结果，示例输出仅用于说明验证路径。

先做 Docker 多阶段、非 root、JVM 容器参数和优雅下线。

```dockerfile
FROM eclipse-temurin:17-jdk AS builder
WORKDIR /build
COPY . .
RUN ./mvnw -q -DskipTests package

FROM eclipse-temurin:17-jre
RUN useradd -r -u 10001 gateway
WORKDIR /app
COPY --from=builder /build/target/gateway.jar /app/gateway.jar
USER 10001
EXPOSE 8080
ENTRYPOINT java -XX:MaxRAMPercentage=75.0 -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError -Djava.security.egd=file:/dev/./urandom -jar /app/gateway.jar
```

JVM 参数要跟 `requests/limits` 配合。容器内存限制 2Gi 时，`MaxRAMPercentage=75` 给堆留约 1.5Gi，剩下给元空间、线程栈、DirectByteBuffer 和 JVM 自身。不要写死 `-Xmx` 超过 limit，否则 OOMKilled 会先于 Java OOM 出现。优雅下线要在应用里监听 SIGTERM，停止接收新请求，等待在途请求和 SSE 排空。

```java
@Component
public class GracefulShutdown implements ApplicationListener<ContextClosedEvent> {
    private final AtomicBoolean shuttingDown = new AtomicBoolean(false);

    public boolean isShuttingDown() {
        return shuttingDown.get();
    }

    @Override
    public void onApplicationEvent(ContextClosedEvent event) {
        shuttingDown.set(true);
    }
}
```

# 06、排查

第一条诊断链：多 Pod 后 429 不稳定，预算偶尔超扣。现象：单 Pod 压测正常，扩展到 3 个 Pod 后，同一个 VirtualKey 的 RPM 统计明显偏低，预算消耗也低于预期。怀疑：Redis 连接有问题，或者限流 Key 不一致。检查：查看应用日志、Redis `KEYS ratelimit:*`、以及每个 Pod 的本地指标。证据：Redis 中只有少量 Key，应用日志显示每个 Pod 仍在用本地 `ConcurrentHashMap` 计数。根因：RateLimit/Budget 迁移只改了配置开关，没有把实际计数路径切到 Redis，或者部分接口仍走本地缓存。修复：统一限流入口，所有 RateLimit 和 Budget 判断先走 Redis Lua 原子脚本，并给 Key 加 TTL。

**错误尝试：** 一开始把 `replicas` 调回 1，认为“多副本不稳定就先单副本”。这错在把生产问题掩盖成部署问题，单副本会失去高可用和滚动升级能力，而且 429 失真根因仍在本地状态。

第二条诊断链：滚动升级时 SSE 长连接被切断。现象：客户端流式输出到一半收到连接关闭。怀疑：Ingress 超时太短。检查：查看 Ingress `proxy-read-timeout`、Pod 事件、应用关闭日志和 Endpoint 变化。证据：Pod 收到 SIGTERM 后立刻退出，Service Endpoint 尚未摘除，`preStop` 只有默认或没有等待。根因：没有先摘流再排空，`terminationGracePeriodSeconds` 被当成唯一手段。修复：readiness 在关闭时先失败，`preStop` 等待 Endpoint 摘除，应用停止接收新请求并等待 SSE 和在途请求完成。

第三条诊断链：Provider Secret 更新后，部分 Pod 仍用旧 Key。现象：Console 显示配置版本已更新，但主 Provider 故障切换时，某些 Pod 报鉴权失败。怀疑：K8s Secret 更新没有生效。检查：对比 Pod 内挂载文件、环境变量、Redis 中的 `configVersion` 和应用健康页。证据：不同 Pod 的 `configVersion` 不一致，部分 Pod 仍缓存旧配置。根因：Secret 更新后没有统一刷新机制，应用只在启动时读取一次。修复：为配置增加 `configVersion`，通过 Redis Pub/Sub 或定时轮询触发刷新；Provider Secret 进入 K8s Secret 或外部 Secret Manager，并统一由配置版本驱动。

> 现象先分层
> 证据再说话
> 根因不绕开
> 修复才闭环

# 07、优化

基于第 06 章证据，V2 要做三件事。

第一，RateLimit 与 Budget 全量迁移 Redis。根因是本地计数在多 Pod 下失去全局性。修改方式是把 RPM、TPM、预算扣减、并发计数统一封装为共享计数器，使用 Lua 脚本保证原子性，并为窗口 Key 设置 TTL。原因是 Redis 单线程执行 Lua，可以避免“读-改-写”竞态。新行为是任意 Pod 都能看到同一份计数，Pod 重启不会丢失窗口内状态。验证方式是在多 Pod 下用同一 VirtualKey 并发请求，观察 429 是否按全局阈值出现，预算扣减是否一致。这里不写具体 QPS 数字，需按当前环境压测核验。

第二，优雅下线顺序固化。根因是 Pod 终止时 Endpoint 摘除、连接排空和进程退出没有形成顺序。修改方式是 readiness 探针在关闭阶段失败，`preStop` 等待摘流，应用收到 SIGTERM 后停止接收新请求，并等待在途请求和 SSE 完成。原因是 K8s 终止流程与 Endpoint 更新是异步的。新行为是滚动升级时新 Pod Ready 后旧 Pod 才退出，长连接尽量自然结束。验证方式是发起长 SSE 请求，同时执行 `kubectl rollout restart deployment/llm-gateway`，观察客户端是否在合理宽限期内完成或收到可控错误。

第三，配置版本统一。根因是 Secret、ConfigMap 和应用缓存没有统一版本。修改方式是引入 `configVersion`，DB 或 Redis 保存当前版本，应用定时轮询或订阅变更，刷新 Provider Secret、Route 和模型配置。原因是不同 Pod 的本地缓存无法依赖文件挂载时间保持一致。新行为是 Console 能显示每个实例的配置版本，依赖健康页能看到 Redis、DB 和 Provider 状态。验证方式是更新 Secret 并提升 `configVersion`，观察所有 Pod 在预期时间内切到新版本。

> 共享先原子
> 下线先摘流
> 配置先版本
> 扩容才无忧

# 08、演进

```text
[同一输入]
    |
    +--[V1] 多副本 + 本地限流 + 直接终止 / 代价：429 失真、SSE 断流、配置漂移
    |
    +--[V2] Redis 共享计数 + 优雅下线 + configVersion / 代价：引入 Redis 与刷新复杂度
    |
[Trade-off]
得到可替换副本与可追踪配置，失去本地状态的简单性，适用于多 Pod 与滚动升级场景
```

正确性上，V1 在单 Pod 可用，多 Pod 不再正确；V2 把治理状态外置后，全局语义恢复。稳定性上，V1 依赖 Pod 不重启，V2 接受 Pod 随时重建，但引入 Redis 依赖。复杂度上，V2 多了 Redis、Lua、配置版本、健康探针和 Ingress 超时配置。成本上，V2 需要 Redis 或托管 Redis，以及更多可观测指标。适用范围上，小流量单副本可以暂缓，但只要目标包含高可用、HPA 或滚动升级，就必须走 V2。

遗留问题也很明确：HPA 指标如何选，是按 CPU 还是按并发 SSE 连接数；Redis 故障时 RateLimit 是放行还是拒绝；外部 Secret Manager 的轮换周期如何与 `configVersion` 对齐；SSE 在 Ingress 和负载均衡上的超时如何与业务最长生成时间匹配。这些问题需要按当前官方文档和实际压测核验，不能凭感觉设参数。

# 09、洞见

## 9.1 副本数一变，本地状态就从优化变成负债

单 Pod 时，本地 Map 是性能优化；多 Pod 时，它变成语义错误。反直觉判断：不是 K8s 让系统变复杂，而是 K8s 把原本隐藏的本地状态假设暴露出来。只要网关承诺全局 RateLimit 和预算，计数就必须离开 JVM。

## 9.2 优雅下线是流程问题，不是参数问题

把 `terminationGracePeriodSeconds` 调大只争取时间，不保证顺序。反直觉判断：真正决定 SSE 是否断流的，不是宽限期长度，而是 Endpoint 摘除、停止接收、排空连接、进程退出是否按顺序发生。顺序错了，时间再长也会切流。

## 9.3 Secret 进入 K8s 不是终点，配置版本才是闭环

K8s Secret 解决敏感值分发，但不解决应用何时刷新、是否刷新一致。没有 `configVersion`，Console 显示的“已更新”可能只是控制面更新，数据面仍在旧版本。配置治理必须能回答：哪个实例，哪个版本，何时生效。

## 9.4 生产化验收要覆盖失败路径

正常请求跑通只证明 V1。真正的仙帝境验收要包含主 Provider 故障、Pod 删除、滚动升级、Redis 抖动、429 长尾和 SSE 超时。失败路径可恢复，才叫生产化。

# 12、作业

## 12.1 理解题：为什么多 Pod 后本地限流会失真？

参考答案：每个 Pod 有独立 JVM 内存，负载均衡会把同一 Key 的请求分散到不同 Pod，各自计数导致全局统计被放大或割裂。RateLimit 和 Budget 属于全局治理状态，必须迁移到 Redis 等共享存储，并用原子操作保证并发正确。

## 12.2 实战题：写一个 Redis Lua 限流脚本，并说明 TTL 的作用。

参考答案：脚本先 `INCR` 计数，若为 1 则 `PEXPIRE` 设置窗口；再判断是否超过阈值，超过返回 0，否则返回 1。TTL 保证窗口自动过期，避免 Key 无限增长，也让限流具备时间窗口语义。

## 12.3 排障题：滚动升级时 SSE 断流，应该先查什么？

参考答案：先查 Pod 终止流程和 Endpoint 变化。看 readiness 是否在关闭时先失败，`preStop` 是否等待摘流，应用是否在 SIGTERM 后停止接收新请求并排空 SSE。再看 Ingress 和负载均衡的读超时是否短于业务最长生成时间。不要只调大 `terminationGracePeriodSeconds`。

## 12.4 架构判断题：Provider Secret 放 K8s Secret 后，是否还需要 configVersion？

参考答案：需要。K8s Secret 解决分发，不解决应用刷新一致性和可观测性。configVersion 让控制面知道期望版本，让数据面知道当前版本，让 Console 能对比实例状态。没有版本，Secret 更新后无法判断哪些 Pod 已生效。

# 13、思考

回到本篇的核心冲突：单机网关的功能正确，如何变成 K8s 多副本的生产正确？答案不是加更多 YAML，而是承认 Pod 是临时执行者。凡是全局状态，必须共享；凡是长连接，必须有序下线；凡是配置和 Secret，必须版本化；凡是生产验收，必须覆盖失败路径。

可复用的工程判断是：先分清哪些状态可丢、哪些必须共享、哪些必须版本化；再决定它们放在 Redis、DB、K8s Secret 还是外部 Secret Manager；最后用 readiness/liveness、preStop、configVersion、HPA 和压测把边界固化。这样滚动升级、Pod 恢复和主 Provider 故障才不会把系统打回单机思维。
