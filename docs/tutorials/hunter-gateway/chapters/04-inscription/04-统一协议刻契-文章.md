我是老李，一直在做后端基础设施。手上的这套东西，底子是 litellmgateway 仓库里那份 open-api.zip Demo：分层是现成的，启动是现成的，模型调用链路也跑得通。

前面几境我们把这份 Demo 逆向清楚了，也把项目名、包名换成了自己的骨头。现在轮到最容易被跳过、却最不能跳过的一步：对外那层壳。

这层壳就是 OpenAI 兼容协议。它看起来只是几个 URL，实际上是整个网关的先天规则——后面所有路由、重试、熔断、计量、控制台，都要长在这套契约上面。契约松一寸，后面所有能力都要歪一尺。

问题来了：协议是照着某个上游抄，还是自己刻一套？

是先花两天把成功响应调通，还是先把错误结构和流式结束符定死？

如果这一步选错，后面到底会出现什么后果？

# 01、故事

我们这个小团队三个人，做的是一个内部 LLM 网关。上游不是一家：有公有云的大模型 API，也有公司内网自建的推理服务。模型换得勤，价格变得快，业务方今天要这个模型，明天要那个模型。

一开始的方案特别朴素：业务代码直接调上游 SDK，哪家便宜调哪家。后来上游一多，问题就来了——每接一家新上游，业务侧就要改一次代码、改一次 key、改一次错误处理。前端同学被逼着自己写一层适配，写到最后没人敢动。

于是我们决定做网关。做完逆向之后，本境的第一个任务是：把对外契约立成 OpenAI Compatible First。也就是说，业务方以后只认一套协议，换上游、换模型、换部署，他们只改 base_url 和 api_key。

变的是上游，不变的是客户端。

这个决定一下来，冲突马上就出现了。上游 A 的错误返回是 `{"code": 1001, "msg": "invalid key"}`，上游 B 是 `{"error": {"message": "...", "type": "..."}}`，上游 C 干脆返回 HTML 错误页。流式更乱：有的用 `data: [DONE]` 收尾，有的直接断开连接，有的每行还带 `event:` 前缀。

如果我只是把这三种东西原样透传出去，那所谓的“兼容”就只是兼容了其中一家。客户端换个模型就崩，这层壳等于白做。

# 02、问题

旧方案为什么失效？因为它是“管道思维”：把网关当成一根透明管子，上游给什么就吐什么。当上游只有一家的时候，这根管子没问题；上游变成三家、五家之后，管子就变成了随机数发生器。

业务影响很直接。前端接 OpenAI 官方 SDK，请求发到网关，返回的却是上游 A 的私有错误结构，SDK 抛出解析异常，前端只能兜底显示“服务异常”，用户看到的是一句没有信息量的话。灰度切流量的效率也被拖死——切一家上游，就要重新对一遍错误处理。

技术表现主要有四类：

第一，字段不对齐。上游返回 `max_output_tokens` 这类私有字段，SDK 拿不到 `usage`。

第二，错误不可机读。Spring 默认的 `{"timestamp":...,"status":401,"error":"Unauthorized","path":"..."}` 不是 OpenAI 错误结构，SDK 里的 `err.code` 是空的，业务侧没法按错误码做差异化重试。

第三，流式不可终止。有些上游最后不发 `[DONE]`，客户端会一直挂着等，直到超时。

第四，异常路径不可控。客户端 Ctrl+C 断开后，网关到上游的连接没被释放，线程慢慢堆积。

所以本境的完成标准必须是可验证的，不能是“看起来能用”三条：

一个上游接入后，`/v1/chat/completions` 同步调用返回标准 `chat.completion` 结构；同一接口 `stream:true` 时返回标准 `chat.completion.chunk` 分片，并且以 `data: [DONE]` 结束；`/v1/models` 能列出可用模型；`/v1/embeddings` 能返回标准向量结构；错误路径下，401、403、404、429、上游错误、超时、上下文超长七类情况都返回 OpenAI 形状的错误体；用官方 Python SDK 和 Java SDK 只改 `base_url` + `api_key` 即可调通，不改任何业务代码。

# 03、原理

OpenAI 兼容协议的本质不是一组 URL，而是三份契约的叠加：请求契约、响应契约、错误契约。而这三份里，被讨论最多的是请求契约，被写死最少的却是错误契约和流式结束契约。

反直觉判断：兼容层的第一优先级不是把成功响应做对，而是把失败响应和流结束做对。

原因在于，成功响应是“收敛的”——`choices[0].message.content` 就这么一个位置，各家上游都能映射过来，映射错了肉眼也能测出来。失败响应是“发散的”：HTTP 状态码、错误体结构、错误码语义、是否可重试，每家都不一样，而且只在异常路径上才暴露，测试时最容易被跳过。流式结束符更隐蔽——它是个“零宽度”的状态，正常结束时没人注意，一旦缺失就是客户端挂死。

第二个原理是：SSE 不是“分块的同步”，它是一个有状态机的小协议。一条完整的 SSE 事件是 `data: <payload>` 加一个空行；`[DONE]` 不是一个 JSON，而是一个哨兵。网关在流式场景里必须承担两个责任：保证每个分片都是合法 JSON 且结构一致；保证任何退出路径（正常结束、上游异常、客户端断开、上游超时）都能让客户端从流里出来。

第三个原理是错误边界必须“先收口再分发”。网关在收到上游错误时，不能直接把上游的语言抛给客户端，而要先把它翻译成自己的错误枚举，再由错误枚举统一序列化。这样做的代价是多一层映射，收益是错误码从此变成网关自己的资产——后面第 09 境的 Retry 才能按错误码判断“该不该重试”，而不是靠字符串匹配。

第四个原理是字段白名单。兼容不等于全量透传，而是“我承诺这些字段，其余的不保证”。上游新增字段不该自动出现在我们的响应里，否则客户端会依赖一个我们没有承诺过的行为。

# 04、架构

```text
[输入] POST /v1/chat/completions (同步或 stream:true)
    |
    v
[模块] OpenAiCompatController + Contract DTO + SseWriter + ErrorMapper
    |
    v
[数据/状态] 统一 DTO 对象 + SSE 分片状态(已发送/未结束) + 上游连接句柄
    |
    v
[处理] 校验 → 归一化 → 调用单一上游 → 响应整形 → 错误翻译
    |
    v
[输出] JSON 响应体 或 data: 分片序列 + data: [DONE] 或 OpenAI 形状错误
```

这条链路里，控制器只做两件事：判断是否流式、决定用哪条出口。真正的收敛发生在中间一层：所有来自上游的东西，无论同步还是流式，都必须过一遍归一化，才能发给客户端。

边界很清楚：本境只接一个上游，不做多上游路由，不做 key 管理，不做限流。这些留给后面几境。把契约层单独立起来的好处是，后面加路由和重试时，只需要改“归一化之前的输入源”，出口那一段完全不动。

收益是客户端可替换、错误可机读、流可终止。代价是多了一层 DTO 转换和一次对象序列化，以及必须为上游的每一次协议变化维护映射规则。

适用条件是：上游至少有一个是 OpenAI 兼容的，或者愿意被适配成 OpenAI 形状。如果上游返回的是完全私有协议且不肯改，那网关就得写一个更重的适配器，但出口契约依然不变。

SSE 写出器。注意 `[DONE]` 不走 JSON 序列化，它是哨兵：

```java
public final class SseWriter {
    private static final byte[] PREFIX = "data: ".getBytes(StandardCharsets.UTF_8);
    private static final byte[] SUFFIX = "\n\n".getBytes(StandardCharsets.UTF_8);
    private static final byte[] DONE = "data: [DONE]\n\n".getBytes(StandardCharsets.UTF_8);

    private final OutputStream out;
    private final ObjectMapper mapper;

    public SseWriter(OutputStream out, ObjectMapper mapper) {
        this.out = out;
        this.mapper = mapper;
    }

    public void send(Object payload) throws IOException {
        out.write(PREFIX);
        out.write(mapper.writeValueAsBytes(payload));
        out.write(SUFFIX);
        out.flush();
    }

    public void done() throws IOException {
        out.write(DONE);
        out.flush();
    }
}
```

控制器，一次性把三个端点立齐：

```java
@RestController
@RequestMapping("/v1")
public class OpenAiCompatController {

    private final ChatService chatService;
    private final ModelService modelService;
    private final EmbeddingService embeddingService;

    public OpenAiCompatController(ChatService chatService,
                                  ModelService modelService,
                                  EmbeddingService embeddingService) {
        this.chatService = chatService;
        this.modelService = modelService;
        this.embeddingService = embeddingService;
    }

    @PostMapping("/chat/completions")
    public void chatCompletions(@RequestBody ChatCompletionRequest request,
                                HttpServletResponse response) throws IOException {
        if (Boolean.TRUE.equals(request.stream())) {
            response.setStatus(HttpServletResponse.SC_OK);
            response.setContentType("text/event-stream;charset=UTF-8");
            response.setHeader("Cache-Control", "no-cache");
            response.setHeader("Connection", "keep-alive");
            chatService.stream(request, new SseWriter(response.getOutputStream(), Json.MAPPER));
            return;
        }
        ChatCompletionResponse body = chatService.complete(request);
        response.setStatus(HttpServletResponse.SC_OK);
        response.setContentType("application/json;charset=UTF-8");
        response.getOutputStream().write(Json.MAPPER.writeValueAsBytes(body));
        response.getOutputStream().flush();
    }

    @GetMapping("/models")
    public ModelList models() {
        return modelService.list();
    }

    @PostMapping("/embeddings")
    public EmbeddingResponse embeddings(@RequestBody EmbeddingRequest request) {
        return embeddingService.embed(request);
    }
}
```

ChatService 的流式路径。这里 `LineHandler` 是自定义函数式接口，允许抛 `IOException`，方便在断连时向上传递：

```java
@Service
public class ChatService {

    private final UpstreamClient upstream;

    public ChatService(UpstreamClient upstream) {
        this.upstream = upstream;
    }

    public ChatCompletionResponse complete(ChatCompletionRequest request) {
        String raw = upstream.postJson("/chat/completions", request);
        return ContractNormalizer.normalize(Json.read(raw, ChatCompletionResponse.class));
    }

    public void stream(ChatCompletionRequest request, SseWriter writer) throws IOException {
        try {
            upstream.streamLines("/chat/completions", request, line -> {
                if (line.isEmpty() || !line.startsWith("data:")) {
                    return true;
                }
                String payload = line.substring(5).trim();
                if ("[DONE]".equals(payload)) {
                    return false;
                }
                writer.send(ContractNormalizer.normalize(Json.read(payload, ChatCompletionChunk.class)));
                return true;
            });
            writer.done();
        } catch (IOException clientGone) {
            throw clientGone;
        }
    }
}
```

上游客户端用 JDK 自带 `HttpClient`，不引入额外 SDK，保证换骨后依赖最小：

```java
@Component
public class UpstreamClient {

    private final HttpClient http = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(5))
            .build();
    private final GatewayProperties props;

    public UpstreamClient(GatewayProperties props) {
        this.props = props;
    }

    public String postJson(String path, Object body) {
        try {
            HttpRequest req = HttpRequest.newBuilder(URI.create(props.upstream().baseUrl() + path))
                    .timeout(Duration.ofMillis(props.upstream().readTimeoutMs()))
                    .header("Content-Type", "application/json")
                    .header("Authorization", "Bearer " + props.upstream().apiKey())
                    .POST(HttpRequest.BodyPublishers.ofString(Json.write(body)))
                    .build();
            HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
            if (resp.statusCode() >= 400) {
                throw GatewayException.fromUpstream(resp.statusCode(), resp.body());
            }
            return resp.body();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new GatewayException(GatewayErrorCode.UPSTREAM_ERROR, "interrupted");
        } catch (IOException e) {
            throw new GatewayException(GatewayErrorCode.UPSTREAM_ERROR, e.getMessage());
        }
    }

    public void streamLines(String path, Object body, LineHandler handler) throws IOException {
        HttpRequest req = HttpRequest.newBuilder(URI.create(props.upstream().baseUrl() + path))
                .header("Content-Type", "application/json")
                .header("Authorization", "Bearer " + props.upstream().apiKey())
                .POST(HttpRequest.BodyPublishers.ofString(Json.write(body)))
                .build();
        HttpResponse<InputStream> resp;
        try {
            resp = http.send(req, HttpResponse.BodyHandlers.ofInputStream());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new GatewayException(GatewayErrorCode.UPSTREAM_ERROR, "interrupted");
        }
        try (InputStream in = resp.body()) {
            if (resp.statusCode() >= 400) {
                throw GatewayException.fromUpstream(resp.statusCode(),
                        new String(in.readAllBytes(), StandardCharsets.UTF_8));
            }
            BufferedReader reader = new BufferedReader(new InputStreamReader(in, StandardCharsets.UTF_8));
            String line;
            while ((line = reader.readLine()) != null) {
                if (!handler.onLine(line)) {
                    break;
                }
            }
        }
    }
}
```

```java
public enum GatewayErrorCode {
    INVALID_API_KEY(401, "invalid_request_error", "invalid_api_key"),
    PERMISSION_DENIED(403, "invalid_request_error", "permission_denied"),
    MODEL_NOT_FOUND(404, "invalid_request_error", "model_not_found"),
    INVALID_REQUEST(400, "invalid_request_error", "invalid_request"),
    CONTEXT_LENGTH_EXCEEDED(400, "invalid_request_error", "context_length_exceeded"),
    RATE_LIMITED(429, "rate_limit_error", "rate_limit_exceeded"),
    UPSTREAM_ERROR(502, "api_error", "upstream_error"),
    UPSTREAM_TIMEOUT(504, "api_error", "upstream_timeout");

    public final int httpStatus;
    public final String type;
    public final String code;

    GatewayErrorCode(int httpStatus, String type, String code) {
        this.httpStatus = httpStatus;
        this.type = type;
        this.code = code;
    }
}

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(GatewayException.class)
    public ResponseEntity<ApiError> handleGateway(GatewayException e) {
        GatewayErrorCode c = e.code();
        return ResponseEntity.status(c.httpStatus)
                .body(new ApiError(new ApiError.ErrorBody(e.getMessage(), c.type, null, c.code)));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleOthers(Exception e) {
        return ResponseEntity.status(500)
                .body(new ApiError(new ApiError.ErrorBody("internal error", "api_error", null, "internal_error")));
    }
}
```

# 06、排查

**诊断链一：401 时客户端拿不到可机读的错误码。**

现象：上游 key 配错，业务方用 Python SDK 调 `/v1/chat/completions`，SDK 抛出异常，但 `err.code` 是 `None`，`err.type` 也是 `None`，前端只能显示“服务异常”。

怀疑：SDK 版本太老，解析能力不够。

检查：用 `curl -i` 直接打同一个请求，看原始响应体。

证据：响应体是 `{"timestamp":"...","status":401,"error":"Unauthorized","path":"/v1/chat/completions"}`，这是 Spring 的默认错误页结构，不是 OpenAI 结构。同时服务端日志里没有任何 `GlobalExceptionHandler` 命中记录。

根因：Demo 原骨架的错误处理是面向页面/默认 JSON 的，没有面向 API 的错误序列化层。上游返回的 401 被包装成 `GatewayException` 抛出后，落到了框架默认处理器手里，`code` 字段在传输过程中丢失。

**错误尝试：** 一开始去升级 openai SDK 到最新版。这是错的，因为 SDK 只是按契约解析，服务端不符合契约，换解析器不会改变解析结果；升级只会掩盖问题，让排查方向偏到依赖版本上。

修复：新增 `GlobalExceptionHandler`，把 `GatewayException` 按 `GatewayErrorCode` 映射成 `{"error":{"message","type","param","code"}}`，并保证 401/403/404/429/502/504 六条路径全部走同一个出口。

**诊断链二：流式调用内容正常，但客户端一直不结束。**

现象：`stream:true` 时，Python SDK 能把内容打印出来，但迭代器不退出，直到客户端超时终止。

怀疑：上游太慢，最后一个分片迟迟不来。

检查：在 `UpstreamClient.streamLines` 里为每一行打上行号与时间戳，同时记录上游返回 `[DONE]` 的时刻。

证据：日志显示上游在正常时间点发了 `data: [DONE]`，我们的读循环也读到了；但客户端侧抓包看到的最后一条是内容分片，没有任何结束标记。

根因：流式循环在遇到 `[DONE]` 时直接 `break`，只把内容分片转发出去，没有把自己的结束标记写给客户端。等于把自己当成透明管道，放弃了“结束状态”的所有权。

修复：把结束责任收归网关——流正常结束时由 `SseWriter.done()` 写 `data: [DONE]`；上游异常结束时也写一次再关闭连接。上游发不发结束符，从此与客户端无关。

**诊断链三：客户端断开后，网关线程数持续上升。**

现象：压测脚本中途 Ctrl+C，网关的 `http-nio-8080-exec-*` 线程活动数不下降，几分钟后新请求开始变慢。

怀疑：上游服务出了问题，请求被阻塞。

检查：`jstack` 抓线程栈，同时在 `ChatService.stream` 的 `finally` 里打日志。

证据：多个线程栈停在 `socketRead0`，且这些线程对应的请求，客户端早已断开；日志显示 `finally` 没有执行到上游连接关闭那一步。

根因：客户端断开触发的是写响应的 `IOException`，异常从 `SseWriter.send` 抛出后一路向上，`UpstreamClient` 的 `try-with-resources` 已经失效——因为异常发生在读循环的回调内部，而 `InputStream` 的关闭依赖于读循环正常退出。

修复：把上游连接的关闭放在读循环外层的 `try-with-resources` 中，并在回调抛 `IOException` 时立刻跳出循环，让资源释放动作统一发生。

> 现象会骗人
> 证据不会骗
> 先抓原始包
> 再定根因处

# 07、优化

三个根因指向同一件事：V1 里缺一个稳定的“契约出口”。所以 V2 不是打三个补丁，而是把出口收成一处。

修改一：错误枚举统一收口。

根因：错误映射散落在 Service 与控制器里，每条路径都可能漏字段。修改：所有上游错误先在 `GatewayException.fromUpstream` 里翻译成 `GatewayErrorCode`，再由唯一的 `GlobalExceptionHandler` 输出。为什么这样做：错误码是网关自己的资产，不是上游的字符串，后面重试策略要按它判断是否可重试。新行为：任何错误路径返回的响应体结构完全一致。验证方案：构造 401、403、404、429、上游 5xx、上游超时、上下文超长七种输入，逐一对比响应体字段名与 `code` 取值。

修改二：流结束责任归网关。

根因：V1 的 `break` 只终止了读循环，没有终止客户端视角的流。修改：在 `ChatService.stream` 正常结束与异常结束两条路径上都调用 `SseWriter.done()`，并用 `finally` 保证只写一次。为什么这样做：`[DONE]` 是协议的一部分，不是上游的可选行为。新行为：无论上游是否发送结束符，客户端总能收到 `data: [DONE]`。验证方案：用两个上游分别测试，一个发 `[DONE]`、一个不发，客户端行为应当一致。

修改三：断连即断上游。

根因：异常从回调里抛出时，上游连接没有被及时释放。修改：`UpstreamClient.streamLines` 用 `try-with-resources` 包住 `InputStream`，回调抛 `IOException` 时立即跳出循环并关闭。为什么这样做：网关的资源生命周期必须以客户端为准，客户端走了，上游连接就没有存在意义。新行为：客户端断开后，上游连接在毫秒级被释放，线程不再堆积。验证方案：循环发起 100 次流式请求并在中途断开，观察线程数与上游连接数是否回到基线（未在当前环境实测，此处只给验证方案）。

> 根因既已现
> 补丁要成面
> 三处一起改
> 才算真收敛

# 08、演进

```text
[同一输入]
    |
    +--[V1] 透传上游响应 / 代价：错误结构不可控、流结束依赖上游
    |
    +--[V2] 网关自持契约 / 代价：多一层 DTO 转换与状态维护
    |
[Trade-off]
{得到：SDK 可替换、错误可机读、流结束确定 / 失去：上游新字段不会自动生效 / 边界：字段白名单需随协议版本演进}
```

正确性上，V1 只在“上游恰好是 OpenAI 兼容且行为规范”时正确；V2 在协议层面正确，与上游是否规范解耦。

稳定性上，V1 的流式路径依赖上游发结束符和上游不超时，任何一个变量抖动都会传到客户端；V2 由网关兜底，异常路径也被显式覆盖。

复杂度上，V2 多了一层契约 DTO 与一次序列化，代码量增加约一个包，但这层是“一次性成本”，后面加路由、重试、计量时都能复用同一个出口。

成本上，V2 每次流式分片多一次 JSON 解析与序列化。对短文本场景可以忽略；对高频长文本场景需要关注，可在后续用字节级透传做优化，但那会牺牲字段白名单的稳定性。

适用范围上，V2 适合“上游多变、客户端固定”的网关场景；如果是单上游单客户端的直连场景，V1 更省事。

遗留问题有三个：没有鉴权与 key 管理，任何人拿到地址就能用；没有路由，模型名是写死的；没有计量，`usage` 只是原样带过来，没有聚合。这三个分别属于第 11 境、第 07 境、第 14 境。

> 旧法省一层
> 新法多一转
> 一转买安心
> 取舍自分明

# 09、洞见

## 9.1 兼容层的定位是收敛，不是转发

反直觉判断：一个网关的兼容层写得对不对，不看它能不能调通官方 SDK，而看它能不能在没有上游配合的情况下，稳定输出一套协议。

转发只需要一个 `proxy_pass`，收敛需要 DTO、错误映射、状态机三件东西。前者做起来快，但把不确定性全部留给了客户端；后者做起来慢，但把不确定性关在了网关内部。当上游只有一家时，转发确实够用；当上游开始变多时，每一家上游都是一个新的不确定性来源，网关不收敛，客户端就得收敛——而客户端往往是改不动的那一端。

## 9.2 先定错误与结束符，再定成功响应

反直觉判断：接口设计的顺序应该是“先定失败，后定成功”。

成功响应是收敛的，映射错了能立刻发现；错误响应是发散的，只有在异常路径才出现，测试最容易漏。流式结束符更极端，它是零宽度的状态，缺了不会报错，只会让客户端挂死。把这三样先定死，后面的重试、降级、告警才有统一的输入。错误码一旦成为网关自己的枚举，第 09 境的 Retry 就只需要判断一个枚举值，而不是去匹配上游的字符串。

## 9.3 流式协议的解耦点，在于谁是结束的发起者

V1 把结束权交给了上游，于是上游的每一个“不规范”都变成了客户端的故障。V2 把结束权收归网关，上游从此只是分片的生产者，不再是流的终结者。

这个判断可以复用到所有流式系统：WebSocket、gRPC streaming、消息推送，凡是“服务端流”，都要明确谁是结束的发起者。发起者如果是外部依赖，你的系统就没有稳定的完成语义。
