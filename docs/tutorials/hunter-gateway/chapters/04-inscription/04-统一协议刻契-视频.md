第四章只干一件事：先把外部契约刻死。上苍之手就是规则先于实现，谁负责？
客户不关心内部怎么分层。他只改 base_url 和 api_key 就要能跑通，这句不成立，第四章白做。
一线最怕流式断在半路却没有任何提示。客户端断开、chunk 丢尾、上游超时，这些才是天天挨骂的地方。
我扒了主流 SDK 源码和文档：OpenAI 兼容已经是事实标准，但 tool_calls 和 usage 各家有差异，靠猜必错。
一期只做三个接口：chat/completions、models、embeddings。Playground 只做最小文本调用，多模态不做。
两个候选：一是重造骨架再包一层，二是逆向 Demo、改包名、在现有代码上增量刻契约。我推荐第二个。
流式最难的不是发 chunk，是客户端断开、[DONE] 丢失、上游超时。这些不定清楚，代码里全是坑。
别说已经兼容了。基线是零：官方 SDK 跑通同步和流式，成功率不到百分之九十五不算过。
开发者搜的是 openai compatible gateway java。错误码和接入文档写不清，搜索进来的人也留不住。
这一章我不投付费。开发者工具靠文档和 GitHub 自然扩散，CAC 算不过来，预算留到下一章再用。
逆向 Demo 不加人、不加机器，三周两个人力，上限六万。超过这条线，投入产出就不成立了。
兼容不等于冒用。接口命名和错误文案不能暗示官方背书；日志留哪些字段，要有授权依据和删除路径。
门排好了：契约冻结是人工门，SDK 兼容测试是自动门。第一棒 Bob 出契约，Alex 接实现，谁卡住谁上报。
最终取舍：DTO 严格按 OpenAI 字段输出，内部模型不许泄漏到响应体。牺牲内部自由度，换客户端零改造。
路径定了：DTO 独立包，SSE 用状态机收尾，客户端断开就取消上游。第一轮那三个失败场景我全部写成测试。
听完 Bob 的取舍和 Alex 的工期，我收紧范围：embeddings 只做透传，不做批处理优化，多模态推到下一章。
成功线：同步百分之百、流式不低于百分之九十八，首字延迟一点五秒内。失败率超百分之五就回滚契约版本。
我用三个真实上游交叉验证：差异集中在 tool_calls 和 usage，契约必须补归一化映射，否则 SDK 解析会失败。
按这个来，客户断流时能拿到 429 或 Timeout 的明确错误码，工单自己就能解释清楚。这一版我认。
补了归一化映射和日志删除路径，合规门槛过了。红线还剩一条：响应头不得伪造 OpenAI 官方标识。
预算维持六万，但加一条止损：三周内兼容测试不达标，本章降级为只交契约文档，实现不再追加投入。
我同步把错误码和快速接入写进文档站，挂 openai compatible 的结构化数据，两周看自然搜索进量。
付费仍然不投，但埋点要干净：文档页到 GitHub Star、到 SDK 试用这条链路必须能归因，以后才算得清账。
听完约束我把话术改掉：不说完全兼容 OpenAI，只说只改 base_url 和 api_key 即可接入，可验证就行。
Owner 锁死：Bob 周三交契约，Alex 第十天交实现，David 第十二天验收，Iris 第十三天出兼容报告。
就它了。第四章是上苍之手：契约先冻结，再谈实现。第十三天前同步加流式跑通，跑不通就只交契约文档。散会。
