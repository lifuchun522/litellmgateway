# 第三至尊术：高级策略叠加，不能绑架 P0 主链路

> 增强不是加法，是决定主链路会不会被拖下水。

```text
[读者] Java 后端与平台工程师
[痛点] 缓存、护栏、灰度一加，主链路就不稳
[现在读] P0 网关闭环已稳，需要安全地叠加增强能力
[读完] 能落地可插拔、可关闭、失败可控的高级策略层
```

```text
[旧方案] 策略直接写进 Gateway Pipeline
    |
    v
[新需求] 缓存 / Guardrail / Canary / 健康评分同时叠加
    |
    v
[冲突] 横切逻辑与核心生命周期耦合，失败面被放大
    |
    v
[后果] 关掉策略主链路 500，开着策略不敢上线
```

我是老李。前面十六境，我们把这套 Java 轻量级 LLM Gateway 从 litelmgateway 的 open-api.zip Demo 一步步逆向出来，换掉包名与项目名，补齐了 Provider、Deployment、LogicalModel、Route、Project、VirtualKey 到 Usage 的这条 P0 主链，Playground 和 OpenAI SDK 都能打通。核心闭环跑通那天，我以为最难的部分已经过去了。

真正难的从运营和合规找上门才开始：他们要在网关里加精确缓存省钱，加 Guardrail 拦不合规内容，加 Canary 拿一小部分流量试新 Provider，还要按健康评分自动摘掉坏掉的 Deployment。这些要求单看都合理，合在一起就变成了同一句话——在不许动主链路的前提下，把能力叠上去。

我第一次的做法很直接：在 Gateway Pipeline 里按顺序插了几段 if。结果是缓存命中把 Guardrail 整段跳过了；Guardrail 抛异常时网关吐 500；Canary 一关，路由分支也跟着乱。增强能力没有让系统更强，反而让最稳的那条主链开始抖。

高级策略到底该插在哪里，才不会绑架 P0 主链路？

缓存命中的请求，护栏还跑不跑，这个顺序由谁来定？

策略执行失败时，是 Fail Open 还是 Fail Closed，谁来拍板？

# 01、故事

我们的网关已经能对外服务了：多个项目各拿自己的 VirtualKey 进来，Route 挑 LogicalModel，Deployment 落到具体 Provider，成功后写一条 Usage。这条链路当时很干净，干净到任何人看代码都能在十分钟内说出一次请求经历了什么。

新的任务是：在这一层稳定之上，叠加一组可选的高级能力——精确缓存、Provider 健康评分、Canary 灰度，以及一个能让后续扩展继续挂上去的 GatewayPolicy 插件点。要求写得很克制：P0 核心必须保持完整可用，所有高级模块都要能单独开关。

我先做的第一版实现，是把缓存写在 Controller 前面，把 Guardrail 写在 Provider 调用之后，把 Canary 写在路由里。三个地方三种写法，谁也不知道对方存在。上线前演练时，只把 Canary 关掉，路由就出现了空的分支；只把缓存关掉，缓存那段 if 还在读一个空的 Map。那一刻我才意识到，问题不在缓存写得好不好，而在这些能力和主链路被焊在了一起。

它们本来应该是主链路之外的增益，结果变成了主链路的一部分。

> 核心先立稳
> 增强后叠加
> 一步一验之
> 不可越级行

# 02、问题

旧方案失效的地方很具体：高级能力以 if 分支形式散落在 Pipeline、Controller 和 Router 里，没有统一的阶段定义、开关和失败语义。

业务影响首先是可信度。缓存一开，命中请求绕过了 Guardrail 与审计，合规同事问一句“这次为什么没走检查”，我们答不上来；Guardrail 一次异常，用户拿到 500，业务方直接得出结论：网关比直连还不可靠。

技术表现有三类。第一，策略逻辑分散在三个层次，改动一处要重新理解全部。第二，缓存 key 只用了 messages，切换 model、temperature 或 max_tokens 之后仍然返回旧结果。第三，策略异常直接冒泡到全局异常处理，被当成 Provider 故障，触发了一次本不该发生的 Fallback。

本篇的完成标准必须可验证，我把它写成四条：

1. 所有高级模块全部关闭时，P0 主链（Route → Deployment → Provider → Usage）的行为与引入策略前一致。
2. 每个策略都有明确的阶段、顺序、开关与失败语义，可以单独启停。
3. 缓存 key 至少覆盖 model、messages、parameters、project 四个维度，换 project 必然不命中。
4. 策略执行失败不改变主链路的 HTTP 语义，除非该策略显式配置为 Fail Closed，且返回的是明确的拒绝而不是 500。

> 旧法已成患
> 新需又不轻
> 标准先立定
> 再谈加几层

# 03、原理

这一境只需要一个原理：主链路是一条不变量，高级策略是横切关注点，横切关注点只有两种合法位置——主链路之上（插件点）或主链路之外（旁路）。插进主链路内部，等于把两个变化速率完全不同的东西焊死。

于是策略层需要一组明确的生命周期阶段：pre-route、post-route、pre-provider、post-provider、response。顺序不是形式主义，顺序就是语义。缓存写在 pre-provider，命中就短路响应；Guardrail 写在 pre-provider 检查输入、post-provider 检查输出；Canary 写在 pre-route，决定候选 Deployment 集合；健康评分写在 post-provider，根据结果更新分数。

这里有一个反直觉判断：缓存的风险不是命中率低，而是命中错了。缓存不生效，最多是多花一次上游成本；一次跨 project 的错误命中，是把 A 租户的问题返回给 B 租户，性质和影响完全不同。所以缓存 key 的维度完整性，比缓存本身是否命中重要得多。

第二个反直觉判断：护栏最大的风险不是漏判，而是在不该拦的时候把主链路打挂。漏判是一次合规缺口，把主链路打挂是一次全局可用性事故。这就是为什么必须先把失败语义设计出来——Fail Open 还是 Fail Closed，必须逐模块配置，而不是让异常栈替我们做决定。

> 主路不可动
> 横切需插槽
> 命中先看键
> 失败先分级

# 04、架构

```text
[输入] /v1/chat/completions 请求 + Project / VirtualKey
    |
    v
[模块] GatewayPipeline（P0 核心，不变量）
    |
    v
[数据/状态] PolicyContext / 模块开关 / 健康分 / 缓存表
    |
    v
[处理] PolicyChain 按 pre-route → post-route → pre-provider → post-provider → response 执行
    |
    v
[输出] Provider 响应 / 策略增强结果 / 审计记录
```

边界很清楚：策略层只能读写 PolicyContext 和旁路状态（缓存、健康分、灰度规则），不允许直接拼装 Provider 的 HTTP 请求，也不允许把 Provider 的异常改写成自己的异常再抛出去。Canary 是唯一被允许影响路由的例外，但也只能在 pre-route 阶段调整候选集合，并留下决策记录。

收益是可关闭、可灰度、可排障：任何一个高级模块出问题，关掉开关就回到已知状态。代价是多一层间接调用，多一份需要维护一致性的旁路状态（缓存会过期、健康分要衰减），排障时还要多问一句“当时哪个策略是开着的”。

适用条件只有一个，但它是硬条件：P0 闭环已经稳定，并且有 Usage 与日志可以对照。核心还没稳的时候加策略层，等于在流沙上盖第二层楼。

> 入链路有序
> 出策略无权
> 边界划清晰
> 代价要先知

```java
// GatewayPolicyChain.java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Component;

import java.util.Comparator;
import java.util.List;

@Component
public class GatewayPolicyChain {

    private static final Logger log = LoggerFactory.getLogger(GatewayPolicyChain.class);

    private final List<GatewayPolicy> policies;
    private final PolicyProperties properties;

    public GatewayPolicyChain(List<GatewayPolicy> policies, PolicyProperties properties) {
        this.policies = policies.stream()
                .sorted(Comparator.comparingInt(GatewayPolicy::order))
                .toList();
        this.properties = properties;
    }

    public void run(PolicyStage stage, PolicyContext ctx) {
        for (GatewayPolicy policy : policies) {
            if (!policy.stages().contains(stage)) {
                continue;
            }
            if (!properties.isEnabled(policy.name())) {
                continue;
            }
            try {
                policy.apply(stage, ctx);
            } catch (Exception e) {
                if (properties.failureMode(policy.name()) == PolicyProperties.FailureMode.FAIL_CLOSED) {
                    throw new PolicyRejectedException(policy.name(), e);
                }
                log.warn("policy={} stage={} failed, fail-open", policy.name(), stage, e);
            }
        }
    }
}
```

最后是精确缓存策略本身，它的 key 必须带齐四个维度：

```java
// ExactCachePolicy.java
import org.springframework.stereotype.Component;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.stream.Collectors;

@Component
public class ExactCachePolicy implements GatewayPolicy {

    private final Map<String, ChatResponse> cache = new ConcurrentHashMap<>();

    @Override
    public String name() {
        return "exact-cache";
    }

    @Override
    public Set<PolicyStage> stages() {
        return Set.of(PolicyStage.PRE_PROVIDER, PolicyStage.RESPONSE);
    }

    @Override
    public int order() {
        return 200;
    }

    @Override
    public void apply(PolicyStage stage, PolicyContext ctx) {
        if (stage == PolicyStage.PRE_PROVIDER) {
            String key = key(ctx);
            ctx.cacheKey(key);
            ChatResponse hit = cache.get(key);
            if (hit != null) {
                ctx.shortCircuit(hit);
            }
            return;
        }
        if (stage == PolicyStage.RESPONSE && ctx.cacheKey() != null && ctx.response() != null) {
            cache.put(ctx.cacheKey(), ctx.response());
        }
    }

    private String key(PolicyContext ctx) {
        String raw = ctx.projectId() + "|" + ctx.model() + "|"
                + canonicalMessages(ctx.messages()) + "|"
                + canonicalParameters(ctx.parameters());
        return sha256(raw);
    }

    private String canonicalMessages(List<ChatMessage> messages) {
        return messages.stream()
                .map(m -> m.role() + ":" + m.content())
                .collect(Collectors.joining("\n"));
    }

    private String canonicalParameters(Map<String, Object> parameters) {
        return parameters.entrySet().stream()
                .sorted(Map.Entry.comparingByKey())
                .map(e -> e.getKey() + "=" + e.getValue())
                .collect(Collectors.joining("&"));
    }

    private String sha256(String raw) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] bytes = digest.digest(raw.getBytes(StandardCharsets.UTF_8));
            StringBuilder sb = new StringBuilder();
            for (byte b : bytes) {
                sb.append(String.format("%02x", b));
            }
            return sb.toString();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

# 06、排查

V1 跑通之后，我在演练环境里连续遇到两个问题，都是“高级能力反而拖累核心”的典型。

第一个问题：开启缓存后，把 model 从 gpt-4o-mini 换成另一个模型，或者把 temperature 从 0.2 改成 0.9，返回的仍然是上一次的答案。

现象：参数变了，结果没变。怀疑：是不是 Provider 侧有缓存，或者 HTTP 客户端连接复用导致的？检查：在 ExactCachePolicy 的 key 方法里把 raw 原文打出来。证据：两次请求打印出的 raw 字符串完全相同，里面只有 messages，根本没有 model 和 parameters。根因：缓存 key 维度不足，只覆盖了 messages 一个维度。

**错误尝试：** 我一开始怀疑是 JSON 序列化顺序不稳定，于是换了一个固定字段顺序的序列化器。为什么错：key 的问题不是“抖”，而是“少”——少掉的维度再怎么稳定排序也不会出现，模型换了却仍然命中同一个 key，这和序列化毫无关系。

修复：把 projectId、model、canonicalMessages、canonicalParameters 四段拼进 raw，再做 SHA-256。修改后复测：换 model 必然 MISS，换 project 必然 MISS，只改 temperature 也必然 MISS。

第二个问题：Guardrail 判定内容不合规时，客户端收到的是 500，而不是明确的拒绝。

现象：故意发一条会被拦的请求，返回 500 加一大段堆栈。怀疑：是不是下游 Provider 报错被包装上来了？检查：看异常栈的顶层类。证据：异常来自 polic 包，说明根本没走到 Provider，异常是在策略层抛出的。根因：策略异常和 Provider 异常共用同一条异常通道，全局异常处理把它当成内部错误。

**错误尝试：** 我在全局异常处理里加了一条分支，把策略异常也映射成 502。为什么错：方向反了。502 的语义是上游故障，一旦这样映射，网关会认为 Provider 不稳定，进而触发 Retry 和 Fallback，请求会被重放，而它本来就应该被拒绝。

修复：引入 PolicyRejectedException，把策略拒绝与 Provider 故障彻底分开，拒绝统一映射为带明确原因的 4xx。修完之后，Fail Closed 的模块拒绝时不再触发任何 Retry。

> 现象先记录
> 怀疑要可证
> 根因落一处
> 修复才闭合

# 07、优化

第 06 章的两个证据指向同一个根因：策略与核心共用状态、共用异常通道、共用缓存语义。V2 就按这个根因改。

根因一，缓存 key 维度缺失。修改：把 project、model、messages、parameters 四维固化进 key 生成逻辑，并把这段逻辑收进策略内部，不允许调用方直接构造。原因：key 的维度就是语义边界，写在策略里才有唯一解释权。新行为：换 project、换 model、改 temperature 或 max_tokens 都会 MISS。验证方式：构造四组只差一个维度的请求，逐一比对缓存日志，预期四组互不命中。

根因二，失败语义缺省且不可配。修改：PolicyProperties 提供逐模块的 FAIL_OPEN / FAIL_CLOSED，默认 FAIL_OPEN，Guardrail 显式配成 FAIL_CLOSED。原因：提效类模块（缓存、健康评分）失败时应放过请求，合规类模块（Guardrail）失败时应明确拒绝，两者不能用同一个默认值。新行为：策略内部异常不再直接冒泡，链上按模块配置决定放过或拒绝。验证方式：在策略里临时注入一个异常，分别在两种配置下各发一次请求，确认一次走通、一次返回明确的 4xx 而不是 500。

根因三，策略生命周期散落。修改：所有能力统一实现 GatewayPolicy，只用 stages() 声明自己关心哪些阶段，order() 声明同阶段内的先后。原因：主链路只认接口，不认具体策略，新增能力不需要改 Pipeline 一行。新行为：新增一个策略只需要加一个 Bean 加一段配置；把 modules 全部置为 false，主链路行为与未引入策略时一致。

V2 之后，页面上的高级策略区域也只在该模块启用后才渲染，避免出现“能看见但点不动”的假功能。

> 一处根因改
> 全链行为变
> 不夸数据好
> 只求可复现

# 08、演进

```text
[同一输入]
    |
    +--[V1] 策略 if 写死在 Pipeline / 失败即 500 / key 缺维度
    |
    +--[V2] 插件点 + 模块开关 + Fail 策略 / 失败可控 / key 四维
    |
[Trade-off]
得到可关闭、可灰度、可排障的增强层；失去主链路的一点直接性，多一份策略状态要维护；只适用于核心闭环已稳定的前提
```

正确性上，V2 把“行为正确”拆成了两层：核心行为正确（全关时与之前一致）和增强行为正确（开启时符合各自语义）。V1 只有一层，所以一旦开启就分不清是核心错了还是策略错了。

稳定性上，V1 的失败路径是把异常直接升级成 500，V2 把失败路径变成可配置的分支。差别不在于 V2 不会失败，而在于 V2 失败时知道自己失败，并且这个失败的后果是被预先决定过的。

复杂度上，V2 明显更重：多了接口、阶段、配置和一份旁路状态。这份复杂度换来的是“新增策略不用改核心”，如果只有一两个策略，这个交换未必划算；策略数量一多，写死在 Pipeline 里的方案会迅速失控。

成本上，精确缓存本身不引入额外上游调用，但它引入了内存与一致性成本；健康评分引入了状态衰减与重启后状态归零的问题，这一点在后面的配置持久化里还得继续处理。

适用范围上，这套结构不是给刚起步的网关用的。它还留着一个明确问题：策略状态在内存里，重启即丢，这需要下一境的能力来兜。

> 同一请求入
> 两版不同行
> 得失各有价
> 取舍看边界

# 09、洞见

## 9.1 增强能力的第一属性是可关闭

反直觉判断：一个策略“能不能用”，取决于它“能不能关”。我们习惯先问缓存命中率多高、护栏覆盖多全，但只要有一个高级模块关不掉，它就已经是主链路的负债，而不是增益。第 02 章那四条完成标准里，第一条就是全关时核心仍完整运行，原因就在这里。

## 9.2 顺序就是语义：缓存不能绕过护栏

反直觉判断：缓存命中率是结果指标，不是设计目标。先把阶段顺序定下来，命中率才有意义。缓存写在 pre-provider 时，它的短路只影响“是否调用 Provider”，不影响前置的输入检查；如果反过来把 Guardrail 放在缓存之后，命中的请求就天然跳过了合规检查——这不是性能优化，这是合规缺口。

## 9.3 Fail Open 与 Fail Closed 必须逐模块配置

反直觉判断：统一的失败策略看起来很整齐，实际是把合规模块和提效模块按同一标准处理，两头都不对。缓存失败放过请求只是多花一次调用；Guardrail 失败放过请求可能是合规事故。默认值应该保守，例外应该显式声明，而不是反过来。

## 9.4 控制面要诚实：模块没启用就不显示

页面只在模块启用后渲染对应区域，是一个很小的决定，但它决定了控制面是否可信。一个点不动的开关，会训练使用者不再相信界面；一个只显示可用能力的界面，才能让人在第一眼就判断出当前系统真正具备什么。

> 增强非加法
> 可关才是能
> 顺序即语义
> 失败需分级

# 10、系统落地

原来有什么：一条稳定的 P0 主链——请求进来经 Route 选 LogicalModel，落到 Deployment，转成 Provider 请求，回来写 Usage。它只认协议，不认策略。

本篇新增了什么：一个 GatewayPolicy 插件点与五个标准阶段（pre-route、post-route、pre-provider、post-provider、response），一套逐模块开关与逐模块失败语义，一个四维 key 的精确缓存，以及健康评分、Canary 的挂载位置。分支是 `chapter/17-advanced-policy`，提交信息为 `feat(ch17): add optional advanced gateway policy extensions`。

现在能做什么：可以按项目灰度试新 Provider，可以用精确缓存降低重复调用，可以在策略失败时按配置放过或拒绝，可以在页面上一键关掉全部高级模块回到已知状态。

还缺什么：语义缓存、Guardrail 的规则体系与 PII / Prompt Injection 防护、Webhook 与告警、策略状态的重启恢复，还有密钥加密、日志脱敏、Prompt 默认不落库、请求体大小限制、CORS 与审计这一整套安全持续强化。它们属于 P1、P2，不应该和 P0 同批上线。

下一步如何演进：先让这套插件点在真实流量下稳定一段时间，把“关闭全部高级模块，P0 核心仍完整运行”变成每次发布的固定回归项，再考虑引入语义缓存与更复杂的护栏规则。

# 11、小结

```text
Q1 → 插在 GatewayPipeline 两侧的插件点，核心只认接口
Q2 → 顺序由 PolicyChain 的阶段定义，缓存不作为绕过护栏的短路
Q3 → 逐模块配置 Fail Open / Fail Closed，默认从保守开始
状态 → 高级策略可开可关，全关时 P0 主链完整运行
```

Q1 的答案决定了系统的形状：策略不在主链路内部，而在它两侧。Q2 的答案决定了系统的语义：阶段顺序就是合规顺序，先定顺序再谈命中率。Q3 的答案决定了系统的边界：失败不是一个要避免的意外，而是一个必须提前设计的配置项。

这一境交付的能力很朴素，也很关键：一套可以叠加、也可以整体拆除的增强层。

# 12、作业

## 12.1 理解题：为什么高级策略应该放在插件点，而不是直接写进 Gateway Pipeline？

参考答案：两者的变化速率不同。主链路承载协议、路由、Provider 适配这些低频变化的不变量；缓存、护栏、灰度是高频变化的能力。写进 Pipeline 会同时带来三个后果：策略异常直接污染核心的 HTTP 语义；新增策略必须改动核心代码；关闭策略时容易留下空分支。放到插件点之后，核心只依赖接口，策略通过 stages() 与 order() 自描述，关闭只是配置变化。

## 12.2 实战题：给出精确缓存 key 的最小维度集合，并说明每个维度的作用。

参考答案：project 用于租户隔离，防止跨项目命中；model 决定输出语义，换模型必须失效；messages 决定输入语义，是命中的主体；parameters（temperature、max_tokens、top_p 等）决定生成行为，同输入不同参数结果不同。四者规范化后拼接再哈希。注意规范化要稳定：messages 按顺序拼接，parameters 按键排序拼接，避免因为 Map 顺序不同产生不同 key。

## 12.3 排障题：开启 Guardrail 之后客户端 500 变多，你怎么定位？

参考答案：第一步看异常来源包，确认是策略内部抛出还是 Provider 返回，这决定了问题在策略层还是上游。第二步看是否触发了 Retry 与 Fallback，如果触发了，说明拒绝被误判成故障，需要把策略异常与 Provider 异常分开映射。第三步看该模块的失败语义配置，确认是 FAIL_OPEN 还是 FAIL_CLOSED。第四步复现并构造一个必然被拦的请求，验证返回码是否为带原因的 4xx 而不是 500。

## 12.4 架构判断题：Canary 灰度是否应该实现为 Provider 内部逻辑？

参考答案：不应该。Provider 的职责是协议适配与请求转换，它对流量分配、租户规则、灰度比例一无所知。Canary 属于策略层，在 pre-route 阶段调整候选 Deployment 集合，并记录决策依据；Provider 只负责把已经选定的请求翻译成上游能理解的格式。把灰度写进 Provider，会让 Provider 承担两个变化速率不同的职责，也会让排障时无法区分是协议问题还是流量问题。

> 一题一思量
> 一动一验证
> 一排一溯源
> 一判见功力

# 13、思考

这一境的核心冲突从头到尾没有变：我们要在一条已经稳定的主链路上叠加能力，而任何叠加都会引入新的失败面。第三至尊术真正的启发不在于“加了什么”，而在于叠加本身必须建立在原有力量之上——法力、速度、神通都在，增幅才有意义；底子不在，叠加只会加速崩塌。

工程上的落点也很清楚：先把核心的不变量识别出来，再把增强能力做成可关闭、可配置、可排障的插件，最后用“全部关闭时核心仍完整运行”这一条作为每次发布的固定回归项。做到这一步，增强层才是资产；做不到，它就是下一个需要被排查的故障源。
