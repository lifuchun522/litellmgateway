# 洞天境柳神法：不重构骨架，只把 Demo 换骨成 LLM Gateway 基线

> 换骨不改肉，改错一个包名，整条链路就断。

```text
[读者] 接手一个能跑但名字不是自己的 Java LLM Demo 的工程师
[痛点] Demo 能跑通，但包名、坐标、配置前缀、镜像名全是别人的，动一处崩一片
[现在读] 第 1 境已把结构逆向清楚，必须先换骨，才谈得上往上长肉
[读完] 能独立完成一次零功能变化的项目换骨，并留下可扫描、可回滚的基线
```

```text
[旧方案] Demo 原样能跑，功能对得上，但名字不是你的
    |
    v
[新需求] 要把它当作自研 Java LLM Gateway 的正式基线继续演进
    |
    v
[冲突] 改名要动包、类、配置、XML、前端、脚本、镜像，牵一发动全身
    |
    v
[后果] 顺手重构 → 功能退化 → 分不清是「改坏了」还是「本来就坏」
```

我是老李。第 1 境我把 open-api.zip 解开，一个目录一个目录地读完它的启动类、配置文件和 Controller，确认它是一份能跑通的 OpenAI 兼容 Demo：`/v1/models` 能列模型，`/v1/chat/completions` 能走通上游。逆向的结论只有一句——它的骨架是对的，但名字不是我的。

骨架对，意味着可以留；名字不对，意味着必须换。Demo 的名字藏在七个地方：Maven 的 groupId 与 artifactId、根 package、启动类、`application.yml` 的配置前缀、静态资源与页面的品牌名、日志里的包名、Docker 的镜像名与容器名。它们不是一起改的，而是一个一个改的，漏掉任何一个，都只在运行时才炸。

所以第 2 境给自己立了一条死规矩：只换骨，不动肉。功能行为必须与第 1 境完全一致，接口返回必须逐字对得上；任何「顺手优化」都写进待办，而不是写进这次提交。

换骨和重构，到底该在哪一刀上分清？

先改名还是先改功能，顺序错了会付出什么代价？

如果换骨之后接口返回变了，你拿什么证明这是环境差异，而不是你改坏的？

# 01、故事

现场是这样的：Demo 在本地跑起来了，`/v1/models` 返回模型列表，`/v1/chat/completions` 也能流式返回。但它身上全是别人的名字——根包 `com.example.demo`，启动类 `DemoApplication`，`application.yml` 里一片 `demo.*` 前缀，欢迎页标题写着 Demo Gateway，`docker-compose.yml` 里的服务名叫 demo。

任务是：在不改变任何一条接口行为的前提下，把这份 Demo 换骨成自研的 Java 轻量级 LLM Gateway 基线。不是改功能，不是拆模块，更不是顺手把 Controller 重构成三层。

当前方案很朴素：搜一个词，改一个词，编译一次，跑一次。我第一次改完，编译过了，启动也过了，我以为收工了；结果一调 `/v1/chat/completions` 直接 500。日志里一行 `Invalid bound statement`，来自 MyBatis 的 XML —— 它用的是字符串形式的包名，编译器根本看不见。

变化在于：这不再是一个跑给自己看的 Demo，而是一条要长期演进的基线。基线上带着半迁移状态往上长，后面每个模块都要在「有一部分代码还挂在别人包名下」的地基上施工。

冲突也在这里：改名这件事，直觉上是「改字符串」，工程上是「改标识符」。字符串可以随便替，标识符改了就必须保证所有引用它的地方同时改——包、import、组件扫描、XML namespace、配置前缀、镜像名，缺一不可。

于是柳神法的那个隐喻就落到了实处：涅槃不是把树砍了重栽，是把旧的形骸烧掉，新的生机从原根长出来。骨架是原根，命名是形骸。

> 名不正则言不顺
> 骨不正则形难立
> 先换骨后长肉
> 一步一验方稳

# 02、问题

旧方案的失效点很明确：报错驱动改名。它在前三个错误上有效，到第五个错误就失控了——你永远不知道还剩几个没暴露的错误，它们只在特定路径上触发：只在流式接口触发、只在某个 profile 触发、只在 Docker 里触发。

业务影响是长期的：这份 Demo 要作为团队自研网关的基线，命名不换，后面所有新增类都挂在别人的包下，代码评审、依赖坐标、镜像命名、日志检索口径全是乱的。

技术表现是可以被观察到的：

- 编译通过，运行时报 `Invalid bound statement`、`ClassNotFoundException`、`No qualifying bean`；
- `mvn -q test` 通过，但接口 404 或 500；
- 容器里跑起来，配置前缀读不到，链路静默走了默认值；
- 前端页面标题还是别人的品牌名；
- 某个裸词被替换到了不该替换的地方，比如示例数据、注释、JSON 字段名。

最麻烦的是第三条：配置前缀读不到不会报错，它只是让 `@ConfigurationProperties` 绑不上，字段全为 null，然后你以为是上游 Provider 出问题了。

可验证的完成标准必须先写下来，否则「换完了」永远是个感觉：

1. `mvn clean package` 成功；
2. 全仓检索旧包名（排除 `.git` 与 `target`）结果为空；
3. 启动后 `/v1/models` 的响应结构与换骨前一致；
4. `/v1/chat/completions` 返回同样的内容；
5. 镜像名与容器名已经是新名字；
6. `git diff` 里没有任何方法体的逻辑变化。

第 6 条是这一境的灵魂。它把「换骨」与「重构」用一条可机械检查的规则切开了。

> 报错驱动终失控
> 清单驱动可复现
> 标准先行再动手
> 行为不变算过关

# 03、原理

本篇只需要三条原理，但每条都能解释后面的故障。

第一条：Java 编译器只保证标识符引用的一致性。包名、类名、import 是标识符，改错了编译不过，编译器会拦住你。但 `application.yml` 里的前缀、MyBatis XML 里的 namespace、模板里的品牌名、Dockerfile 里的 jar 名，全都是字符串——编译器一个字都看不见。

第二条：Spring Boot 的组件扫描以启动类所在包为根。你把 Controller 挪到了新包，启动类还留在旧包，扫描根就没变，接口直接 404。启动类上如果写了 `scanBasePackages`，那更是一条隐式的旧路径。

第三条：MyBatis 的 Mapper 接口与 XML 是靠 namespace 字符串绑定的，不是靠包结构。目录挪对了，namespace 没改，接口能注入进容器，一调用就 `Invalid bound statement`。

反直觉判断：换骨最大的风险不是「改得太多」，而是「改得太少」。改 95% 比改 0% 危险得多——0% 时你清楚自己在旧状态，95% 时你以为自己已经迁完了，剩下的 5% 只在特定路径触发，会让你把时间全花在怀疑上游服务上。

还有一条延伸判断：在迁移这件事上，编译器的绿灯是最弱的证据，全仓的残留扫描才是最强的证据。因为编译器只能证明「它看得见的部分是对的」，而扫描能证明「它看不见的部分也是干净的」。

> 编译器只见标识
> 看不见字符串引
> 九成五比零更险
> 边界成替换章法

# 04、架构

```text
[输入] 一份可运行的 open-api.zip Demo 源码
    |
    v
[模块] 换骨清单：坐标 / 根包 / 启动类 / 配置前缀 / 品牌名 / 脚本与镜像
    |
    v
[数据/状态] 全局唯一的新标识符 cloud.joysky.llmgateway
    |
    v
[处理] 标识符级批量替换 → 字符串级定点替换 → 全仓残留扫描 → 基线回归
    |
    v
[输出] 行为不变、名字全新的 Java LLM Gateway 基线
```

这个架构的边界很清楚：它只处理「名字」。输入是同一份代码，输出是同一份行为，中间不许出现控制流和数据流的改动。凡是要动方法体、拆接口、换序列化框架的，一律不属于本章。

收益有两条。第一，迁移过程变得可复现——换骨清单固定，脚本固定，任何人重跑一遍得到同一个结果。第二，验收变得可机械检查——残留扫描为空、编译通过、基线响应 diff 无差异，三条都是客观判据，不依赖「我觉得没问题」。

代价同样有两条。第一，前期要多做两件事：存一份「黄金基线响应」，写一个残留扫描脚本。第二，因为不许顺手重构，那些早就想改的坏味道必须原样留着，会有一段时间的不适感。

适用条件只有一条：结构不变、只换标识符的迁移。一旦你判断需要拆模块，比如把 Provider 适配层单独拆出去，那就不是本章的活儿——本章的前提是「保留 Demo 原目录与模块结构，只有逆向结果证明必要时才拆模块」。

> 一份清单定边界
> 一个标识统全局
> 扫描兜底防漏网
> 行为不变是底线

# 05、实战一次

环境与版本，以 Demo 自己的构建文件为准，不一致时听 pom 的：

- JDK 17（Demo 的 `maven.compiler.source` 写了什么就用什么）
- Maven 3.9.x；若 Demo 用的是 Gradle，把下面所有 `mvn` 换成 `./gradlew`
- Git 2.4 以上（需要 `git mv` 保留重命名历史）
- `jq`（用于对基线响应做规范化 diff）

依赖不需要新增，本章不加任何三方包。

第一步，先把基线跑起来并存证。

```bash
unzip open-api.zip -d llm-gateway
cd llm-gateway
git init && git add -A
git commit -m "chore: import open-api demo baseline"
mvn -q clean package
java -jar target/*.jar
```

另开一个终端，把黄金基线存下来：

```bash
mkdir -p baseline
curl -s http://localhost:8080/v1/models | jq -S . > baseline/models.json
curl -s -X POST http://localhost:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  --data @baseline/chat-req.json | jq -S . > baseline/chat.json
```

`baseline/chat-req.json` 里放的是你第 1 境验证过的那条请求。这份 baseline 目录，就是整章的验收尺子。

第二步，建分支。

```bash
git checkout -b chapter/02-rename-baseline
```

第三步，迁移目录与根包。先建父目录，再 `git mv`，顺序不能反。

```bash
OLD_PKG="com.example.demo"
NEW_PKG="cloud.joysky.llmgateway"

mkdir -p src/main/java/cloud/joysky
mkdir -p src/test/java/cloud/joysky
git mv src/main/java/com/example/demo src/main/java/cloud/joysky/llmgateway
git mv src/test/java/com/example/demo src/test/java/cloud/joysky/llmgateway
```

如果 Demo 的目录层级不是三段，按 `NEW_PKG` 的层级调整，最终必须让目录结构与包名严格一一对应。

第四步，做标识符级的全局替换。注意这里替换的是「带边界的完整包名」，不是裸词。

```bash
grep -rl "$OLD_PKG" \
  --include="*.java" --include="*.kt" --include="*.xml" \
  --include="*.yml" --include="*.yaml" --include="*.properties" \
  --include="*.gradle" --include="pom.xml" . \
  | xargs sed -i "s|${OLD_PKG}|${NEW_PKG}|g"
```

因为 `$OLD_PKG` 是一个完整包名，它天然带边界，这个替换是安全的，而且是一步到位的。

第五步，换坐标、换启动类。

```bash
sed -i 's|<groupId>com.example</groupId>|<groupId>cloud.joysky</groupId>|' pom.xml
sed -i 's|<artifactId>demo</artifactId>|<artifactId>llm-gateway</artifactId>|' pom.xml
sed -i 's|<name>demo</name>|<name>llm-gateway</name>|' pom.xml

# 启动类改名（类名以实际解压结果为准）
git mv src/main/java/cloud/joysky/llmgateway/DemoApplication.java \
       src/main/java/cloud/joysky/llmgateway/LlmGatewayApplication.java
sed -i 's|DemoApplication|LlmGatewayApplication|g' \
  src/main/java/cloud/joysky/llmgateway/LlmGatewayApplication.java
```

如果启动类上写了 `@SpringBootApplication(scanBasePackages = "com.example.demo")`，第四步已经把它替换掉了；如果没写，就保持默认的不写。

第六步，换配置前缀与 profile 文件。

```bash
grep -rn "@ConfigurationProperties" src/main/java/
grep -rn "^demo:" src/main/resources/
ls src/main/resources/application*.yml src/main/resources/application*.properties 2>/dev/null
```

找到 `@ConfigurationProperties(prefix = "demo")` 之后，把注解里的 prefix 与 yml 里的顶层前缀同时改成新名字。这一步必须两边一起动，因为 prefix 是精确字符串匹配，Spring 的松散绑定不会救你。

第七步，整理环境与运行基线。

```bash
ls -a | grep -E '^\.env'
```

如果 Demo 带 `.env.example`，把其中的变量名前缀统一成新项目口径，并补上 local / mysql 两个 profile 的说明；如果它没有，就在 `src/main/resources/` 下补齐 `application-local.yml` 与 `application-mysql.yml` 的骨架，只放数据源与日志级别，不放业务配置。

日志与 Docker 基线一并检查：`logging.level` 里如果带了旧包名，第四步已经覆盖；`Dockerfile` 里的 jar 文件名、`docker-compose.yml` 里的 service 名与 image 名，需要手动改。

第八步，编译并做残留扫描。

```bash
grep -rn "com\.example\.demo" . --exclude-dir=.git --exclude-dir=target \
  || echo "NO RESIDUE"
```

预期输出：

```text
NO RESIDUE
```

（示例输出）

第九步，启动并回归。

```bash
mvn -q clean package
java -jar target/llm-gateway-*.jar

curl -s http://localhost:8080/v1/models | jq -S . > /tmp/models.after.json
diff baseline/models.json /tmp/models.after.json && echo "models 行为一致"
```

`diff` 无输出即一致。`/v1/chat/completions` 同样跑一遍，把请求体放进文件再发，避免 shell 转义干扰：

```bash
curl -s -X POST http://localhost:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  --data @baseline/chat-req.json | jq -S . > /tmp/chat.after.json
diff baseline/chat.json /tmp/chat.after.json && echo "chat 行为一致"
```

未在当前环境实测，以上为预期结果。首次跑通后，把这两条 `diff` 命令固化进仓库脚本，否则第 3 境还得重新想一遍怎么验。

> 先存基线再动手
> 目录先行后替换
> 编译只是第一关
> 接口回归才算数

# 06、排查

换骨过程中的故障高度同质，我把第 1 境到本章真实踩到的三类列出来。

现象一：编译通过、启动也通过，调用 `/v1/chat/completions` 报 `Invalid bound statement (not found)`。

怀疑：Mapper 接口没注入进来。

检查：

```bash
grep -rn "namespace" src/main/resources/ --include="*.xml"
```

证据：XML 里的 `namespace` 仍然是 `com.example.demo.mapper.XxxMapper`，而接口已经在新包下。

根因：MyBatis 用 namespace 字符串绑定接口与 XML，与包结构无关，编译器看不见这个字符串。

修复：把 XML 中的 namespace 以及 `resultType`、`parameterType` 里的旧包名一并替换（第四步的全局替换已经覆盖，前提是你把 `--include="*.xml"` 加上了）。

现象二：编译通过、启动成功，但 `/v1/models` 返回 404。

怀疑：Controller 没被扫描到。

检查：看启动日志里 `RequestMappingHandlerMapping` 注册了哪些路径，或者直接搜索注解：

```bash
grep -rn "@RestController\|@Controller" src/main/java/
```

证据：Controller 已经在新包下，但启动类仍在旧包下，或者启动类上写着 `scanBasePackages` 指向旧包。

根因：Spring Boot 默认以启动类所在包为组件扫描根，启动类没跟着迁移，扫描根就没变。

修复：`git mv` 启动类到 `cloud.joysky.llmgateway` 根下，或显式修正 `scanBasePackages`。前者更好，因为后者会在代码里留下一条隐式旧路径。

现象三：本地能跑，容器里起不来，或者起来了但配置全是默认值。

怀疑：配置前缀没对齐。

检查：

```bash
grep -rn "@ConfigurationProperties" src/main/java/
grep -rn "^demo:\|^llmgateway:" src/main/resources/
```

证据：注解里还是 `prefix = "demo"`，而 yml 顶层已经改成 `llmgateway:`，两边对不上，绑定静默失败，字段为 null。

根因：`@ConfigurationProperties` 的 prefix 是精确字符串匹配，松散绑定只作用于属性名，不作用于前缀本身。

修复：两边同时改，改完在启动日志里确认绑定成功，或者加一个启动自检断言。

**错误尝试：** 我一开始图省事，全仓跑了 `sed -i 's/demo/llmgateway/g'`，用裸词替换。结果注释里的「demo 数据」、示例 JSON 里的字段名、甚至 `spring.profiles.active` 附近的 `demo-local` 全被改掉，local profile 激活失败，应用静默走了一套完全不同的默认配置，接口返回看起来「像是上游挂了」。

这个尝试错在哪里？错在替换范围失控。裸词没有边界，`demo` 会命中包名、前缀、字段、注释、示例数据、配置值，命中之后你无法用肉眼判断哪些该改哪些不该改，最后只能 `git checkout` 重来。正确的粒度是「带边界的标识符」：完整包名、完整前缀（含冒号）、完整类名、完整镜像名。粒度对了，替换反而是机械且安全的。

> 现象先行莫猜因
> 证据到手再定根
> 裸词替换是陷阱
> 边界替换方为道

# 07、优化

从第 06 章的三条根因往回推，得到三条必须改的东西。

根因 A：字符串形式的引用（XML namespace、`@ConfigurationProperties` 的 prefix、模板文案、Dockerfile jar 名）编译器不可见。
修改：把「迁移完成度」从主观判断改成客观扫描。
原因：看不见的引用只能靠扫描暴露，不能靠「我记得改过」。
新行为：任何一次提交前先跑扫描，扫描不过就不提交。

```bash
#!/usr/bin/env bash
set -euo pipefail

OLD_PKG="com.example.demo"

if grep -rn "$OLD_PKG" . --exclude-dir=.git --exclude-dir=target; then
  echo "换骨未完成：仍存在旧包名引用" >&2
  exit 1
fi

echo "换骨残留检查通过"
```

保存为 `scripts/check-rename.sh`，赋予可执行权限。这段脚本是本章唯一新增的「工程资产」，它的价值在于把第 12 境要做的配置守卫提前埋了一颗种子。

根因 B：裸词替换范围失控。
修改：把替换分成三级。一级是完整包名，全仓批量，安全；二级是 Maven 坐标、启动类名、配置前缀，逐文件确认；三级是品牌文案、镜像名、容器名、脚本注释，人工过一遍清单。
原因：每一级的边界确定性不同，混在一起做就必然过火。
新行为：替换有层级、有顺序、有确认点。

根因 C：缺少「行为不变」的客观判据。
修改：把第 05 章的 baseline 目录与两条 `diff` 命令固化进仓库，作为换骨的回归门。
原因：换骨的验收标准是行为不变，行为只能靠对比证明。
新行为：每次构建后自动比对 `/v1/models` 与 `/v1/chat/completions` 的规范化响应。

```bash
# scripts/smoke.sh
set -euo pipefail
BASE_URL="${BASE_URL:-http://localhost:8080}"
curl -s "$BASE_URL/v1/models" | jq -S . > /tmp/models.after.json
diff baseline/models.json /tmp/models.after.json
echo "换骨回归通过：接口行为与基线一致"
```

验证方式：残留扫描脚本在换骨后的仓库上执行，预期输出「换骨残留检查通过」；冒烟脚本在应用启动后执行，预期 `diff` 无输出。这两条验证都不依赖任何性能数据，只依赖行为一致性，因此可以放心作为长期门禁。

> 分级替换控范围
> 扫描脚本守底线
> 基线比对定行为
> 复现为先不靠猜

# 08、演进

```text
[同一输入] 一份可运行的 open-api.zip Demo
    |
    +--[V1] 报错驱动改名：改一处、跑一次，漏一处、炸一处
    |        代价：反复重启，问题与迁移进度不成正比
    |
    +--[V2] 清单 + 扫描驱动换骨：定唯一新标识符 → 分级替换 → 残留扫描 → 基线回归
    |        代价：前期多写一个扫描脚本，多存一份黄金基线
    |
[Trade-off]
得到什么：迁移可复现、完成度可度量、行为可回归、出错可回滚
失去什么：前期多两件准备工作；不能顺手改坏味道
适用边界：结构不变、只换标识符的迁移；要拆模块就不适用
```

正确性上，V1 与 V2 的终点一样，都能把名字换掉；差别在于 V1 的终点是「碰巧到达」，V2 的终点是「证明到达」。

稳定性上，V1 依赖执行者的记忆和耐心，换一个人重做一遍结果不同；V2 依赖脚本，重做一遍结果相同。

复杂度上，V2 增加了两个文件：一个扫描脚本，一个冒烟脚本。这两个文件是本章唯一的复杂度增量，可控。

成本上，V2 的前期成本更高、后期成本更低。第 2 境省下来的时间其实有限，真正的收益在第 3 境以后——后面每一境都在同一套命名空间和同一套回归脚本上施工。

适用范围上，V2 只适用于「不重构的换骨」。如果某一境的正确做法本身就是拆模块，那必须先拆完、跑通、再走本章这套换骨流程，不能混在一起做。

遗留问题有两个：一是 Demo 原有的坏味道全部保留，包括可能的硬编码、缺少分层、日志不成体系；二是 `cloud.joysky.llmgateway` 这个根包名还需要按团队实际规范最终确认，如果规范不同，本章的脚本改一个变量即可重跑。

> 同一输入两种走
> 一慢一快各有价
> 得到复现失些力
> 边界之内方可用

# 09、洞见

## 9.1 换骨的验收标准是「行为不变」，不是「名字变了」

这一条决定了本章所有技术选择。只要验收标准是「名字变了」，那随便改改，编译能过、能启动，就算完成；只要验收标准是「行为不变」，就必须先有基线、再有对比。前一种标准下，半迁移状态是可以蒙混过关的；后一种标准下，半迁移状态会在第一次 diff 时暴露。

这也是「本章禁止顺手大重构」这句话的真正原因。重构和换骨混在一起，行为一定会变，而行为一变，你就再也分不清是迁移改坏了，还是重构改坏了。分开做，两次都有清晰的判据。

## 9.2 反直觉判断：编译器通过的迁移，才刚走到一半

直觉上，编译通过意味着改得差不多了。实际上编译器只覆盖了标识符那一半，字符串那一半它完全看不见。MyBatis 的 namespace、`@ConfigurationProperties` 的 prefix、模板里的品牌名、Dockerfile 里的 jar 名、`.env` 里的变量名，全是字符串，全在编译器的盲区里。

所以正确的顺序是：让编译器先过，然后用扫描补上另一半，最后用基线 diff 收尾。三步都过，才算迁移完成。如果只做第一步就宣布完成，风险恰好集中在剩下的盲区里。

## 9.3 反直觉判断：带边界的批量替换，比逐个人工修改更安全

很多人以为批量替换危险、人工修改安全。在本章的语境里正好相反。`com.example.demo` 是一个带边界的完整标识符，批量替换它，命中范围是确定的；而人工修改容易被「这个词看起来像」误导，改到不该改的地方，且没有记录可查。

真正危险的不是「批量」，而是「裸词批量」。把 `demo` 当替换目标，不管批量还是手工，都会出事。把 `com.example.demo` 当替换目标，批量反而是最可靠的方式。

## 9.4 迁移必须留下书面清单，否则下一境会重踩同一个坑

本章踩到的三类故障——XML namespace、组件扫描根、配置前缀——都不是独特的知识，而是「不知道就会踩」的常规坑。它们的价值不在于当下解决，而在于被写进仓库：残留扫描脚本就是清单的可执行版本。

这也解释了为什么本章不惜多写两个脚本。脚本不是为了这一次换骨，是为了后面每一境都能一条命令验证「骨头还是正的」。工程资产的意义，永远大于本次任务的便利。

> 名字换完不算完
> 行为不变才交差
> 编译绿灯最易骗
> 扫描为空方心安

# 10、系统落地

原来有什么：一份能跑通 `/v1/models` 与 `/v1/chat/completions` 的 open-api Demo，结构可用，命名不可用。

本篇新增了什么：新的 Maven 坐标、新的根包 `cloud.joysky.llmgateway`、新的启动类、新的配置前缀、新的品牌名与镜像名、一份黄金基线响应、一个残留扫描脚本、一个冒烟回归脚本。业务代码一行没动。

现在能做什么：可以把它作为自研 Java LLM Gateway 的第 0 号基线提交，后续所有能力都在这套命名空间下生长；任何人 clone 下来都能用两条命令验证「骨头是正的」。

还缺什么：缺的是网关的本体语义。现在这份代码能转发请求，但「Provider 是什么、Deployment 是什么、LogicalModel 是什么、它们之间谁引用谁」，代码里还没有清晰的表达。名字换对了，骨架是对的，但骨架上的关节还没命名。

下一步如何演进：先用本体模型把网关的根本语义澄清清楚，再在确立的语义之上固化对外的 OpenAI 兼容契约与统一错误边界。顺序不能反——语义没定就先定协议，协议会长出一堆后来必须拆掉的结构。

> 旧骨换新根未动
> 基线立定待长肉
> 七模型里寻语义

# 12、作业

## 12.1 理解题：为什么「半迁移状态」比「完全未迁移状态」更危险？

参考答案：未迁移状态下，所有人对当前状态有共识，报错能立刻归因到旧代码；半迁移状态下，一部分代码在新包、一部分在旧包，故障只在特定路径触发，容易被误判为环境问题或上游问题，排查成本成倍上升。更关键的是，半迁移状态会让「我已经改完了」这个判断失真，而错误的完成判断比没有完成判断更危险。

## 12.2 实战题：写一个残留扫描脚本，并说明它应该检查哪几类字符串。

参考答案：脚本核心是 `grep -rn "$OLD_PKG" . --exclude-dir=.git --exclude-dir=target`，命中即 `exit 1`。除旧包名外，还应检查：旧配置前缀（如 `^demo:`）、旧类名（如 `DemoApplication`）、旧坐标（`<groupId>com.example</groupId>`）、旧镜像名与容器名、旧日志 logger 名。前四类可以放进同一个脚本，第五类属于部署清单，建议单列一份 checklist。

## 12.3 排障题：换骨后应用启动成功，但 `/v1/models` 返回 404，你的排查顺序是什么？

参考答案：先看启动日志中 `RequestMappingHandlerMapping` 是否注册了对应路径；若没注册，搜索 `@RestController` 确认 Controller 在哪个包；再确认启动类所在包与 Controller 所在包的层级关系，因为 Spring Boot 默认以启动类所在包为扫描根；最后检查启动类上是否存在 `scanBasePackages` 指向旧包。修复优先选用 `git mv` 启动类，而不是加注解覆盖扫描路径。

## 12.4 架构判断题：同事提议「既然都在改路径了，顺手把 Controller 拆成 service 分层吧」，本章该不该做？

参考答案：不该做。换骨与重构必须分属两次独立变更。混在一起的直接后果是行为可能变化，而一旦行为变化，基线 diff 就会失败，届时你无法区分失败来自包名迁移还是来自分层重构。正确做法是先把换骨做干净、把基线回归跑绿、提交并打上基线标签，再另开分支做分层重构——那时你仍然有基线可比。

> 理解半迁更危险
> 实战扫描做守卫
> 排障先看扫描根
> 判断题里守边界

# 13、思考

换骨这一章真正的对手不是包名，是「顺手」。顺手改一下注释、顺手拆一个类、顺手优化一段日志——每一处顺手都在把「行为不变」这条唯一的验收尺子磨掉。尺子一旦没了，换骨就从工程变成手感，而手感是不可交付的。

柳神法的隐喻之所以贴切，是因为它强调「涅槃后的新生」，而不是「推倒重来的革命」。旧骨架还在，生机从原根上长出来；只是旧的形骸必须彻底烧干净，烧一半留一半，新芽就长不出来。这就是半迁移状态最真实的写照。

所以本章沉淀下来的可复用判断只有三句：改名前先定界，界内批量、界外人工；改完后先扫描，扫描为空再谈行为；行为比对不通过，就绝不宣布换骨完成。三条都是机械规则，机械规则的价值在于它们不依赖任何人的记忆。

> 换骨不是重构
> 改名前先定界
> 行为不变为尺
> 基线立则后稳
