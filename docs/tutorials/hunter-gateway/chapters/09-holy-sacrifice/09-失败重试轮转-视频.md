第九章只做失败轮转：Timeout、Retry、Fallback 全留痕，关掉主 Provider 能自动切备份才算过。
客户不关心你怎么重试，他只记得刚才那一次成了还是挂了。价值一句话：同一个模型，永远有第二次机会。
上周三起工单全是超时直接抛错，用户点一次没反应就走了。九成投诉不是模型不行，是没人接住失败。
云厂商 SDK 都做指数退避，无脑重试会把故障放大。公开证据：429、503 必须退避，400 重试毫无意义。
一期只做三件：Timeout 判定、Retry 策略、同模型候选 Deployment 间 Fallback。流式首块一出，不静默换供应商。
两个方案：网关层统一重试拦截器，或下沉到每个 Provider 适配器自管。前者集中可控，后者低耦合但策略会漂。
最怕重试撞上半成功：请求发出去了，钱花了，日志没落。每次上游调用必须先写 RouteAttempt，再决定重不重试。
现在没有基线就等于没有验收。先统计超时占比和重试命中率，否则上线后没人知道是变好了还是变吵了。
开发者搜 LLM Gateway 重试怎么做、超时怎么兜底。把 RetryPolicy 字段写成可检索文档，比投广告便宜得多。
这次不建议投付费：客单价低，CAC 打不平，转化事件也没埋。要投先埋 route_attempt_fallback，跑两周看数据。
多一次重试就多一次 token 账单。给条线：最多三次，退避 0.5 到 4 秒，月度上游成本涨幅不超过 8%。
要写进合同的是：Fallback 到别的 Deployment，数据落在哪、日志留多久。RouteAttempt 必须可审计，出事才说得清。
先 RetryPolicy 结构，再 RouteAttempt 落库，最后时间线页面。分支 chapter/09-retry-fallback，一个提交收口。
接受重试上限三次。销售话术改成一句：同一模型自动兜底，不问客户要第二次点击。流式不切换，也不许承诺。
一线标准：请求详情要看见每次 RouteAttempt、耗时、失败码，客服才敢回话。看不见时间线，这功能等于没做。
复核过：只重试 network、connect、read timeout 和 429、502、503、504。400、401、403 与上下文超限默认不重试。
按基线再收一版：一期不做跨 LogicalModel 兜底，只做同模型候选 Deployment。页面只做时间线，不做策略编辑器。
选网关层拦截器。牺牲的是适配器自由度，换来的是一份可审计、可解释的轮转链，重试决策只在一处发生。
RouteAttempt 先落 pending，结束再改状态，重试共用同一个 traceId。Fallback 只在候选 Deployment 间切，首块已出就终止。
成功线：fallback 后成功率不低于 97%，P95 延迟增幅不超 15%。停止线：重试放大量过 20% 或成本涨幅破 8%，立即降级。
写两篇：超时重试怎么设计、RouteAttempt 怎么排查。落到 RetryPolicy 字段表，验证指标是这些页带来的注册。
这次不投付费，只埋 route_attempt_fallback 事件。两周后自然流量带不动注册，再给两千块预算测一次。
预算线：这块两周开发，上游成本涨幅 8% 就是止损线。超出自动把 maxAttempts 降到一，宁可失败也不让账单失控。
边界过了：RouteAttempt 只记请求 ID、Deployment、状态码、耗时，不落 prompt 原文。日志留 30 天，切换写进协议。
Owner 定死：Alex 做 RetryPolicy 和 RouteAttempt，两天；Emma 出验收用例，三天；Bob 审时间线，五天。周五合并。
定了，就按今天说的做。验收一条：关掉主 Provider 自动切备份，全链路留痕。做不到，代码直接回退。
