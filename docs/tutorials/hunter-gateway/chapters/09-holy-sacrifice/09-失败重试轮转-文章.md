# 轮回宝术：把 Timeout、Retry、Fallback 炼成可解释的失败轮转链

> 重试不是勇气，轮转才是秩序，留痕才是可解释。

```text
[读者] Java 后端/网关工程师，正在给 LLM Gateway 接多家上游
[痛点] 上游一抖动整条请求就 500，想重试又怕重试错
[现在读] 第 09 境轮回宝术，要把失败轮转做成可验证的链路
[读完] 能落地一套带 RouteAttempt 留痕的 Timeout/Retry/Fallback
```

```text
[旧方案] Demo 单上游直连，失败即抛 500
    |
    v
[新需求] 同一 LogicalModel 挂多个 Deployment，上游会超时、限流、502
    |
    v
[冲突] 没有超时预算、没有可重试白名单、没有候选游标，重试只会放大故障
    |
    v
[后果] 用户拿 500，运维查不到坏在哪一跳，Token 还在白烧
```

我是老李，做过几年交易系统的稳定性，现在在做一套 Java 轻量级 LLM Gateway。项目基线是 litellmgateway 仓库里那份 open-api.zip Demo，我们的原则是不重新造骨架：先逆向 Demo，再改包名与项目名，然后在既有代码上增量长出网关能力。

前八境我们把协议、Pipeline、Provider 适配、智能路由、三层归一都立起来了。到了这一境，请求已经能被正确选到某个 Deployment，但选完之后发生什么，代码里几乎是一片空白：上游慢、上游返回 502、上游限流，网关只会把异常原样抛给调用方。

可靠性这件事，从来不是“加个 for 循环重试三次”就能交差的。它更像轮回：一次失败不是终点，而是一次轮转的开始；但轮转必须遵守规则，否则就是灾难。

上游抖动时，网关到底该不该替用户重试？

如果该重试，是重试同一个 Deployment，还是轮转到同一 LogicalModel 下的另一个候选？

如果重试把上游打得更慢，甚至把限流打成封禁，这笔账又该谁来付？

# 01、故事

周一下午两点，值班群里开始刷屏。有业务方反馈，接入网关的客服助手会间歇性报错，前端拿到的是一句冷冰冰的 `upstream error`。

我打开日志，看到的是这样的画面：某家上游在 14:02 到 14:05 之间连续出现读超时，网关把每一个超时都变成了 500 返回给调用方。而与此同时，我们的备份上游一直健康在线，只是没有任何一个请求被路由过去。

任务是：在同一个 LogicalModel 下挂多个候选 Deployment，让失败的请求能够按规则轮转到下一个候选，并且完整记录每一次上游调用的去向、状态与耗时。

当时的方案非常朴素。`GatewayService` 里只有一个 `defaultDeployment`，调用上游的代码是同步阻塞的：拿 endpoint、发请求、拿响应。没有任何超时配置，没有状态码分类，也没有任何“候选”概念，Deployment 在代码里甚至只是个字符串常量。

变化来自运营侧。为了让成本可控、可用性可兜底，我们接入了第二家、第三家上游：同一个逻辑模型 `gpt-4o-mini`，背后可以有 Azure 的部署、也可以有官方直连的部署，甚至可以有一个国产模型的兼容部署。它们的能力对等，但稳定性、限流阈值、网络质量完全不同。

这就把旧方案顶到了墙角：只有一条路的时候，“失败”只有一个含义；有多条路的时候，“失败”至少有五种含义——网络没连上、连上了没读完、上游说 429、上游说 502、上游说你参数不对。这五种失败里，只有前面四种值得轮转，最后一种必须立刻停手。

# 02、问题

旧方案失效的地方非常具体：它把“上游故障”和“请求本身有问题”当成同一类事件处理，都是抛出异常、都是 500。

业务影响随之而来。调用方看到的是 100% 的失败率，而真实情况是某一个上游在抖；重试逻辑一旦简单粗暴地加在异常上，就会把已经过载的上游再打三遍，把偶发抖动升级成雪崩。

技术表现上，至少有三层问题：

第一层是超时缺位。`java.net.http.HttpClient` 默认没有请求级读超时，一次卡住的连接可以挂住一个工作线程几十秒甚至更久，线程池被打满之后，健康的上游也进不来。

第二层是失败不可分类。代码里只有 `catch (Exception e)`，无法区分“可以再试一次”和“再试一万次也一样”。

第三层是无可观测。请求结束后，没人知道这次请求走的是哪个 Deployment、试了几次、每次耗时多少。排查只能靠猜。

这一境的完成标准必须能被验证，我把它写成四条：

一，关闭主 Provider（把主候选的 endpoint 指向不可达地址或直接停掉其服务）之后，请求能自动切到备份 Deployment 并成功返回；

二，客户端参数错误（400）、鉴权失败（401/403）、上下文超限，只产生一次 RouteAttempt，绝不重试；

三，429/502/503/504 与 connect/read timeout 可以触发重试，且重试会在候选 Deployment 之间轮转；

四，请求详情页能看到完整的 RouteAttempts 时间线，包含每次的 deploymentId、httpStatus、errorClass、latencyMs、outcome。

# 03、原理

要把失败轮转做对，先得承认一件事：Timeout、Retry、Fallback 不是三件事，而是同一条链上的三个环节，它们的共同输入是“失败分类”，共同输出是“一次可解释的决策”。

Timeout 是预算：它决定我们愿意等多久。connect timeout 管的是“连不上”，read timeout 管的是“连上了但没说完”。这两者在用户感知上都是慢，但在工程上完全不同——前者通常意味着网络或 DNS 问题，后者往往意味着上游在排队或已经过载。

Retry 是分类之后的再下注：只有那些“换个时间点或换个上游就可能成功”的失败才值得再下注。HTTP 语义给了我们很好的抓手：429 表示限流，502/503/504 表示网关或上游的临时不可用，这些都是典型可恢复信号；而 400（请求构造错误）、401/403（凭据或权限问题）、上下文超限（模型侧硬约束），重试多少次结果都一样，只会浪费一次上游调用配额。

Fallback 是轮转的落点：它必须有明确的作用域。同一个 LogicalModel 下的候选 Deployment 是等价的，可以互相顶替；跨 LogicalModel 切换则改变了语义，那不属于 Fallback，属于改需求。

这里有一个反直觉判断：重试并不能提升单次请求的成功概率，它只是把一个“单次成败”变成了“多次独立尝试的联合分布”。在多数上游故障场景下，重试之所以有效，是因为故障是短暂的、且候选之间彼此独立；而一旦故障来自过载或共享链路，重试反而会通过增加负载降低整体成功率。所以说重试是放大器，不是治愈术——它放大的是候选之间的独立性，也放大你对上游的压力。

第二个反直觉判断来自流式：流式响应一旦输出了首块内容，就不该再做“无感的 Provider 切换”。因为首块之后，客户端已经看到了部分语义，此时换一个上游从头生成，会得到拼接错乱的内容；这不是容错，这是数据损坏。所以流式的边界应该是“首块之前可切换，首块之后只可中断”。

# 04、架构

```text
[输入] OpenAI 兼容 /v1/chat/completions 请求
    |
    v
[模块] Gateway Pipeline → LogicalModel 解析 → CandidateCursor 选 Deployment
    |
    v
[数据/状态] RetryPolicy + RouteAttempt(attemptNo, deploymentId, status, errorClass, latencyMs)
    |
    v
[处理] Timeout → 失败分类 → backoff → 游标推进 Fallback → 流式首块锁死
    |
    v
[输出] 上游响应 / 统一错误体 + RouteAttempts 时间线
```

这个结构的边界很清楚：轮转只发生在同一个 LogicalModel 的候选列表内，游标是单向推进的，不回头、不循环。一次请求最多尝试 `maxAttempts` 次，并且尝试次数不能超过候选数量——因为我们选择的是“每次重试都换候选”，而不是“在同一个故障上游上反复撞墙”。

收益是可解释性：每一次上游调用都留一条 RouteAttempt，失败终局时你能一眼看出“第 1 次打到主候选读超时，第 2 次打到备份候选 200 成功”。代价是多了一个有状态的游标对象，以及一张会随流量增长的 attempt 记录表；后者需要按 requestId 索引，并配合保留策略清理。

适用条件也需说明：只有当候选 Deployment 真正等价（同一 LogicalModel、能力对等）时，Fallback 才成立；如果候选之间的模型能力差异很大，那么“切过去”本质上是在改变回答质量，这属于产品决策，不属于重试策略。

# 05、实战一次

环境与版本：JDK 17、Spring Boot 3.x（沿用 Demo 的 Web 层）、`java.net.http.HttpClient` 作为上游客户端。为保持轻量，我不引入额外的重试库，轮转逻辑用显式循环表达，让每一次尝试都可控、可记录。

依赖层面没有新增：`java.net.http` 属于 JDK 自带，持久化沿用 Demo 已有的 JDBC 访问方式。

先定义策略对象，把“可重试”的判定集中到一处：

```java
package com.example.gateway.routing;

import java.time.Duration;
import java.util.Set;

public record RetryPolicy(
        int maxAttempts,
        Duration baseBackoff,
        double multiplier,
        Duration maxBackoff,
        Set<Integer> retryStatus,
        Set<String> retryErrorClass
) {
    public static RetryPolicy standard() {
        return new RetryPolicy(
                3,
                Duration.ofMillis(200),
                2.0,
                Duration.ofSeconds(2),
                Set.of(429, 502, 503, 504),
                Set.of("CONNECT_TIMEOUT", "READ_TIMEOUT", "CONNECTION_RESET")
        );
    }

    public boolean retryableStatus(int status) {
        return retryStatus.contains(status);
    }

    public boolean retryableError(String errorClass) {
        return retryErrorClass.contains(errorClass);
    }

    public Duration backoffFor(int attemptNo) {
        double factor = Math.pow(multiplier, Math.max(0, attemptNo - 1));
        long millis = (long) Math.min(maxBackoff.toMillis(), baseBackoff.toMillis() * factor);
        return Duration.ofMillis(millis);
    }
}
```

然后是留痕对象与候选游标。游标是这一境的核心状态，它负责“轮转”这件事的秩序：

```java
package com.example.gateway.routing;

import java.util.List;

public final class CandidateCursor {
    private final String logicalModel;
    private final List<String> deployments;
    private int index;

    public CandidateCursor(String logicalModel, List<String> deployments) {
        if (deployments == null || deployments.isEmpty()) {
            throw new IllegalArgumentException("no candidate deployment for " + logicalModel);
        }
        this.logicalModel = logicalModel;
        this.deployments = List.copyOf(deployments);
    }

    public String current() {
        return deployments.get(index);
    }

    public boolean hasNext() {
        return index + 1 < deployments.size();
    }

    public void advance() {
        if (!hasNext()) {
            throw new IllegalStateException("cursor exhausted for " + logicalModel);
        }
        index++;
    }

    public int index() {
        return index;
    }
}
```

上游客户端负责把“异常”翻译成可分类的 errorClass，这是让白名单能工作的前提：

```java
package com.example.gateway.upstream;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpConnectTimeoutException;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpTimeoutException;
import java.time.Duration;

public final class UpstreamClient {

    private final HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))
            .build();

    public Outcome call(String endpoint, String apiKey, String jsonBody, Duration readTimeout) {
        HttpRequest request = HttpRequest.newBuilder(URI.create(endpoint))
                .timeout(readTimeout)
                .header("Content-Type", "application/json")
                .header("Authorization", "Bearer " + apiKey)
                .POST(HttpRequest.BodyPublishers.ofString(jsonBody))
                .build();
        try {
            HttpResponse<String> response =
                    client.send(request, HttpResponse.BodyHandlers.ofString());
            return new Outcome(response.statusCode(), response.body(), null);
        } catch (HttpConnectTimeoutException e) {
            return new Outcome(null, null, "CONNECT_TIMEOUT");
        } catch (HttpTimeoutException e) {
            return new Outcome(null, null, "READ_TIMEOUT");
        } catch (java.io.IOException e) {
            return new Outcome(null, null, "CONNECTION_RESET");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return new Outcome(null, null, "INTERRUPTED");
        }
    }

    public record Outcome(Integer status, String body, String errorClass) {
    }
}
```

最后是轮转执行器。注意这里的判定顺序：先看有没有 HTTP 状态码，再决定是否看 errorClass；只要状态码存在，就以状态码语义为准。

```java
package com.example.gateway.routing;

import com.example.gateway.upstream.UpstreamClient;

import java.time.Duration;
import java.util.ArrayList;
import java.util.List;

public final class RouteExecutor {

    private final DeploymentRegistry registry;
    private final UpstreamClient upstreamClient;
    private final AttemptRecorder recorder;

    public RouteExecutor(DeploymentRegistry registry,
                         UpstreamClient upstreamClient,
                         AttemptRecorder recorder) {
        this.registry = registry;
        this.upstreamClient = upstreamClient;
        this.recorder = recorder;
    }

    public RouteOutcome execute(String requestId, String logicalModel, String jsonBody) {
        List<Deployment> candidates = registry.candidatesOf(logicalModel);
        RetryPolicy policy = registry.retryPolicyOf(logicalModel);
        CandidateCursor cursor = new CandidateCursor(
                logicalModel, candidates.stream().map(Deployment::id).toList());
        List<RouteAttempt> attempts = new ArrayList<>();

        int attemptNo = 0;
        while (true) {
            attemptNo++;
            Deployment deployment = candidates.get(cursor.index());
            long started = System.currentTimeMillis();
            UpstreamClient.Outcome outcome = upstreamClient.call(
                    deployment.endpoint(), deployment.apiKey(), jsonBody, deployment.readTimeout());
            long latency = System.currentTimeMillis() - started;

            boolean retryable = outcome.status() != null
                    ? policy.retryableStatus(outcome.status())
                    : policy.retryableError(outcome.errorClass());

            boolean budgetLeft = attemptNo < policy.maxAttempts();
            boolean candidateLeft = cursor.hasNext();
            boolean willRetry = retryable && budgetLeft && candidateLeft;

            RouteAttempt attempt = new RouteAttempt(
                    requestId, attemptNo, logicalModel, deployment.id(),
                    outcome.status(), outcome.errorClass(), started, latency, !willRetry,
                    retryable ? (willRetry ? "RETRY" : "EXHAUSTED") : "TERMINAL");
            attempts.add(attempt);
            recorder.record(attempt);

            if (!retryable) {
                return RouteOutcome.terminal(outcome, attempts);
            }
            if (!willRetry) {
                return RouteOutcome.exhausted(outcome, attempts);
            }

            sleep(policy.backoffFor(attemptNo));
            cursor.advance();
        }
    }

    private void sleep(Duration duration) {
        try {
            Thread.sleep(duration.toMillis());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("retry backoff interrupted", e);
        }
    }
}
```

V1 到这里就跑通了：超时有预算、失败有分类、轮转有游标、每次尝试有留痕。接下来留下两个显式问题：一是退避没有抖动，多个请求同时失败时会形成同步重试的波峰；二是流式请求在首块之后的行为还没有被约束住。

# 06、排查

现象一：灰度环境里，主候选返回 502 时，日志显示尝试了 3 次，但每次的 `deploymentId` 都是同一个，备份候选从未被调用。

怀疑：候选列表加载为空，或者 Fallback 根本没接上。

检查：查 `route_attempt` 表里该 requestId 的全部记录，再对照配置里的候选数量。

证据：三条 RouteAttempt 的 `deploymentId` 全部是 `azure-east`，而 `candidates` 配置里确实有两个 Deployment。

根因：`willRetry` 判定用的是 `cursor.hasNext()`，但重试分支里只做了退避 `sleep`，漏掉了游标推进；游标永远停在 index 0。

修复：在重试分支显式调用 `cursor.advance()`，并把“游标推进”写进单元测试断言：第二个 attempt 的 deploymentId 必须等于候选列表的第二项。

现象二：调用方传了一个非法参数，上游返回 400，但网关重试了三次，上游日志里出现了三条相同请求。

怀疑：状态码白名单没生效。

检查：把 `RetryPolicy` 的判定顺序打点，同时核对 RouteAttempt 的 `httpStatus` 字段。

证据：三条 RouteAttempt 的 `httpStatus` 全是 400，`outcome` 全是 `RETRY`。

根因：判定写成“先看 errorClass，非空即视为可重试；状态码仅在没有异常时参与判断”。而某些 4xx 响应在读取响应体阶段抛出了 IO 异常，errorClass 非空，于是被误判为网络故障。

修复：把判定顺序反过来——只要 `httpStatus != null`，就只按状态码白名单判定，errorClass 仅在无状态码（即请求根本没拿到响应）时参与判断。

**错误尝试：** 我一开始的写法是在 `catch (Exception e)` 里统一判断“是否超过 maxAttempts，没超过就重试”。这条路看起来最省事，但它错在把“失败”当成同质事件：它无法区分 400 与 502，也无法区分读超时与鉴权失败。结果是参数错误被重试、鉴权问题被重试、上下文超限被重试，上游压力被平白放大，而真正的根因被掩盖在重试噪声里。

**错误尝试：** 我还试过用响应式链路的 `retryWhen` 一把梭，把重试策略声明式地挂在调用链上。它错在两件事：其一，attempt 级别的上下文（这次打的是哪个 Deployment、耗时多少）很难跨算子传递，留痕会变成拼凑；其二，流式场景下一旦首块已经下发，链路上的自动重试会在客户端无感的情况下换上游继续产出，造成内容拼接错乱。最终还是回到显式循环，因为可靠性逻辑必须能被逐行解释。

# 07、优化

针对现象二，根因是判定顺序，V2 的第一处修改就是把状态码优先级显式化：

```java
boolean retryable = outcome.status() != null
        ? policy.retryableStatus(outcome.status())
        : policy.retryableError(outcome.errorClass());
```

这样写的原因是把“上游已经明确表态”与“根本没听到回话”分开：前者按 HTTP 语义走白名单，后者按传输层错误分类走白名单。新行为是 400/401/403 与上下文超限只产生一条 `TERMINAL` 记录，直接返回给调用方；429/502/503/504 与 CONNECT_TIMEOUT/READ_TIMEOUT/CONNECTION_RESET 才进入轮转。验证方式是构造一个返回 400 的桩上游，断言 `route_attempt` 只有一条记录且 `outcome = TERMINAL`。

针对现象一，根因是游标未推进。V2 把“推进”变成重试路径上不可跳过的步骤，并顺手把候选用尽作为终止条件之一：`willRetry = retryable && budgetLeft && candidateLeft`。原因是我们不想在同一个已知故障的 Deployment 上反复重试——那是最容易把偶发抖动放大成雪崩的做法。新行为是：有备份候选时逐跳轮转，没有候选时立即以 `EXHAUSTED` 收口。

第三处修改是给退避加抖动。原因很直接：固定倍率的指数退避会让同一时刻失败的请求在同一个时间点再次涌向上游，形成同步波峰。做法是在 `backoffFor` 的结果上乘一个随机系数（例如 0.5 到 1.0 之间），把重试时间打散。

第四处修改是流式边界的硬约束：在流式路径上增加一个 `firstChunkFlushed` 标志，一旦首块已写出，任何失败都转为中断当前流并向客户端发送结束标记，不再触发 Fallback。原因与原理章一致——首块之后的无感切换会造成内容语义损坏，这比一次可见的失败更糟。

# 08、演进

```text
[同一输入]
    |
    +--[V1] 单 Deployment 直连，失败即抛；重试=全局开关
    |       代价：放大故障、无留痕、无法解释
    |
    +--[V2] 候选游标 + 白名单重试 + 抖动退避 + RouteAttempt 落库 + 流式首块锁死
    |       代价：多一份状态与存储，判定顺序必须严格
    |
[Trade-off]
得到：可解释的失败轮转与可追溯的调用链
失去："所有错误都重试一遍"的省事
边界：仅同 LogicalModel 候选间轮转；流式首块后不再切换
```

正确性上，V1 只能保证“请求发出去了”，V2 能保证“每一次失败都有明确归属”。稳定性上，V1 在抖动时会把压力原样放大，V2 通过状态码白名单与候选轮转把压力分散到真正健康的候选。

复杂度上，V1 是一段直线代码，V2 多了一个有状态的游标、一个策略对象和一张记录表——这份复杂度不是装饰，它是可解释性的价格。成本上，RouteAttempt 会随请求量线性增长，需要按 requestId 建索引并设置保留窗口；如果放任它膨胀，查询会先变慢，然后是写入变慢。

适用范围上，这套机制成立的前提是候选等价。如果同一个 LogicalModel 下的 Deployment 能力不一致，轮转就会变成“随机降级”，那属于产品策略而非容错策略。遗留问题也很清楚：本篇只处理“失败后的轮转”，不处理“连续失败后的准入控制”——那是下一境的事。

# 09、洞见

## 9.1 失败分类必须先于失败处理

所有重试事故的源头，几乎都是因为把失败当成同质事件。Timeout、Retry、Fallback 三者的公共前置条件，是一个能被判断的分类器：先看有没有 HTTP 状态码，再看传输层错误类型，最后才轮到策略决策。分类器写错，后面的策略再精巧都是错的——上一章的两条排查链，根因都不在策略，而在判定顺序与状态推进。

## 9.2 重试不提升成功率，它只改变概率的形状

反直觉判断：重试并不会让“这一次请求”变得更容易成功，它只是把一个单点概率变成了多次独立尝试的联合概率。它的收益完全取决于候选之间的独立性与故障的短暂性。当故障来自共享链路或全局过载时，重试会把失败概率推得更高，因为它给已经过载的系统又加了一份负载。所以重试策略里的每一个数字——maxAttempts、backoff、白名单——本质上都是对“独立性”的假设，而不是对“运气”的期待。

## 9.3 流式的首块是不可逆边界

反直觉判断：流式场景下，“无感切换 Provider”并不是更高级的容错，而是一种数据损坏。因为一旦首块内容已经抵达客户端，客户端就已经消费了这部分语义，此时换一个上游从头生成，得到的是两段拼接的内容。真正的边界应该划在首块之前：首块之前可以自由轮转，首块之后只能中断并明确告知。可解释性在这里的含义是：宁可让用户看到一次诚实的失败，也不让用户看到一段拼接错乱的“成功”。

## 9.4 留痕是可靠性的一等公民

RouteAttempt 不是日志的附属品，而是可靠性机制的一部分。没有它，“关闭主 Provider 后自动切备份”这件事就无法被验证——你只能看到最终成功，看不到中间轮转了几次、在哪个候选上失败。可解释的定义很朴素：给定一个 requestId，你能复述出它经历过的每一跳。这也是把可靠性从“感觉上更稳了”变成“可以被证明”的分界线。

# 10、系统落地

原来我们有什么：一份逆向后的 Demo 骨架、完成换骨的项目与包名、七个本体模型、OpenAI 兼容协议层、Gateway Pipeline、Provider 适配与 Deployment 选择、以及 Routing 的三层归一。请求能被正确路由到某个候选 Deployment，但选完之后没有韧性。

本篇新增了什么：`RetryPolicy` 策略对象（maxAttempts、backoff、retryStatus、retryException）、`CandidateCursor` 候选游标、`RouteAttempt` 留痕模型与落库、`RouteExecutor` 显式轮转循环，以及流式首块锁死标志。管理侧新增请求详情页的 RouteAttempts 时间线。

现在能做什么：关掉主 Provider 后请求自动切到备份并完整留痕；400/401/403 与上下文超限一次即止；429/502/503/504 与 connect/read timeout 按白名单轮转；重试退避带抖动，避免同步波峰。分支与提交按计划落位：分支 `chapter/09-retry-fallback`，提交 `feat(ch09): add retry fallback and route attempt tracing`。验收路径就是那句话——关闭主 Provider 后自动切备份并完整留痕。

还缺什么：其一，连续失败之后的“主动熔断”还没有，当前只是被动重试；其二，RouteAttempt 目前是逐条写入，缺少保留策略与归档；其三，流式的首块锁死只做了拦截，还没有做“首块之后失败”的客户端协议约定。

下一步如何演进：把健康检查与熔断接进来，让连续的 RouteAttempt 失败能自动把某个 Deployment 从候选池里摘出去，并在恢复后重新放回；这一境只负责轮转，准入控制留给第 10 境。

```text
Q1 → 该不该替用户重试？只有可恢复的失败才重试：429/502/503/504 与 connect/read timeout 进白名单，400/401/403 与上下文超限一次即止
Q2 → 重试同一个 Deployment 还是轮转候选？轮转同一 LogicalModel 下的候选，游标单向推进，候选用尽或次数用尽立即收口

```

# 12、作业

## 12.1 理解题：为什么 400 和 401 必须默认不重试，而 429 和 503 可以重试？

参考答案：判断依据不是“严重程度”，而是“重试之后结果是否会改变”。400 表示请求本身在语法或参数上不合法，401/403 表示凭据或权限不成立，上下文超限表示超出了模型侧的硬约束——这三类都是确定性失败，重试只会重复消耗上游配额。429 表示限流、502/503/504 表示临时不可用，它们带有明确的时间语义，换个时间点或换个候选就可能成功，属于可恢复失败。白名单的本质，就是只对“时间或位置相关”的失败再下注。

## 12.2 实战题：如何让重试不会在同一时刻形成波峰？

参考答案：把固定倍率的指数退避改成带随机抖动的退避，即在 `baseBackoff * multiplier^(attemptNo-1)` 的结果上乘一个区间系数（例如 0.5～1.0），并对结果取 `maxBackoff` 上限。同时把“每次重试推进候选游标”作为硬约束，让同一时刻的失败请求分散到不同上游。验证方式是构造 N 个并发失败请求，观察 RouteAttempt 的 `startedAtEpochMs` 是否被拉开发散，而不是聚集在同一毫秒附近。

## 12.3 排障题：某次请求最终成功，但 `route_attempt` 只有一条记录且 deploymentId 是主候选，备份候选从未出现，请给出排查顺序。

参考答案：先确认这次请求是否真的经历过失败——若主候选首次即成功，一条记录就是正确行为，不要制造问题。若确认上游曾抖动，则依次核对：候选列表在配置中是否真的加载出两条；`RouteExecutor` 是否在重试分支调用了 `cursor.advance()`；`willRetry` 的三个条件（retryable、budgetLeft、candidateLeft）中哪一个先为 false；以及 `recorder.record` 是否在 return 之前被短路跳过。最容易被忽略的是最后一条：记录语句放在分支之后，一旦提前返回就永远不会有第二条记录。

## 12.4 架构判断题：如果把最大候选数设为 5、maxAttempts 设为 10，是否意味着更高的可用性？

参考答案：不一定，而且往往更差。轮转的价值来自候选之间的独立性，而不是尝试次数本身。maxAttempts 超过候选数时，必然出现在同一 Deployment 上重复尝试的情况，这在故障场景下等同于对已经异常的上游加压。更合理的配置是让 maxAttempts 不超过候选数量（或略大一点），并把“连续失败后把候选摘出池子”的准入控制作为下一步演进，而不是靠堆次数换可用性。

# 13、思考

这一境真正解决的，不是“失败怎么办”，而是“失败如何被分类、被轮转、被解释”。Timeout 定义了等待的边界，Retry 定义了再下注的条件，Fallback 定义了轮转的落点，RouteAttempt 定义了决策的可验证性。四者缺一，可靠性就退化成了玄学。

最难的部分从来不是写循环，而是忍住不写那些“看起来反正不会错”的循环：不重试 400，不在首块之后切换，不在同一个故障上游上反复撞墙。这些克制构成了秩序，而秩序才是轮回的本意——轮转不是无限次重开，而是在规则之内，把一次失败交给下一个候选。

> 一念辨边界
> 一证定根因
> 一改知取舍
> 一轮见轮回
