# 六道轮回天功：可插拔 Gateway Pipeline 与 Controller 瘦身

> Controller 塞满鉴权限流预算，改一条链路要动十个方法

```text
[读者] 把 LLM 网关从 Demo 推向生产的 Java 后端
[痛点] Controller 里堆着鉴权、限流、预算、路由分支
[现在读] 链路已经长到无法靠读代码确认执行顺序
[读完] 能把策略编排成可插拔 Pipeline，Controller 只做协议适配
```

```text
[旧方案] Controller 顺序调用 auth、limit、route 三个 Service
    |
    v
[新需求] 追加 Budget、Usage、Cost，并要求流式与非流式共用前置链路
    |
    v
[冲突] 每加一个能力都要改 Controller，顺序与短路散落在 if 里
    |
    v
[后果] 策略不可测、不可观测，回归只能靠人工点页面
```

我是老李。这个项目的底座是 lifuchun522/litelmgateway 仓库里 open-api.zip 那份 Demo，前面四境已经走完：逆向、换包名、本体七模型、OpenAI 兼容协议。到了列阵境，要解决的问题不再是「能不能调通」，而是「谁来决定先做什么」。

V1 的方案很朴素：Controller 里顺序写 authService.check()、rateLimitService.tryAcquire()、routeService.pick()，最后调 provider。四个方法排排坐，读起来一目了然，写起来也快，Demo 阶段这套确实够用。

但列阵境要加的东西变多了：Budget 要算钱、Usage 要记账、Cost 要落库、流式和非流式还要共用同一套前置校验。**任务是**把这些能力编排成一条可插拔的流水线，让 Controller 退回到「只做协议适配」的位置。注意，这里说的是「编排」，不是「再多写几个 Service」。

为什么 Controller 会越写越厚？

是继续在 Controller 里加 if，还是抽一层显式的 Pipeline？

如果选错了，等到第七个能力加进来的时候，会付出什么代价？

# 01、故事

现场是这样的：网关已经能通过 OpenAI SDK 跑通单 Provider 的对话接口。运维同学提了三个需求——不同 Project 要有各自预算、不同 VirtualKey 要有各自限流、出错时必须知道是链路哪一步挂的。

当前方案就是那个「排排坐」的 Controller。四个 Service 依次调用，靠行序表达依赖关系：先鉴权再限流，先限流再算预算，路由之后才能调上游，调用结束后才记 Usage。这套顺序从来没有写进任何接口，它只存在于作者脑子里和代码的行序里。

变化来了。Budget 必须在 RateLimit 之后——先挡掉超频请求再算钱，否则一个刷接口的 Key 能把当天的账算爆；Usage 必须在 ProviderInvoke 之后——不知道真实 token 数就没法记账。这两个「必须」和原来那四个「必须」绑在一起，组成一条越来越长的隐式契约。

冲突在一次常规改动中暴露：有人为了让预算更早生效，把 Budget 挪到了 RateLimit 前面。测试环境没暴露问题，因为测试流量根本不会触发限流。这个顺序知识的唯一载体，是某个人手上的那次提交。

> 顺序藏在行间
> 无人说得清因果
> 一改便生疑云
> 先立显式骨架

# 02、问题

旧方案失效的根因很直接：Controller 的行序被当成了契约，但行序既不可测，也不可被外部声明。

业务影响是双份的。第一份是回归成本——每次新增一个治理能力，都要重新确认整条链路的顺序，人工点一遍。第二份是沟通成本——需求方问「超预算的请求会不会先被限流」，没人能凭代码一眼回答。

技术表现有三个：顺序不可测，因为顺序是语句而非数据；短路不一致，有的地方失败返回、有的地方抛异常、有的地方只是打日志继续跑；事件缺失，链路走到哪一步没有统一的可观测输出，排查只能靠翻 log.info。

可验证的完成标准我定成五条：第一，Controller 方法体内不出现任何策略判断，只做协议适配与 RuntimeContext 构造；第二，链路顺序由 order 字段决定，改顺序不需要改 Controller；第三，任一 stage 失败返回固定错误码并停止后续 stage；第四，每个 stage 产生一条带 requestId、traceId 的事件；第五，流式与非流式走同一条前置链路。

> 隐式契约最深
> 加一能力动全身
> 回归只能靠点
> 标准先写清楚

# 03、原理

本篇只讲两个概念的分工：GatewayFilter 和 GatewayPolicy。

GatewayFilter 是链上的执行单元，它有名字、有序号、拿到 RuntimeContext 和 GatewayChain，返回 StageResult。它决定自己要不要推进链条。GatewayPolicy 不含链路推进语义，它是纯判定或纯变换对象，被 Filter 组合复用。比如 BudgetPolicy 只回答「这次请求预计花费是否超限」，至于是哪个 Filter 调它、调完要不要短路，由 Filter 决定。把两者混成一个接口，最后就会得到一个既能推进链路、又能算钱、还能读库的上帝类。

**反直觉判断：Pipeline 的价值不是让代码变少，而是让代码变多。** 它会多出接口、多出 order 常量、多出错误码枚举、多出一个装配 Bean。它唯一换来的东西，是把「顺序」从人的记忆里搬进一个可被排序、可被断言、可被打印的集合里。这个交换在链路只有三步时不划算，在链路有十步时非常划算。

第二个原理是 RuntimeContext 的所有权。它在 Pipeline 入口被创建，身份字段（requestId、traceId、projectId、keyId、logicalModel、stream）一旦设定就不再变；解析出来的中间结果（virtualKey、deploymentId、usage、cost）放在可写的 attributes 里。这样任何一个 Filter 都不能偷偷把 logicalModel 改掉，而路由结果又能被后面的 Usage 读到。

**反直觉判断：热路径读内存快照，比读数据库更「正确」。** 控制面和数据面对一致性的要求不同。管理页要的是「我改完之后再查能看到新值」，网关请求要的是「这一整条链路看到的是同一版配置」。如果链路上每个 stage 各自查库，同一次请求可能在 Auth 看到旧 Key、在 Budget 看到新预算，链路内部自相矛盾。所以构造 RuntimeContext 时绑定一份 RuntimeConfigSnapshot，全程只读它。

第三个原理是短路的显式化。链上每个 Filter 都要能回答一句话：我失败时，后面的人还跑不跑。答案是分两类——前置 stage（Auth、Permission、RateLimit、Budget、ModelResolve、Route）失败必须终止；后置 stage（Usage、Cost、Log）失败只记录，不改变已经产生的响应。

> 责任链非为少写
> 顺序本是契约
> 快照胜似实时
> 一致先于最新

# 04、架构

```text
[输入] OpenAI 兼容 HTTP 请求 + VirtualKey
    |
    v
[模块] GatewayPipeline（ordered GatewayFilter 链）
    |
    v
[数据/状态] RuntimeContext + RuntimeConfigSnapshot（只读）
    |
    v
[处理] Auth → Permission → RateLimit → Budget → ModelResolve → Route → ProviderInvoke → Usage → Cost → Log
    |
    v
[输出] SSE 流 / JSON 响应 + 每 stage 一条可观测事件
```

边界划在这里：Pipeline 不管 HTTP 编解码、不管 SSE 帧格式、不管 OpenAI 错误体长什么样——那些属于 Controller 与协议适配层。Pipeline 只管「谁先谁后、谁挂了就不往下走」。

收益是新增能力的成本从「改 Controller + 重测链路」变成「加一个 Filter + 声明 order」。代价有两条：多了一层间接调用，Debug 时不能靠单步跟下来，必须在事件里打 stage 名；order 成为全局资源，两个人同时加 Filter 时容易撞号，需要集中在一处常量类里分配。

适用条件写清楚：链路阶段数大于等于五个，且顺序会随业务变化，才值得上 Pipeline。如果只有鉴权和转发两步，直接写在 Controller 里更省事。

> 输入先入链
> 逐级问过再放行
> 出口只留一个
> 边界划得分明

Pipeline 本体负责排序、驱动、异常兜底和事件发布。

```java
package com.example.gateway.pipeline;

import java.util.Comparator;
import java.util.List;
import java.util.stream.Collectors;

public final class GatewayPipeline {

    private final List<GatewayFilter> filters;

    public GatewayPipeline(List<GatewayFilter> filters) {
        this.filters = filters.stream()
                .sorted(Comparator.comparingInt(GatewayFilter::order)
                        .thenComparing(GatewayFilter::name))
                .collect(Collectors.toList());
    }

    public List<String> stageNames() {
        return filters.stream().map(GatewayFilter::name).collect(Collectors.toList());
    }

    public StageResult execute(RuntimeContext ctx) {
        return new Chain(filters, ctx, 0).proceed(ctx);
    }

    private static final class Chain implements GatewayChain {

        private final List<GatewayFilter> filters;
        private final RuntimeContext ctx;
        private final int index;

        private Chain(List<GatewayFilter> filters, RuntimeContext ctx, int index) {
            this.filters = filters;
            this.ctx = ctx;
            this.index = index;
        }

        @Override
        public StageResult proceed(RuntimeContext ignored) {
            if (index >= filters.size()) {
                return StageResult.ok();
            }
            GatewayFilter current = filters.get(index);
            long start = System.nanoTime();
            StageResult result;
            try {
                result = current.apply(ctx, new Chain(filters, ctx, index + 1));
            } catch (RuntimeException e) {
                result = StageResult.fail(ErrorCodes.STAGE_INTERNAL_ERROR,
                        current.name() + ": " + e.getClass().getSimpleName());
            }
            StageEvents.publish(ctx, current.name(), result, System.nanoTime() - start);
            return result;
        }
    }
}
```

接下来是三个代表性 Filter：鉴权、限流、路由。

```java
package com.example.gateway.filter;

import com.example.gateway.pipeline.*;
import org.springframework.stereotype.Component;

@Component
public class AuthFilter implements GatewayFilter {

    @Override
    public String name() { return "auth"; }

    @Override
    public int order() { return StageOrder.AUTH; }

    @Override
    public StageResult apply(RuntimeContext ctx, GatewayChain chain) {
        VirtualKeyConfig key = ctx.snapshot().virtualKey(ctx.keyId());
        if (key == null || key.disabled()) {
            return StageResult.fail(ErrorCodes.UNAUTHORIZED, "virtual key not found or disabled");
        }
        ctx.put("virtualKey", key);
        return chain.proceed(ctx);
    }
}
```

```java
package com.example.gateway.filter;

import com.example.gateway.pipeline.*;
import org.springframework.stereotype.Component;

@Component
public class RateLimitFilter implements GatewayFilter {

    private final RateLimiterRegistry registry;

    public RateLimitFilter(RateLimiterRegistry registry) {
        this.registry = registry;
    }

    @Override
    public String name() { return "rate_limit"; }

    @Override
    public int order() { return StageOrder.RATE_LIMIT; }

    @Override
    public StageResult apply(RuntimeContext ctx, GatewayChain chain) {
        VirtualKeyConfig key = (VirtualKeyConfig) ctx.attr("virtualKey");
        if (key == null || key.rpm() <= 0) {
            return chain.proceed(ctx);
        }
        if (!registry.acquire(ctx.keyId(), key.rpm())) {
            return StageResult.fail(ErrorCodes.RATE_LIMITED, "rpm limit " + key.rpm() + " exceeded");
        }
        return chain.proceed(ctx);
    }
}
```

```java
package com.example.gateway.filter;

import com.example.gateway.pipeline.*;
import org.springframework.stereotype.Component;
import java.util.List;

@Component
public class RouteFilter implements GatewayFilter {

    @Override
    public String name() { return "route"; }

    @Override
    public int order() { return StageOrder.ROUTE; }

    @Override
    public StageResult apply(RuntimeContext ctx, GatewayChain chain) {
        List<Deployment> candidates = ctx.snapshot().deploymentsOf(ctx.logicalModel());
        if (candidates.isEmpty()) {
            return StageResult.fail(ErrorCodes.NO_DEPLOYMENT,
                    "no deployment for " + ctx.logicalModel());
        }
        Deployment picked = candidates.get(0);
        ctx.bindDeployment(picked.id());
        return chain.proceed(ctx);
    }
}
```

```java
package com.example.gateway.web;

import com.example.gateway.pipeline.*;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.UUID;

@RestController
public class ChatCompletionsController {

    private final GatewayPipeline pipeline;
    private final RuntimeConfigSnapshotHolder snapshotHolder;

    public ChatCompletionsController(GatewayPipeline pipeline,
                                     RuntimeConfigSnapshotHolder snapshotHolder) {
        this.pipeline = pipeline;
        this.snapshotHolder = snapshotHolder;
    }

    @PostMapping(path = "/v1/chat/completions", produces = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<?> chatCompletions(@RequestBody ChatCompletionRequest request,
                                             @RequestHeader("Authorization") String authorization) {
        RuntimeContext ctx = new RuntimeContext(
                UUID.randomUUID().toString(),
                TraceId.current(),
                request.projectId(),
                ApiKeyParser.parse(authorization),
                request.model(),
                Boolean.TRUE.equals(request.stream()),
                snapshotHolder.current());

        StageResult result = pipeline.execute(ctx);
        if (!result.success()) {
            return ResponseEntity.status(ErrorHttpMapper.statusOf(result.errorCode()))
                    .body(ErrorHttpMapper.toOpenAiError(result));
        }
        return ResponseEntity.ok(ctx.attr("response"));
    }
}
```

# 06、排查

第一条链路，现象是 stream=true 的请求在日志里看不到 rate_limit 事件。怀疑是 RateLimitFilter 对 stream 做了特殊分支。检查方法是拿一个 requestId 去 grep 所有 stage 事件，同时把 Controller 的流式分支代码读一遍。证据很干脆：那批请求一条 stage 事件都没有，连 auth 都没有。根因不是 Filter，而是 Controller 里流式分支先 new SseEmitter 再 return，压根没调用 pipeline.execute。修复是把分流点从 Controller 挪到 ProviderInvoke 之后，前置链路对流式与非流式完全共用。

**错误尝试：** 我先怀疑是 GatewayFilter 的 order 值重复导致排序不稳定，把所有 order 改成 10 的倍数再重新排序，结果事件照样一条不出。这个方向错在把「零条事件」当成了「顺序错乱」。顺序错乱的表现是事件齐全但次序不对，而这里连 auth 事件都没有，说明请求根本没进链，是调用路径问题。

第二条链路，现象是某个 Project 预算已经用尽，请求仍然返回 200。怀疑 BudgetFilter 没读到最新额度。检查方式是打印 ctx.snapshot().version()，再对比管理库里 budget_used 字段的最后更新时间。证据显示 snapshot 版本落后于库里的更新时间，差值正好是那次管理页操作的时刻。根因在控制面：管理页保存时只写了数据库，没有发布配置变更事件，数据面继续读旧快照。修复是引入 ConfigChangedEvent，控制面写库成功后发布事件，数据面监听后重建快照并原子替换引用。

**错误尝试：** 修这条时我的第一反应是在 BudgetFilter 里直接查一次数据库拿最新的已用额度。这个做法错在两点：一是把热路径的可用性绑到了管理库上，管理库抖动会直接打挂网关；二是它破坏了「一次请求只看一版配置」的前提，同一个请求里 Auth 看旧 Key、Budget 看新额度，链路内部自相矛盾。

> 事件为零最可疑
> 排序从来是替罪
> 快照落后非偶然
> 根因总在控制面

# 07、优化

V2-1，统一流式与非流式的入口。根因是分流写在 Controller，修改点是把 stream 标记放进 RuntimeContext，Controller 无论流式与否都先跑完整前置链路，ProviderInvoke Filter 内部再根据 ctx.stream() 决定写 SseEmitter 还是写普通响应对象。这样做是因为前置约束本来就与响应形态无关。新行为是两条路径产生同一套 stage 事件，验证方式是分别发一次流式与非流式请求，把两张事件列表并排看，前置阶段必须逐条对齐（示例验证方法，非实测数据）。

V2-2，快照发布机制。根因是控制面写库后没有通知数据面，修改点有两个：控制面在事务提交后发布 ConfigChangedEvent；数据面用 ConfigSnapshotPublisher 监听该事件，重建 RuntimeConfigSnapshot 并原子替换 Holder 里的引用。这样做是因为数据面要的是「一致的一版」而不是「最新一行」。新行为是配置生效延迟从「等下次重启」变成「事件到达即可见」，验证方式是改一次预算后立刻发请求，观察快照 version 是否递增。

V2-3，异常与错误的统一出口。根因是 Filter 内抛异常会被包装成 STAGE_INTERNAL_ERROR，但这只保住了不崩，没保住语义。修改点是在 Pipeline 的 catch 分支里保留 stage 名，并新增 ErrorHttpMapper 把 gw.* 错误码映射成 OpenAI 风格的错误体，HTTP 状态码也在这一层统一决定。这样做是因为错误码属于链路语义，HTTP 状态属于协议语义，两者不该混在 Filter 里。新行为是任何一个 Filter 失败，客户端都能拿到结构一致的错误响应。

> 分流移入链中
> 变更推送快照
> 异常统一包装
> 优化必有证据

# 08、演进

```text
[同一输入]
    |
    +--[V1] 顺序写在 Controller 行序里 / 代价：改一处要回归全链、无统一事件
    |
    +--[V2] 顺序由 order 声明、快照驱动、事件齐全 / 代价：多一层间接、order 成为全局资源
    |
[Trade-off]
得到什么：链路可测、可观测、可插拔
失去什么：单步调试的直观性，以及一点点调用开销
适用边界：阶段数 ≥ 5 且顺序会变；两三步的网关不要硬上
```

正确性上，V1 依赖人的记忆，V2 依赖排序结果。V2 不能说绝对更对，但它把「顺序对不对」变成了一个可以在单元测试里断言的问题——构造一组 Filter，断言 stageNames() 的顺序。

稳定性上，V1 在新增能力时最容易出事，因为改动落在 Controller 的行序上，而 Controller 是每个人都敢改的文件。V2 把改动收敛到「加一个类 + 分配一个 order」，破坏面小得多，但引入了 order 撞号这个新风险，需要用集中常量类压住。

复杂度上，V2 明显更高：多了六个类、一套错误码、一个事件发布点。这个复杂度在链路短的时候纯属负担。

成本上，V2 的每一次请求多了一次链表跳转式的间接调用，量级可以忽略；真正的成本是团队理解成本，新人要先理解 Filter/Policy 的分工才能动手。

适用范围上，V2 适合已经有六个以上治理需求的网关。遗留问题有三个：快照重建的原子性只是引用替换，重启恢复还没做；路由目前只取候选列表第一个，没有健康度参与；上游失败的轮转还没接上。这三件事分别属于后面的持久化、路由与重试主题。

> 同一请求两条路
> 一条堆在一处
> 一条散作链环
> 取舍各有代价

# 09、洞见

## 9.1 顺序是契约，必须用代码对象表达

**反直觉判断：好的 Pipeline 会让代码行数变多。** 大多数人抽 Pipeline 的动机是「让 Controller 变短」，如果只盯着这个目标，很容易抽出一个把逻辑藏得更深的 Service 层。真正的收益在于顺序变成了一个集合，而集合可以被遍历、被打印、被断言。判断有没有抽对，看一条标准：能不能不启动应用就断言链路顺序。

## 9.2 控制面与数据面要用不同的一致性标准

**反直觉判断：热路径读快照比查库更「正确」。** 数据库里的值更新，不代表对一次请求而言它是「对的」。网关的一次请求是一个短事务，它需要的是自洽。把配置在入口处定版，整条链路读同一版，比每个 stage 各查一次库、各看到不同版本，工程上更可靠。代价是配置生效有延迟，这个延迟必须用事件机制压到可接受范围。

## 9.3 「Controller 只做协议适配」是可验证的边界，不是口号

这句话能被检查。做法是给自己一条硬规则：Controller 文件里出现 ratelimit、budget、route、circuit 这些词就算违规。规则简单到能写进 Code Review 清单，边界就从口头约定变成了可执行约束。

## 9.4 短路语义必须显式声明，否则会在最坏的时候暴露

前置 stage 失败必须终止，后置 stage 失败只记录，这两类行为要在设计时就分好。如果不分，最容易出现的后果是：记账失败把一次已经成功的调用变成 500，用户付了钱却拿到错误。

## 9.5 事件是链路的副产品，不是附加功能

每个 stage 发布一条事件，成本极低，收益是把「链路走到哪」从猜变成了查。它的价值在故障时才体现，但不能等故障后再补——补的时候你恰好最缺可观测性。

> 顺序即是契约
> 快照即是真相
> 边界需要可验
> 短路必须显式

# 10、系统落地

原来有什么？有一份逆向后的 Demo、换过包名的工程、七个本体模型、一条能跑的 OpenAI 兼容接口，以及一个越写越厚的 Controller。

本篇新增了什么？一个 GatewayPipeline、一套 GatewayFilter/GatewayChain 接口、RuntimeContext 与 RuntimeConfigSnapshot、集中分配的 StageOrder、统一错误码 StageEvents 与 ErrorHttpMapper，以及把 Controller 压缩回协议适配层的那次改动。分支是 chapter/05-gateway-pipeline，提交是 feat(ch05): build extensible gateway request pipeline。

现在能做什么？能按 order 声明式地编排一条十阶段链路，能在任意位置插入新 Filter 而不碰 Controller，能让流式与非流式共用前置约束，能让每次请求输出一串可查的 stage 事件。

还缺什么？快照只有内存态，重启后要从库重建；路由只取第一个 Deployment，没有健康与权重；上游失败没有轮转与熔断；预算只做了校验，没有真正扣减。

下一步如何演进？先让路由具备选择能力，再给上游调用加上失败轮转与恢复能力，然后把配置快照落盘，最后才是计量与控制台。顺序不能乱——没有稳定路由，重试就不知道该往哪重试。

> 原来一切在控
> 如今一切在链
> 能加能删能测
> 尚缺持久与熔断

# 11、小结

```text
Q1 → 顺序由 order 常量与排序后的 Filter 集合决定，不再由 Controller 的行序决定
Q2 → 抽 Pipeline 而不是继续加 if，代价是多一层间接与一个全局 order 资源
Q3 → 出错时靠每 stage 一条事件定位，前置失败终止、后置失败只记录
状态 → Controller 只做协议适配，策略逻辑全部收敛进 Pipeline
```

> 一问序由谁定
> 二问路分几支
> 三问错了怎知
> 答在事件之中
