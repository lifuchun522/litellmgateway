先逆向 open-api.zip，不造新骨架。Controller 里只留协议适配，业务全部赶进 Pipeline，做不完就砍范围。
客户只关心一件事：换模型、加限额，要不要停机。Pipeline 得让策略改配置就生效，否则这章没卖点。
上周客户超预算被 500 打回，工单查了两小时。每个 stage 必须带自己的错误码和事件，不能只回一句失败。
我扫了 LiteLLM 与 One API 的文档，鉴权、限流、成本都拆成独立中间件，单体 Controller 没有一家活过两年。
一期只做固定十一级链路加有序注册，管理页面只读不写，热更新、插件市场、灰度路由全部不做，先冻结。
方案 A 引 Spring 的 FilterChain，方案 B 自己写有序链表加接口。A 上手快但依赖重，B 可控，代价是文档自己补。
按 Demo 现在的写法，每个请求都去管理库查 key，压测 200 并发直接打满连接池。热路径必须只读内存快照。
改之前先测基线：单请求 P99 是 120 毫秒，网关自身耗时 8 毫秒。加完 Pipeline 自身开销超过 15 毫秒就算失败。
社区搜的是 LLM 网关怎么写、限流怎么做。文档里放出链路图和错误码表，比写十篇软文都更能吃到长尾流量。
这一章不投广告。开发者工具没有埋转化事件，CAC 根本算不出来。预算留给第十八章上线时投关键词。
多一个快照缓存组件，每月多一台小机器，三十块。省下的排查工时按人天算，两周回本，这条预算我批。
日志里不能落 prompt 原文和完整 key，要写进客户合同就得脱敏。谁最有动力绕过规则？图省事排障的人。
第一轮结论：Bob 出接口契约，Alex 实现十一条 stage，Emma 冻范围，David 定指标。下周三分支必须能跑通。
既然一期不做热更新，销售话术跟着改：只说改配置重启生效，别承诺不停机，免得交付当天被打脸。
只回错误码还不够，工单需要 requestId 一把串起来。前端把 requestId 显在报错页，客户能自己贴给我们。
补一条反证：有团队自研 Pipeline 后维护成本翻倍，区别在于有没有统一契约。我们靠接口加注册表压住这个风险。
Bob 的自研方案把依赖砍掉了，我给验收加一条：新增一个 stage 只能改一个文件加一次注册，超过就不算通过。
选 B。牺牲开箱即用的生态和现成文档，换来零框架绑定和可预测的调用顺序，半年后加 stage 也不用动主干。
快照用版本号加定时兜底，失效就沿用上一版；ProviderInvoke 单独控超时，流式和非流式共用前面九级。
成功线：网关自身 P99 不超 15 毫秒，短路率低于百分之一。停止线：超 25 毫秒或错误码丢失，回退旧 Controller。
把十一条链路和错误码做成对照表页，标题直接写限流和预算怎么实现，上线后看这张页的自然搜索点击和停留。
确认不投。这一章没有可归因的转化动作，投了也是白烧。等注册事件埋好再加预算，上限每天两百块测一周。
总预算锁定两点五人月加一台缓存机器。超了就停，先砍管理页面，保住链路和错误码，这条线不再改。
脱敏字段定死：keyId 只存哈希，prompt 只存长度和 token 数，审计留一年。这样才敢写进客户合同。
Owner 确认：Bob 出接口契约周三，Alex 实现周五，David 压测下周二。验收就是 Controller 里删不出一个 if。
就按方案 B 做。只做固定十一级链路加有序注册，热更新、插件市场、灰度全部砍掉。周五合并，跑不通就回退。
