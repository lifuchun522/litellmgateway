第十二章只做一件事：让 LiteLLM Gateway 在 Demo 骨架上长出 RPM、TPM 限流和预算硬门禁，不做分布式。
客户最怕账单失控和接口被刷爆。一句话价值：给 VirtualKey 和 Project 装上额度阀门，超了立即返回 429。
一线投诉最多的是：超额调用没有 Retry-After，客户不知道等多久；预算超限直接报 500，没人能自助恢复。
我查了 OpenAI 与 Anthropic 的规范：限流统一返回 429 和 Retry-After；预算超限归 403 或 429，不能混 500。
一期只做 VirtualKey、Project 两个维度，RPM、TPM 各一个窗口；Model、Provider 只留接口，页面不做多维筛选。
候选 A：Bucket4j 本地内存，零外部依赖，单节点准；候选 B：Redis 集中式，多节点一致，但要加部署和故障域。
本地限流最怕重启丢桶，预算最怕并发请求同时读到旧用量。我要求限流器可重建，预算检查带版本号或行锁。
基线：现有 Demo 单节点 P95 约 12 毫秒。成功线：加限流后 P95 不超 30 毫秒，误杀率低于千分之一。
开发者搜 LLM Gateway rate limit 和 token budget，要可复制配置。文档给 YAML 示例和 429 对照表，自然流量才会来。
这章是后端治理，没有终端转化事件。我明确不投广告，预算留给下一章注册漏斗；本次只埋 429 计数。
Bucket4j 免费，真正成本是人力：后端约 3 人日，前端 1 人日，测试 1 人日，总共不超过 5 人日。超过 8 人日就砍页面。
限流和预算拒绝必须可审计：谁改了额度、何时生效、依据哪条规则。合同里不能承诺永不超支，只能承诺告警和拒绝。
第一棒 Bob 定接口，Alex 写限流与预算，Emma 出页面验收，David 盯指标。分支 chapter/12-rate-limit-budget，明天开发。
听了 Bob 的本地方案，我接受单节点先行；但客户可见的 429 必须带错误码和 Retry-After，否则销售没法解释账单。
一线标准：客户看到 429 后，能在页面看到今日用量和预算进度，知道等多久或找谁提额。做不到，这个闭环不算完成。
我补一个反证：Bucket4j 在虚拟线程下需要正确配置锁。置信度中高，但必须加并发压测，否则本地限流会误杀。
范围冻结：一期做 VirtualKey、Project 的 RPM、TPM、Daily、Monthly；页面只做四块：限流、预算、今日用量、预算进度。
最终取舍：牺牲多节点强一致，换零外部依赖和一天上线。限流抽象 RateLimiter，预算抽象 BudgetChecker，Redis 只留实现类。
实现路径：Bucket4j 内存桶按 VirtualKey、Project 建；预算检查先读已用量，再加请求预估 token，原子扣减；冲突重试一次。
成功线：超限 429 且 Retry-After 正确率百分之百；停止线：P95 超 50 毫秒或误杀率超百分之一，立即回退无限流版本。
上线后盯两个自然搜索验证：搜索进入文档的停留时长，以及从 429 文档跳到快速开始的点击率。两个都涨，说明发现路径成立。
这次不投付费，但留一个追踪：429 错误页加 UTM 链接到文档。CAC 上限设置为零，下一章再开预算。
预算线锁死：五个人日，不买 Redis 云实例，不加监控 SaaS。ROI 门槛是这章上线后，下一章省下至少两天重复治理开发。
合规门槛过了：429 和预算拒绝都写审计日志，额度变更必须留操作人。红线是不得用限流掩盖数据泄露或越权调用。
Owner：Bob 接口，Alex 限流与预算，Emma 页面，David 指标，Mike 验收。本周五交付。验收：超 RPM、TPM 返回 429，预算超限拒绝新请求。
拍板：按 MVP 单节点方案做，不造分布式骨架。做限流与预算，不做 Model、Provider 维度和多云。周五不达标就砍页面保接口。
