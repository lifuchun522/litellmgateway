我是老李，做 Java 后端很多年，这两年一直在把 LLM Gateway 从 Demo 往生产推。前面十一境把协议、路由、重试、熔断都跑通了，但控制面还是个空壳：谁是合法调用者是确定的，"能调用多少"是不确定的。

内测环境里，一个租户挂着批处理脚本，另一个租户在调试 Playground。前者把上游额度吃掉大半，后者开始收到莫名其妙的超时。整条转发链路上，没有任何一个环节问过一句：你还剩多少？

账单是第二天早上看到的。用量曲线在前一天下午就抬了头，但没有告警、没有拒绝、没有一条可读的 429。系统把"额度"当财务概念，没把它当运行时约束。

同一套转发链路，凭什么有的 Key 能跑满，有的必须停？

你会先做"事后计量再统计"，还是先做"放行前预扣再结算"？

如果选错，先出问题的是账单，还是你和一个大客户的信任关系？

# 01、故事

那天下午的现场很普通：一台单节点的网关，几台上游 Provider，五个 VirtualKey 分给三个内测团队。前面十一境做的活儿都在：Demo 逆向、包名迁移、七模型本体、OpenAI 兼容契约、Gateway Pipeline、Provider/Deployment 适配、路由选择、重试回退熔断。

任务是：在不引入 Redis、不拆服务的前提下，让这台单节点网关自己管住 RPM、TPM 和钱——超了必须拒，拒得必须让 OpenAI SDK 看得懂。

当前方案就一句话：鉴权通过就转发。Project 和 VirtualKey 在数据库里有记录，但记录里没有额度，额度只活在人的脑子里。

变化来自两个方向。外部：上游按 token 计费，账单以天、月为周期结算，一次失控要等很久才被发现。内部：多租户开始共享同一套网关，用量不再是"能不能"，而是"给谁多少"的问题。

冲突就在这里：配额是状态，状态要精确，精确要花成本。而第十二境这只天角蚁教的恰恰是另一件事——极致的力量不是靠更多组件堆出来的，是靠更硬的约束压出来的。

分支先建：`chapter/12-rate-limit-budget`。这一境的改动，最后会压成一个提交：`feat(ch12): add token rate limit and budget governance`。

# 02、问题

旧方案失效得很安静。它甚至不算"失效"，它只是从来没有存在过。

业务侧的表现是：一个 Key 的用量曲线能抬到让其他租户超时，运维只能靠人肉盯上游控制台去关 Key。技术侧的表现更具体：

- 并发请求下，用 `AtomicLong` 做的简单计数在跨秒边界抖动，压测时秒级放行量高于配置的平均速率；
- TPM 完全没有维度，只有请求数被计数，token 量级对网关是不可见的；
- 预算只是报表概念，没有任何一次请求因为"这个 Project 今天花完了"而被拒绝；
- 被拒绝时（其实是上游返回 429 时）透传出去的响应体结构不是 OpenAI 兼容错误，SDK 侧异常体验很差；
- 没有 `Retry-After`，客户端只能盲目重试，重试又进一步推高 TPM。

完成标准要能验证，所以写成四条：

1. RPM 超限返回 HTTP 429，响应体为 `{"error": {...}}` 结构，`type` 为 `rate_limit_error`，`code` 为 `rate_limit_exceeded`；
2. TPM 超限同样返回 429，且适用时返回的 `Retry-After` 与令牌桶实际恢复时间一致；
3. 预算（Daily/Monthly，粒度 Project/VirtualKey）超限时拒绝新请求，返回 429，并用 `code` 区分"速率超限"与"配额耗尽"；
4. 管理页面能看到限流策略、预算策略、今日用量和预算进度。

四条里最容易被忽略的是第 3 条的"区分"。速率超限是等一会儿就好的问题，预算耗尽不是。混在一个错误码里，客户端会疯狂重试一个到月底都不会成功的请求。

> 事后计量太晚
> 账单先于告警
> 缺一条硬边界
> 全站陪着透支

# 03、原理

这一境只需要三个原理：令牌桶、预扣结算、双层闸门。

令牌桶的核心不是"限速"两个字，而是它同时表达了两件事：平均速率和突发容量。桶容量是突发上限，补充速率是平均上限。RPM 用容量 60、每分钟补 60 的桶，和用容量 1、每秒补 1 的桶，平均都是 60 RPM，但前者允许一分钟内打完，后者不允许。选哪个是产品决策，不是技术决策。

第一个反直觉判断：限流器真正保护的对象不是你的服务，而是你的预算。服务通常能扛住比预算多得多的流量，所以"压测通过"和"成本可控"是两件毫不相干的事。这也是为什么限流必须和预算放在同一个决策点上，而不是一个在网关、一个在财务系统里。

TPM 的难点在于：token 数在请求发出前是不确定的。你能做的只有估算（输入 token 数加 `max_tokens` 上限），然后预扣。这意味着限流器一定会遇到"扣多了"和"扣少了"两种情况，必须有一条结算路径把差额补回来。

第二个反直觉判断：预扣加结算看上去比事后计量更"粗暴"，因为它会误伤——明明还有额度，却因为估算偏大被拒。但它是唯一正确的顺序。事后计量的问题不是不准，而是太晚：等你知道花了多少，钱已经花了，拒绝对已经发生的调用没有任何意义。预扣把不确定性前移到决策点，代价是偶发误伤，收益是账单永远不超。

第三个原理是双层闸门的分工。速率限制是短周期、恢复快的约束；预算限制是长周期、恢复慢的约束——日预算要到明天清零，月预算要到下月。两者被拒时给客户端的信号完全不同：前者适合 `Retry-After`，后者给了反而是在骗人。这就是"适用时返回"这几个字的含义。

> 令牌补的是速率
> 预扣锁的是风险
> 桶大不等于安全
> 结算必须闭环

# 04、架构

```text
[输入] OpenAI 兼容请求 /v1/chat/completions
    |
    v
[模块] Auth → RateLimitGate(RPM/TPM) → BudgetGate(Daily/Monthly)
    |
    v
[数据/状态] 内存令牌桶 + 预算预扣累加 + 策略缓存 + 周期用量聚合
    |
    v
[处理] 预扣 → 路由转发 → 结算差额 → 记 Usage
    |
    v
[输出] 上游响应 / 429 + OpenAI 兼容 error + Retry-After
```

边界先说清楚：这一境的桶和预扣累加全在单节点内存里，多副本不同步，进程重启后桶清零。这不优雅，但对 MVP 是正确的取舍——先把语义和契约钉死，再换存储实现。

决策顺序也有讲究。鉴权（Project/VirtualKey 是否存在、是否启用）必须在最外层，否则你会为一个非法 Key 去消耗桶。RPM 在 TPM 前面，因为它便宜且失败概率高，先拦便宜的。预扣失败时要回滚已经扣掉的维度，这是实现里最容易漏的一处。

维度设计上，先做 VirtualKey 和 Project 两层，Model 和 Provider 只预留结构不做实现。理由很实在：VirtualKey 是"人"，Project 是"团队"，这两层是当前真实存在的治理单元；Model/Provider 维度的额度跟上游账号绑定，属于多租户之后的事。

收益：一次请求在转发前就被定性，拒绝码可被 SDK 解析，重试可以被引导。代价：多了一次状态读写的开销，以及内存状态带来的"重启即失忆"。适用条件是单实例、内测规模、可接受偶发误伤。

> 入口先过三关
> 维度逐层收紧
> 状态各归其位
> 决策先于转发

**核心实现**

先是决策对象和限流器。桶按"维度 + 指标"做键，容量为每分钟限额，用贪婪补充避免分钟边界成批放行。

```java
public record RateLimitDecision(
        boolean allowed, String dimension, String code, long retryAfterSeconds) {

    public static RateLimitDecision ok() {
        return new RateLimitDecision(true, null, null, 0);
    }
}
```

```java
@Component
public class Bucket4jRateLimiter {

    private record BucketKey(String scopeId, String metric) {}

    private final Map<BucketKey, Bucket> buckets = new ConcurrentHashMap<>();

    private Bucket bucket(String scopeId, String metric, long capacityPerMinute) {
        return buckets.computeIfAbsent(new BucketKey(scopeId, metric), k -> Bucket.builder()
                .addLimit(limit -> limit.capacity(capacityPerMinute)
                        .refillGreedy(capacityPerMinute, Duration.ofMinutes(1)))
                .build());
    }

    public RateLimitDecision tryAcquire(String scopeId, long rpm, long tpm, long estimatedTokens) {
        ConsumptionProbe rpmProbe = bucket(scopeId, "rpm", rpm).tryConsumeAndReturnRemaining(1);
        if (!rpmProbe.isConsumed()) {
            return reject("rpm", "rate_limit_exceeded", rpmProbe);
        }
        ConsumptionProbe tpmProbe =
                bucket(scopeId, "tpm", tpm).tryConsumeAndReturnRemaining(estimatedTokens);
        if (!tpmProbe.isConsumed()) {
            bucket(scopeId, "rpm", rpm).addTokens(1);
            return reject("tpm", "rate_limit_exceeded", tpmProbe);
        }
        return RateLimitDecision.ok();
    }

    public void settle(String scopeId, long tpm, long reserved, long actual) {
        long delta = reserved - actual;
        if (delta > 0) {
            bucket(scopeId, "tpm", tpm).addTokens(delta);
        } else if (delta < 0) {
            bucket(scopeId, "tpm", tpm).tryConsumeAndReturnRemaining(-delta);
        }
    }

    private RateLimitDecision reject(String metric, String code, ConsumptionProbe probe) {
        long wait = Math.max(1, TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()));
        return new RateLimitDecision(false, metric, code, wait);
    }
}
```

预算是第二道闸。它的关键是"预扣累加"——在内存里维护一份正在飞行中的金额，避免多个并发请求同时读到同一个旧用量。

```java
@Component
public class BudgetGuard {

    private final UsageQuery usageQuery;
    private final BudgetPolicyRepository policyRepository;
    private final Map<String, Long> pendingMicros = new ConcurrentHashMap<>();

    public BudgetDecision reserve(String scopeType, String scopeId, long estimatedMicros) {
        BudgetPolicy policy = policyRepository.find(scopeType, scopeId);
        if (policy == null || policy.dailyLimitMicros() <= 0) {
            return BudgetDecision.allow();
        }
        long used = usageQuery.usedToday(scopeType, scopeId);
        long pending = pendingMicros.merge(key(scopeType, scopeId), estimatedMicros, Long::sum);
        if (used + pending > policy.dailyLimitMicros()) {
            pendingMicros.merge(key(scopeType, scopeId), -estimatedMicros, Long::sum);
            return BudgetDecision.reject("daily", policy.dailyLimitMicros(), used + pending);
        }
        return BudgetDecision.allow();
    }

    public void settle(String scopeType, String scopeId, long estimatedMicros, long actualMicros) {
        pendingMicros.merge(key(scopeType, scopeId), estimatedMicros - actualMicros, Long::sum);
    }

    private String key(String scopeType, String scopeId) {
        return scopeType + ":" + scopeId;
    }
}
```

拒绝要变成 OpenAI 兼容错误。注意这里不能用 `Map.of`，它不接受 null 值，`param` 会直接把构造打成空指针。

```java
public class RateLimitException extends RuntimeException {

    private final String code;
    private final long retryAfterSeconds;

    public RateLimitException(String message, String code, long retryAfterSeconds) {
        super(message);
        this.code = code;
        this.retryAfterSeconds = retryAfterSeconds;
    }

    public String getCode() {
        return code;
    }

    public long getRetryAfterSeconds() {
        return retryAfterSeconds;
    }
}
```

```java
@ExceptionHandler(RateLimitException.class)
public ResponseEntity<Map<String, Object>> handle(RateLimitException ex) {
    Map<String, Object> error = new LinkedHashMap<>();
    error.put("message", ex.getMessage());
    error.put("type", "rate_limit_error");
    error.put("param", null);
    error.put("code", ex.getCode());

    ResponseEntity.BodyBuilder builder = ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS);
    if (ex.getRetryAfterSeconds() > 0) {
        builder.header(HttpHeaders.RETRY_AFTER, String.valueOf(ex.getRetryAfterSeconds()));
    }
    return builder.body(Map.of("error", error));
}
```

# 06、排查

**第一条链：秒级放行量高于配置**

现象：压测脚本并发打请求，按秒统计的放行量出现尖峰，高于配置的平均速率。

怀疑：桶的补充策略不对，或者容量单位按秒配置。

检查：把桶的容量、补充间隔，以及每次 `ConsumptionProbe` 的剩余量打到日志里。

证据：日志显示接近分钟边界时放行量集中，跨过边界后又出现一批——这是固定窗口的特征，不是贪婪补充的特征。

根因：补充用的是固定间隔一次性补满（等价于分钟级固定窗口），在窗口边界允许两倍突发。

修复：统一用贪婪补充，容量等于每分钟限额，补充周期一分钟。

**第二条链：TPM 没打满却持续被拒**

现象：上游返回的 usage 显示这一分钟实际 token 消耗远低于限额，但请求已经开始被 429 拒绝。

怀疑：估算偏大。

检查：在预扣和结算两处各打一行日志，记录 `reserved` 和 `actual`。

证据：`reserved` 明显大于 `actual`，且两者差值持续累加，没有任何回补记录。

根因：结算只在成功路径执行，异常路径和流式提前返回都没走到。

修复：把结算放进统一的收尾逻辑，保证扣过就一定结。

**第三条链：预算还有余额却短时超发**

现象：日预算在页面上还有余量，但同一秒内多个并发请求全部被放行，事后聚合的用量超过了限额。

**错误尝试：** 先把用量缓存的 TTL 从 60 秒调到 1 秒，希望靠"读得更勤"减少超发。为什么错：TTL 只缩小了脏读窗口，没有消除竞态，`读用量 → 判断 → 放行` 这个三段式在并发下依然不是原子的，同时把数据库压力放大了几十倍。

根因：预算检查不是原子预留，多个请求同时读到同一个旧用量。

修复：改成先预扣再判断，预扣用 `ConcurrentHashMap.merge` 的原子语义累加，请求结束后按实际用量结算差额。

> 现象先于猜测
> 证据高于经验
> 根因常在自己
> 修在最小处

# 07、优化

V2 的四项改动全部来自上一章的证据。

**改动一：把结算变成闭环。** 根因是结算只在成功路径执行。修改方式是把预扣和结算包成一次调用前后的配对操作，用 try/finally 保证异常路径也结算，流式响应在流结束时结算。新行为是：被拒请求立刻返还预扣，流式请求在最后一个 chunk 后回补差额。验证方式是对比压测中 `reserved` 与 `actual` 的累计差值，应稳定收敛而不是单向增长。

**改动二：预算从"读-判断"改成"预扣-判断-结算"。** 根因是读取不是预留。修改后用 `merge` 做原子累加，判断基于已用量加预扣中金额。新行为是并发请求也能共享同一份进行中的账单视图。验证方式是用并发脚本同时发起多个请求，观察是否出现放行量超过限额的情况。

**改动三：429 的语义分层。** 根因是错误码没有区分。修改后按被拒维度决定 `code` 与是否带 `Retry-After`：速率维度带精确等待秒数，预算维度不带。新行为是客户端能区分"等一会儿"和"别等了"。验证方式是分别触发两种拒绝，检查响应体与响应头。

**改动四：`Retry-After` 取被拒维度的真实恢复时间。** 原来的写法是固定返回 1 秒，客户端重试依然会被拒。改为从 `ConsumptionProbe.getNanosToWaitForRefill()` 换算，并向下取整到秒、最小为 1。新行为是"提示即可用"。

这四项里只有改动二会改变系统复杂度——它把一个无状态判断变成了有状态预留。这是必须付的代价，因为账单不允许竞态。

> 预扣再结差额
> 原子替掉读改
> 返还不可遗漏
> 边界各自成层

```text
    |
    +--[V1] 先转发后统计 / 计数抖动、TPM 不可见、预算无预留
    |        代价：账单先于告警，429 结构不可解析
    |
    +--[V2] 转发前预扣 / 双维度桶 + 预算预留 + 结算闭环
    |        代价：多一次状态读写，偶发估算误伤
    |
[Trade-off]
得到：可解释的拒绝、可预测的账单、可被 SDK 识别的错误
失去：无状态判断的简单性，以及"拒绝一定要准"的幻想
适用边界：单实例、内测规模、内存状态可接受重启失忆
```

正确性上，V1 在所有并发场景下都不成立，V2 在单节点内成立、多节点不成立。稳定性上，V1 的问题是渐进的（用量慢慢超），V2 的问题是瞬时的（重启后桶清零，会有一次突发放行）。复杂度上，V2 多了两个状态容器和一条结算路径，可测试性要求提高。成本上内存开销可忽略，真正的成本是排查难度——限流系统出问题时现象是"请求被拒"，原因可能在估算、在结算、在策略加载。

遗留问题很清楚：内存状态不跨进程，Model/Provider 维度还没做，金额精度依赖 token 估算。这些问题不该在这一境解决，因为它们的前提条件是"多副本部署"。

> 一版守住平均
> 二版守住瞬间
> 代价是复杂度
> 换来账目可查

# 09、洞见

## 9.1 限流是定价系统的一部分

把限流当成"防刷"就低估了它。每一个 RPM/TPM 数字背后都是一次资源分配决策：给了谁、给多少、超了怎么办。网关里写的每一行限流代码，本质都是产品定价模型的可执行版本。这也解释了为什么策略必须落库、必须能在页面上改——定价会变，而重发代码不是改价的方式。

## 9.2 预扣和结算，是把不确定性前移

反直觉判断：预扣加结算比事后计量更容易误伤，却是唯一能守住账单的顺序。因为事后计量的错误方向不可逆——钱花了就花了；而预扣的错误方向可修正——多扣的在结算时退回来。工程上永远优先选择错误可逆的方案，哪怕它在正常路径上更啰嗦。

## 9.3 429 是一种契约，不是错误码

反直觉判断：最贵的失败不是返回 429，而是沉默地放行。客户端收到 429 会退避、会降级、会提示用户；而客户端在额度耗尽时先拿到 200、再被上游切断，会重试、会放大、会在最不该失败的时候失败。把 429 的 body 结构、`code` 语义、`Retry-After` 的适用条件写死，等于给所有调用方一份可以据此编程的契约。

## 9.4 维度选择就是授权模型的形状

先做 VirtualKey 和 Project，不是因为它容易，而是因为这两层对应真实的责任主体：Key 是一台机器或一个人，Project 是一个团队或一个产品。Model 和 Provider 维度属于成本归集，不是权限归集，硬塞到同一层会让策略表变成一团互相覆盖的规则。预留结构而不实现，比先实现再拆要便宜得多。

> 限流是账不是墙
> 预扣胜过事后追
> 维度即权力边界
> 拒绝要有返回值

# 10、系统落地

原来有什么：一条能转发、能路由、能重试、能熔断的链路，和一个能鉴权但不限量的鉴权层。所有关于"多少"的概念都不存在。

本篇新增了什么：两个决策点（速率闸、预算闸）、一套 OpenAI 兼容的拒绝契约、限流与预算的策略存储、今日用量与预算进度的查询，以及一个能被 SDK 正确解析的 429。

现在能做什么：给每个 VirtualKey / Project 配 RPM、TPM、日预算、月预算；超速立即 429 并给出准确等待时间；超预算拒绝新请求并且不误导重试；在页面上看到今天的用量和预算进度条。

还缺什么：多副本共享状态（现在是各算各的）、Model/Provider 维度、分布式桶与原子累加、金额精度的改进（token 估算与计价表），以及限流本身的可观测性。

下一步如何演进：把内存桶和内存预扣换成共享存储实现，接口保持不变——这也是本篇坚持把限流抽象在 `tryAcquire/settle` 后面、把预算抽象在 `reserve/settle` 后面的原因。换存储时改的是实现类，不是调用方。

分支与提交按计划收口：

```bash
git switch -c chapter/12-rate-limit-budget
git add .
git commit -m "feat(ch12): add token rate limit and budget governance"
```

验收结论按四条标准走：超 RPM 返回 429、超 TPM 返回 429 且带 `Retry-After`、预算超限拒绝新请求且 `code` 可区分、页面能看到策略与今日用量。四条都过，第 12 境才算落地。

> 策略落进库表
> 进度进入控制台
> 缺口留给多机
> 下一步做共享

# 11、小结

```text
Q1 → 能，双层闸门把"多少"变成了转发前的硬判断
Q2 → 选预扣 + 结算，因为它的错误方向可逆
Q3 → 先出问题的是账单，代价由信任来付
状态 → 单节点 RPM/TPM 限流 + Project/VirtualKey 预算闸门可交付
```

RPM 与 TPM 分别在 VirtualKey、Project 两个维度生效，Token 维度靠预估预扣、按实际用量结算；预算按 Daily/Monthly 作用于 Project/VirtualKey，检查基于已用量加请求预估；被拒请求统一返回 OpenAI 兼容 429，速率维度适用时带 `Retry-After`。

这一境真正的产出不是限流器，而是一个可替换的决策边界：所有"能不能放行"的判断都发生在转发之前，并且有明确的拒绝语义。

> 三问皆有答案
> 两闸同时生效
> 单机已可交付
> 多机仍待共享

# 12、作业

## 12.1 理解题：为什么预扣加结算比事后计量更适合管预算？

参考答案：事后计量的错误不可逆——等统计出超额时钱已经花出去了，拒绝只能作用于未来，不能作用于已发生。预扣把决策点前移到转发前，误差在结算时被修正，代价是偶发误伤。工程上优先选错误可逆的方案。

## 12.2 实战题：两个维度同时限流时，如何保证一次请求不会"扣了 TPM 但 RPM 没扣"？

参考答案：按固定顺序扣（先便宜的 RPM，再贵的 TPM），后续维度失败时回滚已扣维度。更好的是把多维度扣减做成统一入口：全部成功才提交，任一失败全部归还。回滚要注意桶容量上限的截断效应，`addTokens` 在桶已满时不会真正补回全部差额。

## 12.3 排障题：压测时发现某些秒的放行量明显高于配置速率，你按什么顺序排查？

参考答案：先看桶的补充策略与容量单位，确认是贪婪补充还是固定间隔补充；再看限流判断发生在转发前还是转发后；然后看多实例是否各自持有独立桶；最后看是否存在维度键拼装错误，导致多个租户共用一个桶。

## 12.4 架构判断题：为什么 Model/Provider 维度只预留结构而不实现？

参考答案：因为维度对应的是责任主体，不是技术分组。VirtualKey 和 Project 是当前存在的治理与计费单元；Model/Provider 维度依赖上游账号与成本归集模型，在多租户成型之前没有稳定的业务含义。预留字段和枚举比先实现再拆表便宜，也不会污染现有策略。

> 理解先明边界
> 实战须跑断言
> 排障要拿证据
> 判断落在取舍

# 13、思考

第 12 境的冲突从头到尾只有一句话：配额的精确性和实现的简单性不能同时拿满。天角蚁给的不是更多法宝，是更硬的约束——先把"多少"变成可执行的东西，再谈优雅。

值得带走的是三条判断：任何"事后才知道"的治理都是假治理，所以要预扣；任何没有返回值的拒绝都是坏契约，所以要写清 429；任何依赖单机内存的状态都是临时状态，所以要把它藏在接口后面。

当约束足够硬，系统的边界就清晰了——你知道它什么时候会拒，也知道拒绝之后会发生什么。

> 一念定边界
> 一证寻根因
> 一改知取舍
> 一役见真章
