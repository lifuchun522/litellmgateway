# 统一 requestId 与指标口径：LLM Gateway 可观测链路落地

> 一句 499 摆在面前，日志里却找不到它死在哪一段 Pipeline。

```text
[读者] 正在把开源 Demo 改造成多 Provider LLM Gateway 的 Java 工程师
[痛点] 失败请求只知道 502，不知道死在路由、重试还是上游
[现在读] Pipeline 与治理能力已成型，缺统一标识、指标与定位能力
[读完] 能落地标识贯穿、低基数指标与阶段级故障定位
```

```text
[旧方案] 单 Provider 直连 + 控制台文本日志 + 一个默认 HTTP 指标
    |
    v
[新需求] 多 Provider + 路由 + 重试 + 兜底 + 熔断，一条请求穿过十来个阶段
    |
    v
[冲突] 每个阶段各自造标识，指标维度随手加，日志与指标各说各话
    |
    v
[后果] 失败请求定位不到阶段，Prometheus 基数先失控
```

我是老李。手上这套东西的起点，是 litellmgateway 仓库 `open-api.zip` 里的那个 Demo：一个 Controller 收下 ChatCompletion 请求，转手打给一个上游，返回 JSON 或者 SSE。前面十几境我们没造新骨架，就在这个 Demo 上换包名、长本体，一路加了 Provider 适配、LogicalModel/Deployment 分层、路由决策、重试兜底、熔断恢复、VirtualKey 与限流预算、Usage/Cost 计量，最后还搭了个中文控制台。任务是：让任何一条失败请求，都能在十秒内说清它死在 Pipeline 的哪一个阶段。

真正把它推到台面上的，是一次凌晨排障。业务侧贴过来一个 499，我打开日志 grep 那个 requestId，只在入口过滤器里找到一行 request received，后面 Provider 调用、重试、兜底、熔断，全是各写各的日志，连 UUID 都不是同一个。指标那边更干净：只有 Spring Boot 默认给的 `http_server_requests_seconds`，切不出 provider，也切不出阶段，更看不到首字延迟。

更麻烦的是，有人为了「信息更全」，顺手把 requestId 和 keyId 塞进了 Meter 的 tag。本地跑没问题，连着压了几分钟，`/actuator/prometheus` 的响应体肉眼可见地膨胀。那一刻我意识到，这一境要解决的不是「多打点日志」，而是先给这套系统定一套标识与维度的规矩。

一条失败请求，我能在十秒内说出它死在哪个 Pipeline 阶段吗？

统一标识应该放在日志字段里，还是放在指标标签里？

如果放错地方，先撑不住的是 Prometheus，还是我的排查能力？

# 01、故事

现场是这样的：网关已经跑到第 15 境，中文控制台里能配 Provider、能配 VirtualKey、能看限流预算。上线两周，QPS 不高，但调用方开始报错。

系统这边的处理链路其实已经很复杂：入口校验 → 限流 → 预算 → 路由选 Deployment → 调 Provider → 失败重试 → 换 Provider 兜底 → 熔断短路 → 流式转发 → 计费落库。每一段都是前面某一境加进来的，逻辑上串得起来，可观测上却是断的。

任务来了：调用方给了三个词——「慢」「偶尔 502」「流式首字卡」。我需要给出一个能定位、能量化、可回归的可观测方案，而不是再教他们怎么 grep。

当前方案很朴素：SLF4J + logback 的纯文本日志，加上 Actuator 默认暴露的 `health` 和几个 JVM 指标。日志里能搜到 requestId，但那个 requestId 是入口 Filter 自己 `UUID.randomUUID()` 出来的，Provider 客户端那边又造了一个新的；traceId 压根没有。

变化在于，这个系统已经从「转发器」变成了「网关」：有多个 Provider，有 LogicalModel 到 Deployment 的映射，有重试次数，有兜底路径，有熔断状态，还有按 key 的限流和预算。链路的长度变了，失败的可能性从 1 个变成了十几类。

冲突就在这里：链路变长需要更多维度去切分问题，而 Prometheus 的存储模型对维度数量是乘法敏感的。想多切，就不能乱切；想定位，就得先统一标识。

> 一条请求落
> 七段各留名
> 日志串不起
> 故障无处寻

# 02、问题

旧方案失效的第一层，是标识失效。入口一个 UUID、重试一个 UUID、Provider 客户端一个 UUID，三条日志各自成立，合起来不成一条链路。排障时你只能按时间窗口捞，一捞一大片。

第二层，是指标口径失效。`http_server_requests_seconds` 只告诉你「这个接口慢」，不告诉你「是路由慢、还是上游慢、还是重试拖慢」。而 LLM 网关真正关心的几个量——首字延迟（TTFT）、token 数、费用、兜底率、限流拒绝数——默认指标里一个都没有。

业务影响是可以直接描述的：调用方只能拿到一个 502，SLA 争议时说不清责任归属；内部只能反复重启和猜测，变更风险高，灰度不敢放量。

技术表现上，问题收敛成四条：

- 失败请求无法关联到 Pipeline 阶段，日志缺少 `stage` 字段；
- 指标没有 provider / logical_model / status 这些低基数切面；
- 流式请求没有 TTFT 指标，慢在首包还是慢在整段无法区分；
- 有人把 requestId、keyId 写进了 Meter tag，指标端点体积随请求数增长。

可验证的完成标准，我定成六条：

1. 响应头返回 `X-Request-Id`，凭它能在日志里还原完整链路；
2. 每条阶段日志包含 `stage`、`route`、`attempt` 三个字段；
3. `/actuator/prometheus` 中不存在 `requestId`、`keyId`、`userId` 任何标签；
4. 存在 requests、duration、TTFT、tokens、cost、provider errors、fallback、rate-limit rejected 八类指标；
5. 能画出 Provider 健康、Error Top、P95、Fallback Rate 四张图；
6. 同步、SSE、401、403、429、timeout、fallback、breaker 八类回归测试全绿。

> 现象不可证
> 修复便无凭
> 先立验收线
> 再谈可观测

# 03、原理

这一境只讲一件事需要的原理：把「一条请求」变成「一条可查询、可聚合、可回归的记录」。

先看 Prometheus 的存储模型。一个时间序列由「指标名 + 全部标签的取值组合」唯一确定。标签不是免费的：标签维度之间存在组合爆炸。`provider` 有 5 个取值、`status` 有 5 个取值、`route` 有 8 个取值，组合就是 200 条序列；一旦把 `requestId` 加进来，取值数量等于请求数，序列数就跟着请求数线性增长。这是内存里的 map，也是磁盘上的 chunk，不是「反正加一个标签而已」。

反直觉判断：指标不是日志的降维聚合，日志也不是指标的明细展开。二者的基数预算是相反方向的。指标天生是低基数、可长期保存、可跨实例聚合的；日志天生是高基数、可丢弃、可存明细的。把高基数内容塞进指标的标签里，你不会得到「信息更全的指标」，只会得到「一个撑不住的系统和一个丢掉的指标」。

第二件事是标识的分层。这套系统里其实有四种身份，用途完全不同：

- `requestId`：单次入口请求，一次生成，贯穿全程，用于串日志；
- `traceId`：跨进程链路，遵循 W3C traceparent，用于跨服务、跨 Provider 的调用还原；
- `projectId`：租户身份，属于业务维度；
- `keyId`：凭证身份，属于权限与配额维度。

前两个是「追踪标识」，后两个是「业务标识」。它们都应该出现在日志和 span 里，都不应该出现在 Prometheus 的标签里。Prometheus 需要的标签是低基数、有限枚举的那些：provider、logical_model、deployment、status、error_type、stage、stream。

第三件事是阶段切分。所谓「定位到阶段」，前提是阶段本身是稳定枚举。我在 Pipeline 里固定了这样一组阶段：`PARSE`、`AUTH`、`RATE_LIMIT`、`BUDGET`、`ROUTE`、`CALL`、`RETRY`、`FALLBACK`、`STREAM`、`BILLING`。阶段是有限的、可枚举的、数量级在十位数以下的——这正是一个合格的指标维度。

第四件事是 TTFT。流式场景里，整段耗时和用户体验几乎无关，用户感知的是「第一个 token 什么时候到」。如果只在 `SseEmitter.complete()` 的时候停表，你得到的指标会显示一切正常，而用户仍然在骂娘。TTFT 必须是一个独立的计时器，在收到第一个 chunk 时停表。

> 基数有预算
> 维度须克制
> 日志承其重
> 指标守其轻

# 04、架构

```text
[输入] /v1/chat/completions（同步 JSON 或 SSE 流）
    |
    v
[模块] IdentityFilter → Pipeline(PARSE/AUTH/RATE_LIMIT/BUDGET/ROUTE/CALL/RETRY/FALLBACK/STREAM/BILLING)
    |
    v
[数据/状态] GatewayIdentity（MDC + Reactor Context）/ MeterRegistry / Span
    |
    v
[处理] 每阶段开启 Observation，低基数维度入指标，高基数标识入日志
    |
    v
[输出] /actuator/prometheus + JSON 结构化日志 + Grafana 看板
```

边界很清楚：这一层只解决「看得见」，不解决「跑得快」。它不改变路由算法，不改变重试策略，也不替代压测。它做的事情只有三件：给请求发一个统一身份、给每个阶段记一笔账、把账汇总成可查询的形式。

收益是排障路径从「grep 时间窗口」变成「按 requestId 拉一条时间线」，从「接口整体 P95」变成「按 provider 和 stage 切的 P95」。有了阶段维度的耗时，你甚至能看出重试是不是在掩盖一个本来就很慢的上游。

代价有两条。第一条是侵入性：每个 Pipeline 阶段都要包一层计时和打点，代码会有一定重复，需要抽一个 helper 收口。第二条是存储成本：`publishPercentileHistogram()` 会让每条 Timer 产生一组 bucket 序列，指标端点的体积会变大，需要按实际查询需求决定哪些 Timer 开直方图。

适用条件也得说清楚：这套方案的前提是阶段枚举稳定。如果 Pipeline 阶段还在天天变，第一个月你会把标签重命名好几遍，历史数据也就断了。所以第 15 境先把控制台和管理面收口，第 16 境再做观测，顺序是对的。

> 入口铸一纹
> 段段皆留痕
> 高基入日志
> 低基入指标

package com.litellmgateway.observability;

import java.util.UUID;

public final class GatewayIdentity {

    public static final String REQUEST_ID = "requestId";
    public static final String TRACE_ID = "traceId";
    public static final String PROJECT_ID = "projectId";
    public static final String KEY_ID = "keyId";
    public static final String STAGE = "stage";
    public static final String ATTEMPT = "attempt";
    public static final String ROUTE = "route";

    private GatewayIdentity() {
    }

    public static String newRequestId() {
        return "req_" + UUID.randomUUID().toString().replace("-", "");
    }
}

第三步，入口过滤器统一注入标识，并把 requestId 回写到响应头，让调用方能拿着它来找你：

```java
package com.litellmgateway.observability;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class GatewayIdentityFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        String requestId = request.getHeader("X-Request-Id");
        if (requestId == null || requestId.isBlank()) {
            requestId = GatewayIdentity.newRequestId();
        }
        MDC.put(GatewayIdentity.REQUEST_ID, requestId);
        response.setHeader("X-Request-Id", requestId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(GatewayIdentity.REQUEST_ID);
        }
    }
}
```

第四步，指标集中到一个类里。注意这里每个方法传入的都是低基数维度，requestId 一个都没有：

```java
package com.litellmgateway.observability;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.DistributionSummary;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import org.springframework.stereotype.Component;

import java.time.Duration;

@Component
public class GatewayMetrics {

    private final MeterRegistry registry;

    public GatewayMetrics(MeterRegistry registry) {
        this.registry = registry;
    }

    public Timer.Sample start() {
        return Timer.start(registry);
    }

    public void request(String provider, String logicalModel, String deployment,
                        boolean stream, String status) {
        Counter.builder("gateway.requests")
                .tag("provider", nz(provider))
                .tag("logical_model", nz(logicalModel))
                .tag("deployment", nz(deployment))
                .tag("stream", Boolean.toString(stream))
                .tag("status", nz(status))
                .register(registry)
                .increment();
    }

    public void stopStage(Timer.Sample sample, PipelineStage stage, String status) {
        sample.stop(Timer.builder("gateway.request.duration")
                .tag("stage", stage.name().toLowerCase())
                .tag("status", nz(status))
                .publishPercentileHistogram()
                .register(registry));
    }

    public void ttft(String provider, String logicalModel, Duration duration) {
        Timer.builder("gateway.ttft")
                .tag("provider", nz(provider))
                .tag("logical_model", nz(logicalModel))
                .publishPercentileHistogram()
                .register(registry)
                .record(duration);
    }

    public void tokens(String provider, String logicalModel, String type, long count) {
        Counter.builder("gateway.tokens")
                .tag("provider", nz(provider))
                .tag("logical_model", nz(logicalModel))
                .tag("type", nz(type))
                .register(registry)
                .increment(count);
    }

    public void cost(String provider, String logicalModel, double amount) {
        DistributionSummary.builder("gateway.cost")
                .tag("provider", nz(provider))
                .tag("logical_model", nz(logicalModel))
                .baseUnit("usd")
                .register(registry)
                .record(amount);
    }

    public void providerError(String provider, String errorType, int status) {
        Counter.builder("gateway.provider.errors")
                .tag("provider", nz(provider))
                .tag("error_type", nz(errorType))
                .tag("status", Integer.toString(status))
                .register(registry)
                .increment();
    }

    public void fallback(String from, String to, String reason) {
        Counter.builder("gateway.fallback")
                .tag("from_provider", nz(from))
                .tag("to_provider", nz(to))
                .tag("reason", nz(reason))
                .register(registry)
                .increment();
    }

    public void rateLimitRejected(String scope, String reason) {
        Counter.builder("gateway.rate_limit.rejected")
                .tag("scope", nz(scope))
                .tag("reason", nz(reason))
                .register(registry)
                .increment();
    }

    private static String nz(String value) {
        return value == null || value.isBlank() ? "unknown" : value;
    }
}
```

第五步，在 Pipeline 里用一个 helper 把「计时 + 打点 + 阶段日志」收口，避免每个阶段重复抄一遍：

```java
package com.litellmgateway.pipeline;

import com.litellmgateway.observability.GatewayIdentity;
import com.litellmgateway.observability.GatewayMetrics;
import com.litellmgateway.observability.PipelineStage;
import io.micrometer.core.instrument.Timer;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;

import java.util.function.Supplier;

@Component
public class StageRunner {

    private static final Logger log = LoggerFactory.getLogger(StageRunner.class);

    private final GatewayMetrics metrics;

    public StageRunner(GatewayMetrics metrics) {
        this.metrics = metrics;
    }

    public <T> T run(PipelineStage stage, String attempt, Supplier<T> action) {
        Timer.Sample sample = metrics.start();
        MDC.put(GatewayIdentity.STAGE, stage.name().toLowerCase());
        MDC.put(GatewayIdentity.ATTEMPT, attempt);
        String status = "ok";
        try {
            return action.get();
        } catch (RuntimeException ex) {
            status = "error";
            log.warn("pipeline stage failed: {}", ex.getMessage());
            throw ex;
        } finally {
            metrics.stopStage(sample, stage, status);
            log.info("pipeline stage finished");
            MDC.remove(GatewayIdentity.STAGE);
            MDC.remove(GatewayIdentity.ATTEMPT);
        }
    }
}
```

# 06、排查

第一条诊断链，指标端点的基数问题。

现象：`/actuator/prometheus` 的响应体从几百 KB 涨到数 MB，抓取耗时肉眼可见地变长，应用堆内存也一直不降。

怀疑：有高基数标签混进来了。

检查：直接数一下序列条数，再看标签名。

```bash
curl -s http://localhost:8080/actuator/prometheus | grep -c '^gateway_requests_total'
curl -s http://localhost:8080/actuator/prometheus | grep -m1 '^gateway_requests_total'
```

证据：第一条命令的输出随请求数持续增长，第二条命令打印出来的样本行里出现了 `requestId="req_..."` 这样的标签。

**错误尝试：** 第一反应是去 Prometheus 侧加 `metric_relabel_configs`，在抓取时把 `requestId` 标签 drop 掉。这个思路错在位置：relabel 发生在抓取端，而高基数的序列是在应用的内存注册表里被创建和保留的，应用本身的内存和 CPU 开销一点没少，只是 Prometheus 那边看不到了。问题的源头在写入端，不在采集端。

根因：有代码路径把 `requestId`、`keyId` 当成 tag 传进了 `Counter.builder()`。

修复：在指标层做标签白名单，只允许 provider、logical_model、deployment、status、error_type、stage、stream 这几类低基数维度进入 Meter；标识类字段一律走 MDC 和结构化日志。

第二条诊断链，异步链路的 traceId 丢失。

现象：同一 requestId 的日志，在进入 Provider 调用之前 traceId 有值，`ROUTE` 阶段之后的部分 traceId 变成空。

怀疑：MDC 是 ThreadLocal，异步线程不继承。

检查：把同一 requestId 的日志按时间排序，看 traceId 在哪一行开始断。

```bash
grep 'req_9f2c1a7b4e6d43f0a1b2c3d4e5f60718' app.log | jq -r '[.stage, .traceId] | @tsv'
```

证据：`route` 那行的 traceId 是完整的十六进制串，`call` 那行是 `null`。

**错误尝试：** 在 WebClient 的回调里手动 `MDC.put(TRACE_ID, ...)`。这个做法在低并发下看起来能用，但它把上下文写进了线程池里的复用线程，一次请求写进去的 traceId 会污染下一个复用到这条线程的请求，排查时反而制造出更难解释的串线。

根因：MDC 绑定在线程上，而 Pipeline 里的 Provider 调用发生在 Reactor 的调度线程上，ThreadLocal 不跨线程传递。

修复：两个方向收口——同步线程池用 `TaskDecorator` 把父线程的 MDC 复制进子线程并在执行后清理；响应式链路用 Reactor Context 承载 traceId，在日志输出点从 Context 读回并写入 MDC。

第三条诊断链，TTFT 缺失。

现象：SSE 接口的 `gateway.request.duration` 的 P95 一直在正常区间，但调用方持续反馈首字很慢。

怀疑：计时器记录的位置不对。

检查：对比流式请求的耗时指标和上游首包到达的时间戳。

```bash
curl -N -s http://localhost:8080/v1/chat/completions \
  -H 'Authorization: Bearer sk-demo' \
  -H 'Content-Type: application/json' \
  -d '{"model":"gpt-4o-mini","stream":true,"messages":[{"role":"user","content":"hi"}]}' \
  -w '\ntotal=%{time_total}\n'
```

证据：指标里的 duration 和 curl 报出来的 `time_total` 几乎一致，也就是说停表的地方在整段流结束（`emitter.complete()`），而不是首个 chunk 到达。

根因：把「整段耗时」当成了「用户体验耗时」。流式场景下这两个量几乎无关。

修复：在收到第一个 chunk 时记录一次独立的 TTFT Timer，整段耗时仍然保留在 `gateway.request.duration` 的 `STREAM` 阶段里，两个指标共存，各回答一个问题。

> 疑处先取证
> 妄改最伤身
> 一条因果链
> 胜十次重启

# 07、优化

V2 的修改严格对着第 06 章的三条根因来。

第一条，针对「高基数标签写进了 Meter」。修改：在 `GatewayMetrics` 之上加一层标签白名单校验，凡是调用方传入的 tag key 不在白名单内，直接抛 IllegalArgumentException 并打一条 error 日志，让这类错误在开发和测试阶段就暴露，而不是等上线后才发现。同时把所有标识类字段统一改走 MDC。新行为是：Meter 的标签集合被固定在十来种取值组合以内，`/actuator/prometheus` 的体积不随请求数增长。验证方式就是第 06 章那条 `grep -cE 'requestId|keyId|userId'`，期望恒为 0，且连续压一段时间后端点体积保持稳定。

第二条，针对「异步线程 MDC 丢失」。修改：加一个 `TaskDecorator` 用于同步线程池，加一个 Reactor 的上下文读写工具用于响应式链路，两者都在 `finally` 里做清理。新行为是同一 requestId 的所有阶段日志都带同一个 traceId。验证方式是第 06 章那条按 requestId 拉时间线的命令，期望每一行的 traceId 都非空且完全一致。

第三条，针对「TTFT 被整段耗时掩盖」。修改：在 `STREAM` 阶段里，首个 chunk 到达时调用 `metrics.ttft(...)` 停表，并且只在 `stream=true` 时执行。新行为是多出 `gateway_ttft_seconds` 的直方图，可以按 provider 和 logical_model 切出首字延迟分布。验证方式是对同一个上游分别发同步和流式请求，观察 TTFT 指标只在流式请求上增长。

顺带做的一处收口：把结构化日志的字段固定下来。日志里只放标识和上下文，不放指标该管的东西，也不放上游响应的完整 body（避免日志里出现用户 prompt）。

```json
{
  "level": "WARN",
  "logger": "com.litellmgateway.pipeline.StageRunner",
  "message": "pipeline stage failed",
  "requestId": "req_9f2c1a7b4e6d43f0a1b2c3d4e5f60718",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "projectId": "proj_default",
  "keyId": "vk_9",
  "stage": "call",
  "attempt": "2",
  "route": "gpt-4o-mini->deployment-azure-eastus",
  "provider": "azure",
  "errorType": "timeout"
}
```

如果项目基线是 Spring Boot 3.4 及以上，可以直接用内置的结构化日志能力输出这种格式；更低版本则用 logback 的 JSON encoder 自己拼。这一点需按当前官方文档核验你所用版本支持的配置项名称。

四张图的查询也一起落下来。Provider 健康度用错误率近似：

```promql
1 - (
  sum by (provider) (rate(gateway_provider_errors_total[5m]))
  /
  sum by (provider) (rate(gateway_requests_total[5m]))
)
```

Error Top 按错误类型聚合：

```promql
topk(10, sum by (provider, error_type) (increase(gateway_provider_errors_total[1h])))
```

P95 用直方图算，这是开启 `publishPercentileHistogram()` 之后才有的：

```promql
histogram_quantile(0.95,
  sum by (le, logical_model) (
    rate(gateway_request_duration_seconds_bucket{stage="call"}[5m])
  )
)
```

Fallback Rate 是兜底次数占总请求的比例：

```promql
sum(rate(gateway_fallback_total[5m]))
/
sum(rate(gateway_requests_total[5m]))
```

> 改法不须多
> 三处对症下
> 一验定成效

# 08、演进

```text
[同一输入] POST /v1/chat/completions (stream=true)
    |
    +--[V1] 入口造 requestId，各阶段各写日志；只有整段耗时；标签里混入 requestId
    |       代价：失败请求无法定位阶段，指标端点体积随请求数增长
    |
    +--[V2] 统一四类标识，阶段枚举入指标，TTFT 独立计时，标签白名单收口
    |       代价：每个阶段多一层包装，直方图让指标端点变大，阶段变更需同步改枚举
    |
[Trade-off]
得到：失败请求可按 requestId 还原完整阶段时间线，可按 provider/stage 切 P95 与错误率
失去：一点运行时开销和指标存储空间，以及 Pipeline 阶段不能再随手改名
适用边界：阶段枚举稳定的网关；如果 Pipeline 还在剧烈重构，先别急着定死指标维度
```

正确性上，V1 并非「错」，它只是把三类信息混在了一个载体里：标识（高基数）、维度（低基数）、明细（高体积）。V2 做的是分流，而不是增加信息量。

稳定性上，V2 明显更好。V1 的指标端点体积随流量增长，属于一种慢性的、会在某个流量拐点上突然暴露的故障；V2 把标签基数固定住之后，这个拐点就不存在了。

复杂度上 V2 更高。多了一层 `StageRunner`，多了一个标签白名单，多了 MDC 在异步链路上的传递逻辑。这些代码本身不复杂，但它们在每一个 Pipeline 阶段都会出现，任何一次阶段增删都要同步改枚举和看板。

成本上，主要的增量在指标存储：直方图 bucket 让每条 Timer 展开成多条序列。要不要给某个 Timer 开直方图，取决于你是否真的需要分位数查询，不查就别开。

适用范围上，这套方案适用于「阶段稳定、上游多变」的网关。如果反过来，阶段天天变而上游只有一个，那这套投入的性价比就要重新算。

遗留问题有两个。第一，`traceId` 目前只在应用内部传递，跨 Provider 的 HTTP 调用还没有真正带上 `traceparent` 头，跨进程链路还需要在 Provider 客户端里补一层注入。第二，回归测试覆盖的是行为正确性，不覆盖基数正确性——还没有一条测试专门断言标签白名单之外的内容不会出现在指标端点里。

> 同入不同果
> 取舍在边界
> 旧法未可弃
> 新法未可全

# 09、洞见

## 9.1 标识先于指标

这一境最容易走反的顺序，是先想「我要打哪些指标」，再回头补标识。真实顺序应该反过来：先定清楚一条请求的身份怎么生成、怎么传递、怎么落地，指标才有稳定的聚合维度可挂。第 05 章里 `GatewayIdentity` 和 `PipelineStage` 这两个类加起来不到二十行，但它们是后面全部代码的地基。地基没打，指标打出来也是一盘散沙。

## 9.2 可观测性的成本是乘法，不是加法

反直觉判断：给指标多加一个标签，成本不是「加一」，而是「乘以这个标签的取值数量」。三个五取值的标签，是 125 条序列；再塞进一个取值等于请求数的 requestId，序列数就跟着流量走。这也是为什么第 06 章那条错误尝试是错的——在采集端 drop 标签，写入端的爆炸一点没停。要控制成本，只能在写入端控制维度。

## 9.3 日志比指标更适合承载高基数

反直觉判断：直觉上「指标更省空间」，所以大家习惯把一切塞进标签；但在高基数的场景里，结论正好相反。指标是按序列索引的，序列基数一高，索引本身就成了瓶颈；而日志是追加写的，写一条丢一条的成本是线性的。所以 requestId、keyId、userId 这类东西，天生应该待在日志和 span 里，指标只保留那十来个能长期聚合的枚举维度。

## 9.4 阶段即验收口径

「失败请求可定位到具体 Pipeline 阶段」这句话，听起来像验收描述，实际上是一个架构约束：它要求阶段必须是稳定枚举、必须能被打点包装、必须能被日志携带。如果这三个条件不满足，这句话就永远只能写在文档里。这也是为什么我把阶段枚举放在第 05 章而不是放到最后——它是被架构推导出来的，不是被临时加上去的。

> 标识先于度
> 成本乘不除
> 阶段即口径
> 排障即成图
