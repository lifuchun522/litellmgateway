# 可解释的模型路由：四种策略、候选过滤与运行时指标落地

> 路由不是抽签，选谁都得说得清

```text
[读者] 正在把 LLM 网关从 Demo 推向生产的 Java 后端与平台工程师
[痛点] 同一个逻辑模型下挂了多个部署，却只会随机挑一个，出事说不清为什么
[现在读] 路由决策层是网关从能转发变成能运营的分水岭，这一层不补，后面全是空转
[读完] 能做出一套可解释、可回放、可调权的四种策略路由
```

```text
[旧方案] 一个 logical model 对应一个 deployment，请求直接转发
    |
    v
[新需求] 同一个 logical model 下挂多个 deployment：多账号、多区域、多集群
    |
    v
[冲突] 选谁？为什么选它？它不可用时选谁？权重改了流量为什么不变？
    |
    v
[后果] 路由成为黑盒，扩容、灰度、降级全靠猜，故障复盘拿不出证据
```

我是老李，在深圳做后端架构。过去半年，我一直在把一套 LiteLLM 风格的网关从 Demo 往生产推。前面几个阶段，我们把 Demo 逆向完、项目名和包名换掉、七模型本体立住、OpenAI 兼容协议和 Gateway Pipeline 打通、Provider 与 Deployment 也接上了。到这一步，网关其实只会做一件事：把请求转给唯一的那一个下游。

真正的生产不长这样。同一个逻辑模型背后通常挂着三到五个 Deployment：主账号、备用账号、区域副本、自建推理集群。它们的额度、时延、可用性、能力各不相同。运维会把主通道权重调到 80，会在主通道被限流时要求自动降权，会在新集群上线时先放一点流量探路。

任务是清楚的：让同一个 logical model 能按策略分配到多个 deployment。而前面所有章节里，候选永远只有一个；这一章第一次要面对候选有一堆的局面。选择本身不难，难的是选择之后——第二天有人问，为什么昨晚这批请求走了备用通道，你能不能在半分钟内答上来。

当同一个逻辑模型背后挂着五个部署，网关凭什么把这次请求交给其中某一个？

是永远走优先级最高的、按权重摇号、均匀随机，还是挑延迟最低的那一个？

如果选错了，而且事后根本查不出为什么选它，这套网关还有谁敢往生产上放？

# 01、故事

事情起因很小。运维提了一个需求：主通道额度快满了，希望网关能自动把一部分流量挪到备用通道，挪多少要能调，出问题要能马上调回来。

我第一版的实现非常朴素——在转发代码里加了一段判断：如果主 Deployment 的开关是开的就走主通道，否则遍历剩下的 Deployment 列表，取第一个可用的。上线当天没出事，第二天出事了。

具体现象是：备用通道的账单一直在涨，主通道的额度却始终没用满。我去翻代码才想起来，判断条件写反了半行——主 Deployment 的启用状态读的是缓存里的旧值，而缓存是在启动时加载的，改配置不重启不生效。更糟的是，第二天有人问「昨晚为什么走备用」，我翻遍日志只能找到一条 HTTP 记录，没有任何地方记录「当时有哪些候选、各自为什么被排除、最后为什么选它」。

那一刻我意识到，路由这件事，写出一个能跑的分支很简单，写出一段能被复盘的分支很难。

> 一模型多部署
> 一问谁先接单
> 一策未立之前
> 全靠人工猜

# 02、问题

旧方案失效的地方很具体：候选只有一个的时候，路由等于转发，没有决策；候选有多个的时候，代码里的每一条 if 都是一次没有记录的决策。

业务层面的影响是三条。第一，流量不可控：想让某个通道多扛一点，只能改代码；第二，降级不可信：主通道被限流，网关不一定知道该切，切到哪也不知道依据；第三，事故不可复盘：事后只能看到结果，看不到过程。

技术层面的表现也很具体。同一份 logical model 的配置在不同代码路径里被读了三遍，三遍的过滤条件各不相同；有的地方只判断 enabled，有的地方判断 enabled 加健康状态，有的地方干脆不判断。到了线上，就是「配置和实际行为对不上」。

所以这一章需要一个可验证的完成标准。我把验收写成一句话：**同一个 logical model 可以按策略分配到多个 deployment，并且每一次分配都能拿出一份包含候选、过滤原因、最终选择的解释记录。**

这句话里没有「快」，没有「稳」，只有「可分配」和「可解释」。因为在一个还在往生产走的网关上，可解释是先决条件——不能解释的策略，你敢开，我不敢调。

> 旧策略已失效
> 新候选排成行
> 说不清为何选
> 生产不敢上

# 03、原理

这一章真正要立的原理，是把「路由」拆成四个动作：过滤、打分、选择、记录。很多团队只做了第三件事，前两件混在业务代码里，第四件根本不存在。

第一个，也是最容易被忽略的一点：**过滤必须发生在打分之前。**

反直觉判断：很多人以为过滤是「把不能用的去掉」，属于清理动作，放哪儿都行。实际上过滤的位置直接决定了权重配置的语义。假设两个实例的权重是 80 和 20，其中一个被禁用。如果先按权重抽签再检查可用性，抽到被禁用的那个就重抽一次，那么剩余那个实例实际承接了 100% 的流量，而运维手上看到的配置仍然是 80。配置和行为之间出现了一个静默的偏差，而这个偏差在事故复盘时最难解释——因为配置是对的，代码也是对的，只有顺序是错的。

第二个原理：优先级和权重不是同一件事。优先级回答的是「这一批实例是不是该被考虑」，权重回答的是「在这一批里各分多少」。它们是两层决策，不是一个连续的打分。把优先级翻译成「权重乘以一个很大的系数」，看起来能工作，实际上会在权重差异较大时产生奇怪的交叉——一个优先级高但权重极低的实例，可能被一个优先级低但权重极高的实例压过去。

第三个原理：延迟指标必须是衰减的，不能是累计平均。累计平均的数学含义是「这个实例自上线以来的全部表现」，它对刚刚发生的劣化反应迟钝。一个已经跑了十万次请求、平均延迟 200ms 的实例，接下来连续十次飙到 5s，平均延迟几乎纹丝不动。路由如果看的是这个数，它会在实例已经坏掉的时候继续把流量压上去。

第四个原理：延迟最低不等于最该被选。这一点留到排查那一章用证据说话，先记住这个结论就行。

> 先过滤再打分
> 优先生死分层
> 权重只管内斗
> 延迟须衰减

# 04、架构

```text
[输入] 带 capabilities / projectId / virtualKeyId 的模型调用请求
    |
    v
[模块] CandidateFilter（禁用/熔断/能力/权限四层过滤）
    |
    v
[数据/状态] RoutePolicy + RouteTarget + LatencyRegistry(EWMA/failures)
    |
    v
[处理] RoutingStrategy 插件（PRIORITY / WEIGHTED / RANDOM / LEAST_LATENCY）
    |
    v
[输出] 选中的 deployment + RouteExplanation 决策记录
```

边界在哪里？这一层只负责「选哪个 deployment」，不负责「调用失败之后怎么办」。重试、退避、熔断后半开探测属于后面的章节。路由层唯一需要向它们暴露的，是一个稳定的选择结果和一份可读的解释记录。

收益是什么？收益是路由从一段代码变成了一个可以配置、可以模拟、可以复盘的决策层。权重和优先级进数据库和管理页面，策略变成插件，替换策略不需要改调用链。

代价是什么？代价有三样。第一，多了一次数据读取和一次指标查询，路由不再是零成本分支；第二，多了一张决策记录表，写放大是真实存在的，记录必须能采样、能过期；第三，多了一层抽象，新人接手时要先理解「候选」这个中间概念。

适用条件是什么？这套设计适合「同一逻辑模型下有多于一个等价部署」的场景。如果整个网关下面只有一个 Provider 一个账号，那么这一层是纯粹的负担，先不要引入。

> 边界划在入口
> 状态留在运行
> 决策落成记录
> 收益伴随代价

核心实现。先定义候选、拒绝与解释三个记录：

```java
package com.llmgw.route;

public enum RouteStrategy { PRIORITY, WEIGHTED, RANDOM, LEAST_LATENCY }

public enum RejectReason {
    TARGET_DISABLED, DEPLOYMENT_DISABLED, UNHEALTHY, CAPABILITY_MISMATCH, PERMISSION_DENIED
}

public record Candidate(long deploymentId, int priority, int weight) {}

public record Rejection(long deploymentId, RejectReason reason, String detail) {}

public record RouteExplanation(
        long logicalModelId,
        RouteStrategy strategy,
        java.util.List<Candidate> candidates,
        java.util.List<Rejection> rejections,
        long selectedDeploymentId,
        String decision,
        long elapsedMicros) {}
```

过滤器，四层判断，顺序固定：

```java
package com.llmgw.route;

import org.springframework.stereotype.Component;
import java.util.*;

@Component
public class CandidateFilter {

    private final RouteTargetRepository targets;
    private final DeploymentRepository deployments;
    private final HealthRegistry health;
    private final AuthorizationService auth;

    public CandidateFilter(RouteTargetRepository targets, DeploymentRepository deployments,
                           HealthRegistry health, AuthorizationService auth) {
        this.targets = targets;
        this.deployments = deployments;
        this.health = health;
        this.auth = auth;
    }

    public FilterResult filter(long logicalModelId, RouteContext ctx) {
        List<Candidate> passed = new ArrayList<>();
        List<Rejection> rejected = new ArrayList<>();
        for (RouteTargetView t : targets.findViews(logicalModelId)) {
            Rejection r = check(t, ctx);
            if (r == null) {
                passed.add(new Candidate(t.deploymentId(), t.priority(), t.weight()));
            } else {
                rejected.add(r);
            }
        }
        return new FilterResult(passed, rejected);
    }

    private Rejection check(RouteTargetView t, RouteContext ctx) {
        if (!t.targetEnabled()) {
            return new Rejection(t.deploymentId(), RejectReason.TARGET_DISABLED, t.reason());
        }
        if (!t.deploymentEnabled()) {
            return new Rejection(t.deploymentId(), RejectReason.DEPLOYMENT_DISABLED, t.reason());
        }
        if (health.state(t.deploymentId()) == BreakerState.OPEN) {
            return new Rejection(t.deploymentId(), RejectReason.UNHEALTHY,
                    health.snapshot(t.deploymentId()));
        }
        Set<String> missing = new HashSet<>(ctx.requiredCapabilities());
        missing.removeAll(t.capabilities());
        if (!missing.isEmpty()) {
            return new Rejection(t.deploymentId(), RejectReason.CAPABILITY_MISMATCH, missing.toString());
        }
        if (!auth.isDeploymentAllowed(ctx.projectId(), ctx.virtualKeyId(), t.deploymentId())) {
            return new Rejection(t.deploymentId(), RejectReason.PERMISSION_DENIED, t.reason());
        }
        return null;
    }
}

record FilterResult(List<Candidate> candidates, List<Rejection> rejections) {}
```

策略插件，接口只有一个方法，权重抽取单独封成一个工具：

```java
package com.llmgw.route;

import java.util.List;
import java.util.Random;

public interface RoutingStrategy {
    RouteStrategy type();
    Candidate select(List<Candidate> candidates, RouteContext ctx);
}

final class WeightedPicker {
    private WeightedPicker() {}

    static Candidate pick(List<Candidate> list, Random random) {
        int total = 0;
        for (Candidate c : list) {
            total += Math.max(c.weight(), 0);
        }
        if (total <= 0) {
            return list.get(random.nextInt(list.size()));
        }
        int cursor = random.nextInt(total);
        int acc = 0;
        for (Candidate c : list) {
            acc += Math.max(c.weight(), 0);
            if (cursor < acc) {
                return c;
            }
        }
        return list.get(list.size() - 1);
    }
}
```

四种策略。PRIORITY 是「先取最小优先级的那一批，再在批内按权重抽」：

```java
package com.llmgw.route;

import org.springframework.stereotype.Component;
import java.util.Comparator;
import java.util.List;

@Component
public class PriorityStrategy implements RoutingStrategy {

    @Override
    public RouteStrategy type() { return RouteStrategy.PRIORITY; }

    @Override
    public Candidate select(List<Candidate> candidates, RouteContext ctx) {
        int best = candidates.stream().mapToInt(Candidate::priority).min().orElseThrow();
        List<Candidate> tier = candidates.stream()
                .filter(c -> c.priority() == best)
                .sorted(Comparator.comparingLong(Candidate::deploymentId))
                .toList();
        return WeightedPicker.pick(tier, ctx.random());
    }
}

@Component
public class WeightedStrategy implements RoutingStrategy {

    @Override
    public RouteStrategy type() { return RouteStrategy.WEIGHTED; }

    @Override
    public Candidate select(List<Candidate> candidates, RouteContext ctx) {
        return WeightedPicker.pick(candidates, ctx.random());
    }
}

@Component
public class RandomStrategy implements RoutingStrategy {

    @Override
    public RouteStrategy type() { return RouteStrategy.RANDOM; }

    @Override
    public Candidate select(List<Candidate> candidates, RouteContext ctx) {
        return candidates.get(ctx.random().nextInt(candidates.size()));
    }
}
```

LEAST_LATENCY 是唯一带状态的策略，需要运行时指标配合：

```java
package com.llmgw.route;

import org.springframework.stereotype.Component;
import java.util.Comparator;
import java.util.List;

@Component
public class LeastLatencyStrategy implements RoutingStrategy {

    private final LatencyRegistry latency;
    private final RoutingProperties props;

    public LeastLatencyStrategy(LatencyRegistry latency, RoutingProperties props) {
        this.latency = latency;
        this.props = props;
    }

    @Override
    public RouteStrategy type() { return RouteStrategy.LEAST_LATENCY; }

    @Override
    public Candidate select(List<Candidate> candidates, RouteContext ctx) {
        long minSamples = props.getLeastLatency().getExploreMinSamples();
        List<Candidate> cold = candidates.stream()
                .filter(c -> latency.samples(c.deploymentId()) < minSamples)
                .toList();
        if (!cold.isEmpty()) {
            return WeightedPicker.pick(cold, ctx.random());
        }
        return candidates.stream()
                .min(Comparator.comparingDouble(c -> latency.score(c.deploymentId(),
                        props.getLeastLatency().getFailurePenalty())))
                .orElseThrow();
    }
}
```

指标登记器用 EWMA，样本少时衰减快，样本多时衰减慢，同时对失败率做惩罚：

```java
package com.llmgw.route;

import org.springframework.stereotype.Component;
import java.util.concurrent.ConcurrentHashMap;

@Component
public class LatencyRegistry {

    private static final double ALPHA_WARM = 0.5;
    private static final double ALPHA_STEADY = 0.1;

    private final ConcurrentHashMap<Long, Stat> stats = new ConcurrentHashMap<>();

    public void record(long deploymentId, long nanos, boolean failed) {
        stats.computeIfAbsent(deploymentId, k -> new Stat()).record(nanos, failed);
    }

    public long samples(long deploymentId) {
        Stat s = stats.get(deploymentId);
        return s == null ? 0L : s.samples();
    }

    public double score(long deploymentId, double failurePenalty) {
        Stat s = stats.get(deploymentId);
        if (s == null) {
            return Double.MAX_VALUE;
        }
        double millis = s.ewmaNanos() / 1_000_000.0;
        double failureRate = s.samples() == 0 ? 0.0 : (double) s.failures() / s.samples();
        return millis * (1.0 + failurePenalty * failureRate);
    }

    private static final class Stat {
        private long samples;
        private long failures;
        private double ewmaNanos;

        synchronized void record(long nanos, boolean failed) {
            samples++;
            if (failed) {
                failures++;
            }
            double alpha = samples <= 8 ? ALPHA_WARM : ALPHA_STEADY;
            ewmaNanos = samples == 1 ? nanos : (1 - alpha) * ewmaNanos + alpha * nanos;
        }

        synchronized long samples() { return samples; }
        synchronized long failures() { return failures; }
        synchronized double ewmaNanos() { return ewmaNanos; }
    }
}
```

路由服务把四段串起来，落记录，返回决策：

```java
package com.llmgw.route;

import org.springframework.stereotype.Service;
import java.util.*;

@Service
public class ModelRouter {

    private final CandidateFilter filter;
    private final RoutePolicyRepository policies;
    private final RouteExplainRepository explainRepo;
    private final Map<RouteStrategy, RoutingStrategy> strategies;

    public ModelRouter(CandidateFilter filter, RoutePolicyRepository policies,
                       RouteExplainRepository explainRepo, List<RoutingStrategy> strategyList) {
        this.filter = filter;
        this.policies = policies;
        this.explainRepo = explainRepo;
        this.strategies = new EnumMap<>(RouteStrategy.class);
        for (RoutingStrategy s : strategyList) {
            this.strategies.put(s.type(), s);
        }
    }

    public RouteDecision route(long logicalModelId, RouteContext ctx) {
        long start = System.nanoTime();
        RoutePolicy policy = policies.findEnabled(logicalModelId)
                .orElseThrow(() -> new NoRouteException(logicalModelId));
        FilterResult fr = filter.filter(logicalModelId, ctx);
        if (fr.candidates().isEmpty()) {
            throw new NoRouteException(logicalModelId, fr.rejections());
        }
        RoutingStrategy strategy = strategies.get(policy.strategy());
        Candidate picked = strategy.select(fr.candidates(), ctx);
        RouteExplanation explanation = new RouteExplanation(
                logicalModelId, policy.strategy(), fr.candidates(), fr.rejections(),
                picked.deploymentId(), describe(policy, picked),
                (System.nanoTime() - start) / 1000);
        explainRepo.save(explanation);
        return new RouteDecision(picked.deploymentId(), explanation);
    }

    private String describe(RoutePolicy p, Candidate c) {
        return p.strategy() + " -> dep " + c.deploymentId()
                + " | priority " + c.priority()
                + " | weight " + c.weight();
    }
}
```

看到 candidates 和 rejections 同时非空、并且 selectedDeploymentId 落在 candidates 里，这一版就算跑通了。跑通之后立刻会冒出新问题：反复调用时，能不能保证多个 deployment 都被选到？延迟指标怎么被写进去？这些留到排查那一章。

> 九步跑通一遍
> 表在库中落地
> 类在包中各归
> 输出可被回放

# 06、排查

**现象一：切到 LEAST_LATENCY 之后，五个 deployment 只有两个在承接流量。**

怀疑：延迟采集没上报，其余三个被判定为高延迟。

检查：调解释接口看最近若干次决策，同时打印 LatencyRegistry 的样本数。

证据：被选中的两个 deployment，samples 持续增长；另外三个 samples 恒为 0，而 score 对无样本返回 Double.MAX_VALUE。

根因：我把「无样本」等同于「极慢」。慢的实例永远排不到前面，也就永远拿不到新样本，于是永远慢下去。典型的冷启动饥饿——观测越少的实例越不被选，越不被选观测越少。

修复：V2 增加探索组，samples 低于 explore-min-samples 的实例先按权重抽签，攒够样本后再回到延迟比较。

**错误尝试：** 有人第一反应是把无样本时的返回值从 MAX_VALUE 改成 0，理由是「没有数据就先当作最快的」。为什么错？返回 0 等于向路由宣布这是一个零延迟神机，全部流量会在瞬间涌向它，直到第一个真实样本进来把它打回原形，然后全部流量又瞬间撤走。这不是修复了饥饿，而是把饥饿反转成了雪崩。正确做法是给「未知」一个独立的处理分支，而不是伪造一个「极好」的数值。

**现象二：把主通道权重从 100 改成 50，观察一段时间，流量分布纹丝不动。**

怀疑：权重没写进库，或者写了但没读。

检查：先直接查 route_target 表，再查仓库层 findEnabled 的返回值，最后看服务里有没有本地缓存。

证据：表里权重已经是 50 和 50，仓库层读出来也是 50 和 50，但策略拿到的对象里权重仍是旧值——缓存是在启动阶段一次性加载进本地 Map 的，没有任何失效入口。

根因：策略读的是启动快照，配置热更新链路缺失。改配置不重启，等于没改。

修复：给策略读取加一层带 TTL 的缓存，并让写接口在事务提交后主动失效；同时把「配置生效时间」记录进解释表，让复盘时能对齐时间线。

**现象三：一个带能力要求的请求，返回无可用部署，但管理页面上五个 deployment 全是启用状态。**

怀疑：健康检查把所有实例都判挂了。

检查：读解释记录里的 rejections 列表，而不是先看健康面板。

证据：五条 rejection 里三条是 CAPABILITY_MISMATCH，两条是 UNHEALTHY。

根因：候选过滤把「永久不匹配」和「暂时不可用」混在同一层，失败后直接抛异常，没有分级降级路径。管理页面上的 enabled 只代表开关状态，链路里还有熔断态、能力声明和 Project/Key 授权三层。

修复：把拒绝原因分层，永久不匹配与暂时不可用区别对待，并在解释记录里保留完整的 rejections，避免运维只能看到一句无可用部署。

> 现象先于猜测
> 证据先于结论
> 错误尝试一次
> 根因才敢落地

# 07、优化

第一个根因是冷启动饥饿，修改点在策略内部：新增探索组。修改原因：未知状态需要一个明确的、有限的探索预算，而不是被当成极端值参与比较。新行为：样本数低于阈值的实例优先按权重抽签承接流量，攒够样本后自动退出探索组。验证方式：反复调用同一个 logical model，观察解释记录中 selectedDeploymentId 是否出现多个不同取值，以及被选中 deployment 的 samples 是否都在增长。

第二个根因是配置快照不失效，修改点落在读取链路：给策略读取加 TTL 缓存，写接口提交后主动失效。修改原因：路由配置属于会被人频繁调整的运营参数，它的生命周期不该和进程一样长。新行为：改完权重，在 TTL 窗口之后自动生效，无需重启。验证方式：改权重，等待一个 TTL，重新读解释记录，确认 decision 字段里的权重值已更新。

第三个根因是拒绝原因不分层，修改点落在数据结构：Rejection 从纯字符串改为枚举加明细。修改原因：运维看到无可用部署的时候，需要的不只是一句失败，而是一张排除清单。新行为：每一次零候选的失败都带出完整的拒绝列表，并且能区分永久原因和暂时原因。验证方式：构造一个能力不匹配的请求，确认返回体中包含 CAPABILITY_MISMATCH 的具体缺失项。

第四个改动是给 LEAST_LATENCY 加上失败率惩罚。score 从「EWMA 延迟」变成「EWMA 延迟乘以失败率放大系数」。原因很简单：一个延迟很低但每分钟失败若干次的实例，用纯延迟看是优等生，用业务视角看是事故源。惩罚系数放进配置，便于在不同环境里单独调。

> 探索留出预算
> 缓存加上失效
> 拒绝分出层级
> 解释留全现场

# 08、演进

```text
[同一输入]
    |
    +--[V1] 单一 if 分支直接选 deployment / 代价：配错不生效，事后无记录
    |
    +--[V2] 过滤 + 策略插件 + 解释记录 / 代价：多两次读，多一张表，多一层抽象
    |
[Trade-off]
得到：可配置、可模拟、可复盘的决策层；失去：零成本分支和一部分直觉上的简单；适用边界：同一 logical model 下存在多于一个等价部署
```

正确性上，V1 的正确性依赖代码里的条件写对；V2 的正确性依赖配置与策略的组合被显式检查。V1 出错时表现为「配置对、行为不对」，V2 出错时表现为「解释记录和预期不符」——后者更容易被发现，也更容易被定位。

稳定性上，V2 多了两个新的不稳定源：指标采集与解释落库。指标写错会让选路倾斜，落库写错会让路由失败。所以 V2 必须把这两件事做成旁路可降级：采集异常不影响路由，落库异常只丢记录不丢请求。

复杂度上，V2 把一段 if 拆成了四个类加两张表。这个复杂度是实打实增加的，不是抽象带来的幻觉。它的合理性建立在候选数量会上涨这个前提上——如果候选永远只有一个，V2 就是负收益。

成本上，多了一次配置读取、一次指标查询和一次记录写入。控制手段分别是 TTL 缓存、内存指标和采样落库。这三样都不是可选项，缺一个就会在流量上涨时先崩掉。

适用范围上，这套结构对「多账号同模型」最有效，对「多模型异构路由」还需要扩展——因为后者要处理模型能力本身不同，而不只是同一模型的多个副本。

遗留问题有两个：第一，熔断状态只读不写，健康链路还没接上；第二，Key 级别的配额与路由尚未联动，被限流的 Key 仍可能被路由到最贵的通道。这两个问题留给后面的章节。

> 同输入分两路
> 一路省一路稳
> 取舍写在纸上
> 边界留在心里

# 09、洞见

## 9.1 路由的第一性问题是可解释，不是最优化

一个能跑但说不清的路由，和一个慢一点但事事有据的路由，在生产环境里价值完全不同。原因在于路由是运营接口：运维要靠它做灰度、降级、切量，而每一次调整之后，第一个问题永远是「现在流量到哪儿去了」。解释记录就是对这个问题的回答。没有它，所有策略调优都变成盲调。

## 9.2 反直觉判断：延迟指标越实时，路由越抖

直觉上，指标应该越新鲜越好。但路由决策是一个低频、重决策的动作，用瞬时延迟做选择，会把网络抖动、单次大请求、GC 停顿全部当成实例劣化，导致流量在两个实例之间来回横跳。EWMA 的意义不是「更准」，而是「更钝」——它主动放弃了对瞬时波动的响应能力，换取决策的稳定性。指标越平滑，路由越安静。

## 9.3 反直觉判断：过滤放在打分之后，权重会被静默稀释

大多数人是先算出「谁权重最大」再去检查它能不能用，抽到不可用的就重抽，看起来是等价的。但重抽会改变概率分布，而且改变的方向是往「剩下的实例怎么都行」去的。运维配的是 80 和 20，实际跑出来是 100 和 0，两边都觉得自己没错。过滤前置不是性能优化，而是语义修正。

## 9.4 优先级和权重必须分两层表达

把优先级压成一个大权重，看起来配置更简单，代价是丢掉了「同优先级内多实例」这个语义。真实场景里，一批同优先级的实例往往是对等的副本，它们之间应该按权重分摊；而不同优先级之间是主备关系，不该被权重交叉。两个语义混成一个数，就会出现「低优先级实例偶尔抢走高优先级流量」这种没人能解释的行为。

## 9.5 冷启动需要预留探索预算

任何基于历史表现的策略，都会对没有历史的新实例不友好。这不是 bug，是这类策略的固有属性。解决办法不是把新实例当成最好的，也不是把它排除在外，而是给它一个有限的、可见的探索额度：先按固定权重大量采样，攒够样本后自动退出。这个额度必须显式配置，因为「探索多少」是一个业务取舍，不是一个技术
