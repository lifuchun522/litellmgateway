## 一、这一境要解决的问题

第 01 境把 `open-api.zip` 逆成了可回归的 0 号基线，但那份基线从头到尾是别人的名字：坐标 `com.qvsu:qvsu-openapi`、产品名「聚搭OpenAPI系统」、配置前缀 `qvsu:`、产物 `qvsu-openapi.jar`。

改名的失效模式很具体：**报错驱动改名**——改一处、跑一次，漏一处、炸一处，前三个错误有效，到第五个就失控。而且最危险的不是改多了，是**改少了**：改 95% 在编译期不报错，在运行期静默失效。

所以本境的验收标准不是「改完」，是**行为零差异，且零差异由脚本判定**。

## 三、四处「编译器看不见」的字符串引用

粗体是验证方式——**这四处是本境真正会翻车的地方**，因为它们改了也不报错。

| # | 位置 | 旧值 | 验证方式 | 结果 |
|---|---|---|---|---|
| 1 | `mapper/**/*Mapper.xml` 的 `namespace` | `com.qvsu.system.mapper.*` | 起服务后访问依赖 Mapper 的页面 | 启动正常（Mapper 未因 namespace 不匹配在启动期报错） |
| 2 | `logback.xml` 的 `<logger name>` | `com.qvsu` | 观察应用自身包是否按配置级别输出 | 通过（诊断端点与业务日志均可见） |
| 3 | `banner.txt` 的 `${...}` 占位符 | `${qvsu.version}` | 启动横幅显示的版本号 | 新前缀实例显示 `1.0.0` |
| 4 | 数据库 `sys_job.invoke_target` | `qvsuTask.qvsuNoParams` 等（实测 19 行） | 提供幂等升级语句 + Bean 名不变 | 语句可重复执行，覆盖 3 种旧写法 |

> 第 4 条是本境最容易被漏掉的一条：**数据库里存着 Java 方法名**。改 Bean 名会让已存在的定时任务在下一次调度时找不到目标。本境的处置是「Bean 名保持 `qvsuTask` 不动 + 方法名改新值 + 幂等 SQL 升级」，并把 Bean 名的删除时间写进技术债。

**关于文章点名的三个翻车点**：文章说「改名翻车点集中在三处：`spring.factories`、MyBatis namespace、yml 前缀」。本工程**不存在 `spring.factories`**（全仓检索为空，因为它是 Spring Boot 2.7 的纯 Spring Boot 工程、没有自定义自动配置）。这条差异记入第六节。

## 四、兼容期设计

### 规则（三条，集中在 `LegacyPrefixCompat` 一个类里）

| 场景 | 行为 |
|---|---|
| 只有旧前缀 `qvsu:` | 把值搬到 `LlmGatewayConfig`，打废弃警告（含生效键名），标记 `legacyApplied=true` |
| 新旧前缀同时存在 | **新前缀优先**，旧前缀一个值都不采用，只记录「可以删了」 |
| 都没有 | 不做任何事，`legacyApplied=false` |

### 为什么不用双前缀绑定

让一个配置类同时接受两个前缀，需要两套 setter 或自定义 `Binder`，会把「新前缀优先」这条规则打散到字段级别。集中在一个类里，规则只有一处，测试也只断言一处。

### 踩到的坑：第一版静默失效

第一版用 `Binder.bind("qvsu", Bindable.mapOf(String.class, String.class))` 读旧前缀，**绑不出来**——旧前缀是一组扁平标量键（`qvsu.name`），Binder 到 `Map` 只吃带层级的映射结构。实测 `values` 为空，于是兼容代码静默不生效：不报错、不告警、只是没起作用。

改成逐键 `env.getProperty("qvsu." + key)` 后正常。这个坑值得记下来，因为它是「静默失效」的教科书例子。

### 兼容状态怎么观测

新增只读端点 `GET /internal/compat/config-prefix`（`@Anonymous`）：

```json
{"effectiveName":"轻量级 LLM 网关","effectiveVersion":"1.0.0",
 "legacyApplied":false,"legacyKeys":"","newPrefixPresent":true,"legacyPrefixPresent":false}
```

**为什么不用启动横幅**：本境实测踩到两次误判——横幅上的 `${llmgateway.version}` 在配置未解析时会**原样打印占位符**；而旧前缀测试里它又恰好显示了旧值，看起来像生效了。横幅是给人看的，不是给断言用的。

### 离线单测

`LegacyPrefixCompatTest`（5 例）直接对 `LegacyPrefixCompat.resolve(Environment)` 断言，用 `MockEnvironment` 造输入，**不启动 Spring、不连数据库**：

```text
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
```

这是本仓库**第一个能在 CI 里真跑的测试**——第 01 境的 4 个集成测试都要连 5433 端口的 PostgreSQL，CI 里只能 `continue-on-error`。

> 为什么不干脆用 `@SpringBootTest`：`LlmGatewayConfig` 的字段是静态的（基线既有设计），多个最小上下文之间会串值，断言会退化成对上下文创建顺序的断言。改为直连判定逻辑后，测试只测本境新写的代码。

## 五、回归尺子（本境的灵魂）

### 基线快照存的是什么

`baseline/*.json`（6 个行为 + 1 个请求样例）：

```json
{"name":"models","method":"GET","path":"/v1/models","httpStatus":302,"location":"/login","contentType":""}
```

**不是响应正文。** 原因：`/login` 的 HTML 里含每次请求都变的 CSRF token 与会话 id，直接 diff 必然假阳性，而假阳性会训练人忽略这个门禁——比没有门禁更糟。归一化到「状态码 + 跳转目标 + 内容类型」后，diff 是确定性的，且足以证明**换骨没有改变路由与鉴权行为**。

### 实测结果

```text
== 与基线比对 ==
  一致：chat
  一致：index
  一致：login
  一致：models
  一致：nope
  一致：open

换骨回归通过：接口行为与基线一致      （退出码 0）
```

### 残留扫描

```text
== 1/3 旧包名 com.qvsu ==      无残留
== 2/3 旧配置前缀 qvsu: ==      无残留
== 3/3 旧制品/镜像/容器标识 ==   无残留

换骨残留检查通过
```

扫描脚本明确列出**有意保留**的旧标识，避免「扫不出来」被误读成「忘了改」。

### 两个踩到的坑

1. **回归脚本把请求样例当成行为快照**：第一版遍历 `baseline/*.json` 时把 `chat-req.json`（输入）也当快照比对，每轮都报「基线有、当前缺失」的假差异。修正为显式排除。
2. **本机 HTTP 代理导致探活失真**：本机设着 `HTTP_PROXY=http://127.0.0.1:15236`，不显式绕过时 `curl` 对本机端口一律返回 503、`HttpWebRequest` 直接挂住。两侧探活脚本都强制 `Proxy = null`。
